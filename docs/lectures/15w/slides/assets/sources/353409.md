# 8.4 내 업무 루틴에 붙이기

![8.4 내 업무 루틴에 붙이기 삽화](https://static.wikidocs.net/images/page/353409/8.4-%EB%82%B4-%EC%97%85%EB%AC%B4-%EB%A3%A8%ED%8B%B4%EC%97%90-%EB%B6%99%EC%9D%B4%EA%B8%B0.jpg)

LLM위키는 만들어 두는 순간 완성되는 문서함이 아닙니다. 업무가 바뀌면 자료도 바뀌고, 예전에 맞던 판단 기준도 낡습니다. 그래서 LLM위키를 오래 쓰려면 “언제 무엇을 넣고, 언제 무엇을 점검할지”를 업무 루틴 안에 붙여야 합니다.

이 절에서는 세 가지를 정합니다. 매일 어떤 자료를 넣을지 정하고, 주마다 무엇을 확인할지 정합니다. 마지막으로 LLM위키를 개인 업무 시스템의 일부로 확장하는 방법을 살펴봅니다. 목표는 거창한 자동화가 아니라, 다음 주의 내가 같은 설명을 반복하지 않게 만드는 것입니다.

## 매일 넣을 자료 정하기

매일 모든 자료를 위키에 넣으려 하면 금세 지칩니다. LLM위키에 넣을 자료는 “나중에 다시 쓸 가능성이 높은 업무 맥락”이어야 합니다. 회의 중 스쳐 지나간 잡담, 아직 공유 권한을 확인하지 않은 고객 정보, 원문이 없는 기억 조각은 바로 위키 문서로 만들지 않는 편이 안전합니다.

매일 넣을 자료를 고를 때는 세 가지 질문만 사용합니다.

- 다음에도 LLM에게 설명할 가능성이 있는가?
- 원천 자료를 남길 수 있는가?
- 업무 판단이나 산출물에 다시 쓰일 가능성이 있는가?

이 질문에 모두 “예”라고 답할 수 있으면 `raw/`에 원본을 보관합니다. 그런 다음 필요한 경우에만 `wiki/`에 정리된 문서를 만듭니다. Karpathy의 LLM Wiki 아이디어에서 제시한 `raw sources`, `wiki`, `schema` 구조를 업무 루틴으로 옮기면, 매일 할 일은 “원본을 보존하고, 다시 쓸 것만 정리하는 일”이 됩니다.

**학습자료: 매일 넣을 자료를 고르는 기준**

| 자료 후보 | 넣는 조건 | 먼저 둘 위치 | 바로 넣지 않는 경우 |
| --- | --- | --- | --- |
| 회의록 | 결정 사항, 담당자, 기한이 있다 | `raw/meetings/` | 참석자 동의나 공유 범위가 불분명하다 |
| LLM에게 반복 설명한 업무 규칙 | 다음 요청에도 같은 설명이 필요하다 | `wiki/rules/` 또는 `wiki/concepts/` | 개인 취향에 가까워 재사용 가능성이 낮다 |
| 공식 문서나 제품 문서 | 업무 판단의 근거로 쓰인다 | `raw/references/` | 최신성 확인이 필요한데 확인 날짜가 없다 |
| 고객 피드백 | 반복 패턴이나 우선순위 판단에 쓰인다 | `raw/feedback/` | 개인정보나 계약 정보가 그대로 들어 있다 |
| 보고서 초안 | 다음 보고서 형식의 기준이 된다 | `output/` | 근거가 연결되지 않은 일회성 문장이다 |
| 할 일 목록 | 실행 기준이나 의사결정 이력이 있다 | `raw/tasks/` 또는 `log.md` | 단순 개인 일정이라 지식으로 남길 필요가 없다 |

이 표는 “자료를 많이 모으기”보다 “다시 쓸 자료만 남기기”를 위한 기준입니다. 특히 원본과 정리 문서를 섞지 않는 것이 중요합니다. 원본은 나중에 사실을 다시 확인하는 기준점이고, 위키 문서는 LLM과 사람이 읽기 좋게 정리한 파생 지식입니다.

아니오

예

아니오

예

예

아니오

아니오

예

오늘 생긴 업무 자료

다음에도 쓸 가능성이 있는가?

넣지 않고 지나간다

원천 자료를 남길 수 있는가?

확인 필요 메모로만 남긴다

민감 정보나 권한 문제가 있는가?

마스킹하거나 보류한다

raw에 원본 저장

정리할 가치가 있는가?

log에 수집 기록만 남긴다

wiki 문서로 정리

index와 관련 문서에 연결

이 흐름에서 가장 중요한 지점은 `raw`에 넣기 전의 권한 확인입니다. LLM위키가 로컬 Markdown으로 구성되어 있더라도, LLM 도구나 플러그인으로 처리하는 순간 외부 모델 호출이나 웹 수집 정책이 개입할 수 있습니다. 고객 정보, 개인정보, 계약 정보, 비공개 코드는 조직의 기준을 먼저 확인해야 합니다.

### 실습: 하루 5분 입력 목록 만들기

**목표**

매일 LLM위키에 넣을 자료 후보를 빠르게 고르는 입력 목록을 만듭니다.

**실행 전제**

Markdown 문서를 편집할 수 있으면 됩니다. 특정 LLM 도구나 플러그인은 필요하지 않습니다.

**성공 기준**

하루 업무가 끝날 때 5분 안에 자료 후보를 `보관`, `정리`, `보류`, `버림` 중 하나로 분류할 수 있어야 합니다.

```markdown
Copy# daily-inbox.md

## 오늘 넣을 후보

| 시간 | 자료 | 출처 | 판단 | 이유 |
|---|---|---|---|---|
| 10:00 | 주간 회의록 | 회의 메모 | 보관 | 결정 사항과 담당자가 있음 |
| 14:30 | LLM에게 반복 설명한 보고서 톤 | 대화 기록 | 정리 | 다음 보고서에도 필요함 |
| 16:00 | 고객 A의 상세 불만 | 상담 메모 | 보류 | 개인정보 마스킹 필요 |
| 18:00 | 점심 메뉴 추천 대화 | 개인 메모 | 버림 | 업무 지식으로 재사용하지 않음 |

## 오늘 정리할 문서

- `wiki/rules/report-tone.md`
- `raw/meetings/2026-05-16-weekly.md`

## 확인 필요

- 고객 피드백을 위키에 넣기 전에 익명화 기준 확인
```

이 템플릿은 “매일 위키 문서를 완성하라”는 뜻이 아닙니다. 하루 끝에 자료의 운명을 정하는 장치입니다. 보관할 자료와 정리할 자료를 나누면, LLM위키는 부담스러운 저장소가 아니라 다음 작업을 줄여 주는 업무 메모가 됩니다.

## 주간 점검 흐름 만들기

매일 자료를 넣기만 하면 위키는 점점 커집니다. 커진 위키는 도움이 되기도 하지만, 오래된 주장과 출처 없는 요약을 함께 품게 됩니다. 그래서 주 1회는 “새 지식을 더하는 시간”이 아니라 “믿고 쓸 수 있는지 확인하는 시간”을 둡니다.

주간 점검의 핵심은 LLM위키의 기본 흐름인 `ingest → query → lint`를 작게 반복하는 것입니다. 새 자료를 넣고, 위키에 질문해 보고, 문서의 출처와 모순을 점검합니다. 여기서 `lint`는 특정 도구 명령만 뜻하지 않습니다. 사람이 체크리스트로 확인하는 것도 운영상 충분히 유효한 lint입니다.

**학습자료: 주간 점검 30분 흐름**

| 시간 | 할 일 | 확인 질문 | 결과물 |
| --- | --- | --- | --- |
| 5분 | 이번 주 추가 자료 확인 | `raw/`에 원본이 남아 있는가? | 누락 자료 목록 |
| 10분 | 많이 쓰인 위키 문서 확인 | 출처와 확인 날짜가 있는가? | 보완할 문서 1~3개 |
| 5분 | 오래된 주장 확인 | 최신성이 필요한 문장이 있는가? | `확인 필요` 표시 |
| 5분 | 충돌 확인 | 같은 주제에서 서로 다른 결론이 있는가? | 상충 메모 |
| 5분 | 다음 주 질문 정리 | 다음 업무에서 다시 물을 질문은 무엇인가? | `weekly-review.md` |

이 흐름은 짧아야 지속됩니다. 주간 점검에서 모든 문서를 고치려고 하면 다음 주부터 하지 않게 됩니다. 한 번에 고칠 문서는 1~3개로 제한합니다. 나머지는 `확인 필요`로 표시해도 충분합니다.

다음 주 업무점검질문wikiraw매일 입력다음 주 업무점검질문wikiraw매일 입력원천 자료 저장다시 쓸 지식만 정리이번 주 업무 질문으로 확인출처, 오래됨, 모순 점검보완 또는 확인 필요 표시다음 주 질문과 할 일 정리

이 도해에서 주간 점검은 위키를 깨끗하게 꾸미는 시간이 아닙니다. 다음 주 업무에서 틀린 답을 줄이는 시간입니다. 특히 LLM이 만든 위키 문서는 원본이 아니므로, 중요한 판단에는 반드시 원천 자료로 돌아갈 수 있어야 합니다.

### 실습: 확인 필요 문장을 자동으로 모으기

**목표**

`wiki/` 문서 안의 `확인 필요`, `출처 없음`, `TODO` 표시를 찾아 주간 점검 파일로 모읍니다.

**실행 전제**

macOS 또는 Linux에서 Bash/Zsh를 사용할 수 있어야 합니다. 이 예제는 데모 폴더를 새로 만들며, 기존 파일은 수정하지 않습니다.

**성공 기준**

실행 후 `output/weekly-review-날짜.md` 파일이 만들어지고, 점검할 문장 목록이 들어 있어야 합니다.

```bash
CopyBASE="${TMPDIR:-/tmp}/llm-wiki-weekly-review-demo"

if [ -e "$BASE" ]; then
  echo "이미 실습 폴더가 있습니다. BASE 값을 바꾸고 다시 실행하세요." >&2
  exit 1
fi

mkdir -p "$BASE/wiki" "$BASE/output"

cat > "$BASE/wiki/report-rule.md" <<'EOF'
# 보고서 작성 규칙

## 확인된 내용

- 실행 계획은 담당자, 기한, 검증 방법을 함께 쓴다.

## 확인 필요

- 임원 보고서에는 항상 1쪽 요약을 먼저 둔다.
EOF

cat > "$BASE/wiki/customer-feedback.md" <<'EOF'
# 고객 피드백 정리

- 반복 문의는 결제, 로그인, 알림 설정에 집중된다.
- 출처 없음: 로그인 문의가 전체의 절반 이상이다.
- TODO: 5월 상담 기록으로 다시 확인한다.
EOF

REPORT="$BASE/output/weekly-review-$(date +%F).md"

{
  echo "# 주간 LLM위키 점검"
  echo
  echo "## 점검 대상"
  echo
  grep -R -n -E "확인 필요|출처 없음|TODO" "$BASE/wiki" || true
} > "$REPORT"

echo "$REPORT"
sed -n '1,80p' "$REPORT"
```

예상 결과에서 날짜와 임시 폴더 경로는 실행 환경에 따라 달라집니다.

```text
Copy/tmp/llm-wiki-weekly-review-demo/output/weekly-review-YYYY-MM-DD.md
# 주간 LLM위키 점검

## 점검 대상

/tmp/llm-wiki-weekly-review-demo/wiki/report-rule.md:7:## 확인 필요
/tmp/llm-wiki-weekly-review-demo/wiki/customer-feedback.md:4:- 출처 없음: 로그인 문의가 전체의 절반 이상이다.
/tmp/llm-wiki-weekly-review-demo/wiki/customer-feedback.md:5:- TODO: 5월 상담 기록으로 다시 확인한다.
```

이 예제는 완전한 검증 도구가 아닙니다. 하지만 작은 위키에서는 충분히 쓸모가 있습니다. “확인 필요” 표시를 찾는 것만으로도 오래된 주장과 출처 없는 단정을 줄일 수 있습니다. `nvk/llm-wiki` 같은 구현체의 lint, audit, archive 기능을 사용하는 경우에도 원리는 같습니다. 도구가 찾아 준 항목을 사람이 원문과 대조해야 합니다.

## 개인 업무 시스템으로 확장하기

LLM위키가 한 달 이상 유지되면, 자연스럽게 다른 업무 도구와 연결하고 싶어집니다. 캘린더, 할 일 앱, 노트 앱, 코드 저장소, 보고서 폴더가 따로 움직이면 위키가 고립되기 때문입니다. 다만 처음부터 모든 도구를 연결하면 운영 부담이 커집니다.

개인 업무 시스템으로 확장할 때는 세 공간만 구분합니다.

- 입력함: 아직 판단하지 않은 자료가 들어오는 곳
- 위키: 다시 쓸 지식으로 정리한 곳
- 산출물: 보고서, 실행 계획, 회의 준비 자료처럼 업무에 제출하거나 실행할 결과물

이 세 공간이 분리되어 있으면 도구가 바뀌어도 운영 방식은 유지됩니다. Obsidian을 쓰든, 일반 Markdown 편집기를 쓰든, Codex나 Claude Code를 쓰든 핵심은 같습니다. 원본은 보존하고, 위키는 정리하고, 산출물은 근거로 돌아갈 수 있게 만듭니다.

**학습자료: 개인 업무 시스템 확장 지도**

| 업무 도구 | LLM위키와 연결하는 방식 | 주의할 점 |
| --- | --- | --- |
| 캘린더 | 회의 후 결정 사항과 후속 질문을 `daily-inbox.md`에 남긴다 | 참석자, 고객명, 비공개 안건을 그대로 넣지 않는다 |
| 할 일 앱 | 실행 항목의 배경 설명을 위키 문서에 연결한다 | 단순 할 일까지 모두 위키화하지 않는다 |
| 노트 앱 | 원문 메모와 위키 문서를 링크로 연결한다 | 원본과 요약을 같은 문서에 섞지 않는다 |
| LLM 도구 | `AGENTS.md` 또는 `CLAUDE.md`에 운영 규칙을 둔다 | 지침 파일은 행동을 보장하지 않으므로 결과를 검토한다 |
| 보고서 폴더 | `output/` 산출물에 근거 문서 링크를 남긴다 | 위키 문서를 원본처럼 인용하지 않는다 |

이 표는 도구를 많이 붙이라는 뜻이 아닙니다. 업무 흐름에서 이미 쓰는 도구가 있다면, LLM위키의 어느 공간과 연결할지 정하라는 뜻입니다. 연결할 위치가 정해지면 “이 자료는 어디에 넣어야 하지?”라는 고민이 줄어듭니다.

이 흐름에서 `AGENTS.md`와 `CLAUDE.md`는 위키 운영을 돕는 규칙 파일입니다. OpenAI Codex는 `AGENTS.md`를, Claude Code는 `CLAUDE.md`를 프로젝트 지침으로 활용합니다. 다만 이런 파일은 LLM의 행동을 강제로 보장하지 않습니다. “따르도록 유도하는 문서”로 이해하고, 중요한 결과는 주간 점검에서 확인해야 합니다.

### 실습: 개인 운영 규칙 만들기

**목표**

LLM 도구가 위키를 다룰 때 따라야 할 개인 운영 규칙을 문서로 만듭니다.

**실행 전제**

Codex를 주로 쓰면 `AGENTS.md`, Claude Code를 주로 쓰면 `CLAUDE.md`에 적습니다. 두 도구를 함께 쓰면 같은 내용을 두 파일에 맞게 관리합니다.

**성공 기준**

LLM에게 위키 정리를 맡길 때 원본 보존, 출처 표시, 확인 필요 표시를 반복 설명하지 않아도 됩니다.

```markdown
Copy# LLM위키 운영 규칙

## 기본 원칙

- `raw/`의 원천 자료는 임의로 수정하지 않습니다.
- `wiki/` 문서는 원천 자료를 바탕으로 정리한 파생 문서입니다.
- 중요한 주장에는 원천 자료 경로와 확인 날짜를 남깁니다.
- 근거가 부족한 내용은 `확인 필요`로 표시합니다.
- 오래된 정보일 가능성이 있으면 단정하지 않습니다.

## 매일 입력

- 회의록, 반복 업무 규칙, 공식 문서, 보고서 초안 후보만 우선 검토합니다.
- 개인정보, 고객 정보, 계약 정보는 마스킹 여부를 먼저 확인합니다.
- 자료를 넣었다면 `log.md`에 날짜와 처리 내용을 남깁니다.

## 주간 점검

- `확인 필요`, `출처 없음`, `TODO` 표시를 먼저 찾습니다.
- 이번 주 실제로 사용한 문서 1~3개만 보완합니다.
- 다음 주에 다시 물을 질문을 `output/weekly-review.md`에 정리합니다.
```

Codex 프로젝트에서는 이 내용을 `AGENTS.md`에 둘 수 있습니다. Claude Code 프로젝트에서는 같은 내용을 `CLAUDE.md`에 둘 수 있습니다. 이미 `AGENTS.md`를 쓰고 Claude Code에서도 같은 규칙을 쓰고 싶다면, Claude Code 문서 기준으로 `CLAUDE.md`에서 다른 파일을 가져오는 방식을 확인해야 합니다.

### 확장할 때 멈춰야 할 신호

개인 업무 시스템으로 확장하다 보면 자동화 욕심이 생깁니다. 하지만 다음 신호가 보이면 확장을 멈추고 루틴을 줄이는 편이 낫습니다.

| 신호 | 의미 | 줄이는 방법 |
| --- | --- | --- |
| 매일 입력이 10분을 넘는다 | 자료 선별 기준이 넓다 | “다음에도 쓸 자료”만 남긴다 |
| 주간 점검을 건너뛴다 | 점검 범위가 크다 | 문서 1~3개만 고친다 |
| 출처 없는 요약이 늘어난다 | 정리 속도가 검증 속도보다 빠르다 | `raw` 링크 없는 문서는 확인 필요로 둔다 |
| 도구 설정에 시간을 더 쓴다 | 운영보다 환경 관리가 커졌다 | 수동 Markdown 루틴으로 돌아간다 |
| 산출물이 위키와 끊어진다 | 결과물 재사용성이 낮다 | `output/` 문서에 근거 링크를 남긴다 |

LLM위키의 목적은 지식 관리 자체가 아닙니다. 업무를 다시 시작할 때 필요한 맥락을 줄이는 것입니다. 루틴이 복잡해져서 위키를 열기 싫어진다면, 입력 기준과 점검 기준을 줄여야 합니다.

## 정리와 검증 포인트

내 업무 루틴에 붙인 LLM위키는 세 가지 리듬으로 움직입니다.

- 매일: 다시 쓸 가능성이 높은 자료만 고릅니다.
- 매주: 출처, 오래됨, 모순, 확인 필요 표시를 점검합니다.
- 필요할 때: 캘린더, 노트, 할 일, LLM 도구와 연결하되 원본과 산출물을 분리합니다.

마지막으로 다음 질문에 답해 봅니다.

| 검증 질문 | 통과 기준 |
| --- | --- |
| 매일 어떤 자료를 넣을지 정했는가? | `보관`, `정리`, `보류`, `버림` 기준이 있다 |
| 원천 자료와 위키 문서가 분리되어 있는가? | `raw/`와 `wiki/`의 역할이 다르다 |
| 주간 점검 시간이 정해져 있는가? | 30분 안에 끝나는 체크리스트가 있다 |
| 출처 없는 주장을 찾을 방법이 있는가? | `확인 필요`, `출처 없음`, `TODO` 표시를 검색한다 |
| 개인 업무 도구와 연결 기준이 있는가? | 입력함, 위키, 산출물의 위치가 정해져 있다 |
| LLM 지침 파일을 과신하지 않는가? | 결과를 사람이 다시 검토한다 |

이 기준을 통과하면 LLM위키는 일회성 실습이 아니라 업무 루틴이 됩니다. 완벽한 위키를 만드는 것보다 중요한 일은, 다음 업무에서 바로 다시 쓸 수 있는 상태를 유지하는 것입니다.
