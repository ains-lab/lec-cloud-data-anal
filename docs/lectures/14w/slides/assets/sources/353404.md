# 7.3 다음 행동으로 연결하기

![7.3 다음 행동으로 연결하기 삽화](https://static.wikidocs.net/images/page/353404/7.3-%EB%8B%A4%EC%9D%8C-%ED%96%89%EB%8F%99%EC%9C%BC%EB%A1%9C-%EC%97%B0%EA%B2%B0%ED%95%98%EA%B8%B0.jpg)

보고서는 제출하면 끝나는 문서처럼 보입니다. 하지만 실제 업무에서는 보고서 뒤에 더 중요한 일이 남습니다. 누가 무엇을 할지 정하고, 회의에서 어떤 결정을 내려야 하는지 준비하고, 결정된 내용을 다시 지식으로 남겨야 합니다.

LLM위키를 쓰는 이유도 여기에 있습니다. 위키는 보고서 초안을 만드는 도구로만 쓰면 금방 한계가 옵니다. 더 좋은 쓰임은 산출물을 다음 행동으로 바꾸고, 그 행동의 결과를 다시 위키에 반영하는 흐름을 만드는 것입니다. 이 절에서는 보고서에서 실행 항목을 뽑고, 회의 준비 자료를 만들고, 산출물과 위키의 연결을 유지하는 방법을 다룹니다.

## 보고서에서 할 일 뽑기

보고서에는 보통 세 가지가 섞여 있습니다. 확인된 사실, 해석이나 판단, 앞으로 해야 할 일입니다. 이 셋을 구분하지 않으면 보고서는 읽기 좋은 문서로 끝납니다. 다음 행동으로 이어지려면 보고서의 문장을 실행 항목으로 바꿔야 합니다.

LLM위키에서는 이 작업을 더 안정적으로 할 수 있습니다. 보고서가 위키 문서와 원천 자료를 근거로 만들어졌기 때문입니다. 할 일을 뽑을 때도 “그럴듯한 지시”가 아니라 “근거가 있는 실행 후보”를 만들 수 있습니다.

### 보고서 문장을 실행 항목으로 바꾸기

보고서에서 바로 실행할 수 없는 문장은 보통 넓게 쓰여 있습니다.

```markdown
Copy고객 문의 자동화의 우선순위를 높일 필요가 있다.
```

이 문장은 방향은 말하지만 행동은 말하지 않습니다. 누가 무엇을 언제까지 해야 하는지 알 수 없습니다. 다음처럼 바꾸면 실행 항목이 됩니다.

```markdown
Copy- 담당자: 운영팀 민지
- 할 일: 최근 4주간 고객 문의 중 반복 문의 30개를 유형별로 분류한다.
- 기한: 2026-05-24
- 근거: `wiki/customer-inquiry-patterns.md`, `raw/meeting-notes/2026-05-10.md`
- 완료 기준: 유형별 문의 수와 자동화 후보 3개를 표로 정리한다.
```

핵심은 “해야 한다”를 “누가 무엇을 어떤 기준으로 끝낼 것인가”로 바꾸는 것입니다.

**학습자료: 보고서에서 할 일을 뽑는 흐름**

이 흐름에서 가장 중요한 단계는 `근거 문서 연결`입니다. 근거가 없는 문장에서 뽑은 할 일은 실행 항목이 아니라 추측입니다. 추측도 업무에는 필요할 수 있지만, 그때는 “확인 필요”로 표시해야 합니다.

### 실습: 보고서 초안에서 실행 항목 만들기

**목표**

보고서 초안에서 실제로 움직일 수 있는 할 일 목록을 만듭니다.

**실행 전제**

다음과 같은 위키 구조를 사용한다고 가정합니다.

```text
Copyraw/
  meeting-notes/
    2026-05-10-customer-support.md
wiki/
  customer-inquiry-patterns.md
  automation-priority.md
output/
  customer-support-automation-report.md
```

**성공 기준**

보고서의 주장마다 실행 항목, 담당자, 기한, 완료 기준, 근거가 연결됩니다.

먼저 보고서 초안이 다음과 같다고 가정합니다.

```markdown
Copy# 고객 문의 자동화 검토 보고서

## 핵심 요약

최근 4주간 고객 문의 중 배송 상태 확인, 환불 절차 문의, 세금계산서 재발행 요청이 반복적으로 등장했다. 이 세 유형은 답변 기준이 비교적 고정되어 있어 자동화 후보로 볼 수 있다.

## 제안

1. 배송 상태 확인 문의부터 자동화 실험을 시작한다.
2. 환불 절차 문의는 정책 변경 가능성이 있으므로 최신 운영 기준을 먼저 확인한다.
3. 세금계산서 재발행 요청은 회계팀 검토가 필요하다.

## 근거

- `wiki/customer-inquiry-patterns.md`
- `wiki/automation-priority.md`
- `raw/meeting-notes/2026-05-10-customer-support.md`
```

이 보고서를 LLM에게 그대로 “할 일 뽑아 줘”라고 맡기면 결과가 넓어질 수 있습니다. 다음처럼 출력 형식을 고정합니다.

```text
Copy다음 보고서 초안에서 실행 항목을 뽑아 주세요.

조건:
- 보고서에 근거가 있는 항목만 실행 항목으로 만드세요.
- 근거가 부족한 항목은 "확인 필요"로 분리하세요.
- 각 항목에는 담당자, 기한, 완료 기준, 근거 문서를 포함하세요.
- 담당자나 기한이 보고서에 없으면 임의로 단정하지 말고 "미정"으로 표시하세요.

출력 형식:
| 상태 | 실행 항목 | 담당자 | 기한 | 완료 기준 | 근거 |
```

예상 결과는 다음과 같습니다.

| 상태 | 실행 항목 | 담당자 | 기한 | 완료 기준 | 근거 |
| --- | --- | --- | --- | --- | --- |
| 실행 후보 | 배송 상태 확인 문의 자동화 실험 범위를 정한다 | 미정 | 미정 | 실험 대상 문의 유형, 제외 범위, 성공 지표가 정리된다 | `wiki/customer-inquiry-patterns.md`, `wiki/automation-priority.md` |
| 확인 필요 | 환불 절차 문의에 적용할 최신 운영 기준을 확인한다 | 미정 | 미정 | 최신 환불 기준 문서 또는 담당 부서 확인 결과가 남는다 | `raw/meeting-notes/2026-05-10-customer-support.md` |
| 검토 요청 | 세금계산서 재발행 요청 자동화 가능성을 회계팀에 검토 요청한다 | 미정 | 미정 | 회계팀의 가능/불가 판단과 조건이 기록된다 | `wiki/customer-inquiry-patterns.md` |

이 표는 바로 업무 관리 도구에 옮길 수 있는 형태입니다. 아직 담당자와 기한이 비어 있다면 회의에서 정해야 할 항목입니다. 이처럼 보고서에서 할 일을 뽑으면 다음 회의의 안건도 자연스럽게 생깁니다.

### 선택 실습: 할 일 표를 자동 점검하기

작은 실습에서는 LLM이 만든 표를 사람이 읽고 점검해도 충분합니다. 다만 반복해서 실행 항목을 만든다면 빠진 칸을 자동으로 확인하는 작은 스크립트가 도움이 됩니다.

**실행 전제**

Python 3.9 이상이 설치되어 있어야 합니다. 외부 패키지는 사용하지 않습니다.

아래 예제는 Markdown 표에서 빈 칸이나 `미정` 값을 찾아냅니다.

```python
Copy# check_actions.py
from pathlib import Path

table = Path("actions.md").read_text(encoding="utf-8").splitlines()

required_columns = ["상태", "실행 항목", "담당자", "기한", "완료 기준", "근거"]

rows = []
for line in table:
    if not line.startswith("|"):
        continue
    cells = [cell.strip() for cell in line.strip("|").split("|")]
    if cells == required_columns:
        header = cells
        continue
    if set(cells) == {"---"}:
        continue
    if len(cells) == len(required_columns):
        rows.append(dict(zip(required_columns, cells)))

problems = []
for index, row in enumerate(rows, start=1):
    for column in required_columns:
        value = row[column]
        if not value or value == "미정":
            problems.append(f"{index}번 행: '{column}' 값 확인 필요")

if problems:
    print("점검 결과")
    for problem in problems:
        print(f"- {problem}")
else:
    print("모든 실행 항목에 필수 값이 있습니다.")
```

함께 사용할 `actions.md`는 다음처럼 둡니다.

```markdown
Copy| 상태 | 실행 항목 | 담당자 | 기한 | 완료 기준 | 근거 |
|---|---|---|---|---|---|
| 실행 후보 | 배송 상태 확인 문의 자동화 실험 범위를 정한다 | 미정 | 미정 | 실험 대상 문의 유형, 제외 범위, 성공 지표가 정리된다 | `wiki/customer-inquiry-patterns.md` |
| 확인 필요 | 환불 절차 문의에 적용할 최신 운영 기준을 확인한다 | 운영팀 | 2026-05-24 | 최신 환불 기준 문서가 남는다 | `raw/meeting-notes/2026-05-10-customer-support.md` |
```

실행 명령은 다음과 같습니다.

```bash
Copypython3 check_actions.py
```

예상 결과는 다음과 같습니다.

```text
Copy점검 결과
- 1번 행: '담당자' 값 확인 필요
- 1번 행: '기한' 값 확인 필요
```

이 스크립트는 업무를 대신 판단하지 않습니다. 대신 실행 항목으로 쓰기에 부족한 칸을 빨리 찾아 줍니다. LLM이 만든 결과를 그대로 믿기보다, 빠진 조건을 확인하는 작은 검증 도구로 쓰면 됩니다.

## 회의 준비 자료 만들기

보고서에서 뽑은 할 일은 곧 회의 안건이 됩니다. 하지만 회의 준비 자료는 할 일 목록과 다릅니다. 회의에서는 “무엇을 할까?”보다 “무엇을 결정해야 할까?”가 더 중요합니다.

좋은 회의 준비 자료는 참석자가 회의 전에 같은 맥락을 읽고 들어오게 만듭니다. 특히 LLM위키를 사용하면 회의 자료에 근거 문서, 결정 후보, 확인 필요 항목을 함께 담을 수 있습니다.

### 회의 자료는 결정 중심으로 구성하기

회의 준비 자료에는 다음 네 가지가 들어가면 좋습니다.

| 구성 요소 | 역할 | 예시 |
| --- | --- | --- |
| 회의 목적 | 왜 모이는지 정한다 | 고객 문의 자동화 실험 범위 결정 |
| 사전 맥락 | 참석자가 읽어야 할 배경을 정리한다 | 반복 문의 유형 3개, 자동화 후보 기준 |
| 결정할 것 | 회의가 끝날 때 확정되어야 할 항목이다 | 첫 실험 대상, 담당자, 성공 지표 |
| 확인 필요 | 지금 단정할 수 없는 내용을 분리한다 | 환불 정책 최신 기준, 회계팀 검토 조건 |

이 표를 보면 회의 준비 자료가 단순한 요약문이 아니라는 점이 드러납니다. 요약문은 “무슨 일이 있었는가”를 설명합니다. 회의 준비 자료는 “무엇을 결정해야 하는가”를 좁힙니다.

**학습자료: 보고서에서 회의 준비 자료로 이어지는 구조**

flowchart LR
A\[보고서\] --> B\[실행 후보\]
A --> C\[확인 필요\]
A --> D\[근거 문서\]

B --> E\[회의 안건\]
C --> E
D --> F\[사전 읽기 자료\]
F --> E

E --> G\[결정 사항\]
G --> H\[실행 계획\]
G --> I\[위키 갱신\]

이 도해에서 회의는 보고서와 실행 계획 사이에 놓입니다. 회의가 끝나면 결정 사항은 다시 실행 계획과 위키 갱신으로 나뉩니다. 회의 결과를 위키에 반영하지 않으면 다음 보고서에서 같은 맥락을 다시 설명해야 합니다.

### 실습: 회의 준비 페이지 만들기

**목표**

보고서와 위키 문서를 바탕으로 회의 준비 페이지를 만듭니다.

**실행 전제**

앞의 실습에서 만든 실행 항목 표가 있다고 가정합니다.

**성공 기준**

회의 목적, 사전 읽기 자료, 결정할 것, 확인 필요 항목, 예상 질문이 한 문서에 정리됩니다.

LLM에게는 다음처럼 요청합니다.

```text
Copy다음 실행 항목 표를 바탕으로 30분 회의 준비 자료를 만들어 주세요.

조건:
- 회의 목적을 한 문장으로 쓰세요.
- 참석자가 회의 전에 읽어야 할 위키 문서와 원천 자료를 분리하세요.
- 회의에서 결정할 항목을 3개 이하로 줄이세요.
- 근거가 약한 내용은 "확인 필요"로 표시하세요.
- 회의 뒤 위키에 반영해야 할 항목을 마지막에 적으세요.

출력 형식:
# 회의 준비 자료
## 회의 목적
## 참석자
## 사전 읽기 자료
## 결정할 것
## 확인 필요
## 예상 질문
## 회의 후 위키 반영
```

예상 결과는 다음과 같습니다.

```markdown
Copy# 회의 준비 자료: 고객 문의 자동화 실험 범위 결정

## 회의 목적

배송 상태 확인 문의를 첫 자동화 실험 대상으로 삼을지 결정하고, 담당자와 성공 기준을 정한다.

## 참석자

- 운영팀
- 고객지원팀
- 제품 담당자
- 회계팀은 세금계산서 재발행 항목 검토가 필요할 때 참석 또는 서면 의견 제공

## 사전 읽기 자료

### 위키 문서

- `wiki/customer-inquiry-patterns.md`
- `wiki/automation-priority.md`

### 원천 자료

- `raw/meeting-notes/2026-05-10-customer-support.md`

## 결정할 것

1. 첫 자동화 실험 대상을 배송 상태 확인 문의로 확정할 것인가?
2. 실험의 완료 기준을 무엇으로 둘 것인가?
3. 실험 담당자와 검토 일정을 어떻게 정할 것인가?

## 확인 필요

- 환불 절차 문의는 최신 운영 기준 확인 전까지 자동화 대상에서 제외한다.
- 세금계산서 재발행 요청은 회계팀 검토 결과가 필요하다.

## 예상 질문

| 질문 | 준비 답변 | 근거 |
|---|---|---|
| 왜 배송 상태 확인부터 시작하는가? | 문의 유형이 반복적이고 답변 기준이 비교적 고정되어 있기 때문이다. | `wiki/customer-inquiry-patterns.md` |
| 환불 절차 문의는 왜 제외하는가? | 정책 변경 가능성이 있어 최신 기준 확인이 먼저 필요하다. | `raw/meeting-notes/2026-05-10-customer-support.md` |
| 성공 기준은 어떻게 잡을 수 있는가? | 반복 문의 처리 시간, 자동 응답 적용률, 상담원 수정 요청 수를 후보로 둘 수 있다. | 확인 필요 |

## 회의 후 위키 반영

- 결정된 실험 대상을 `wiki/automation-priority.md`에 반영한다.
- 담당자와 기한은 `output/customer-support-automation-action-plan.md`에 반영한다.
- 새로 확인한 환불 기준은 원천 자료로 보관한 뒤 위키 문서에 요약한다.
```

이 회의 준비 자료는 참석자에게 “읽어야 할 것”과 “결정해야 할 것”을 분리해서 보여 줍니다. 특히 예상 질문 표는 회의 시간을 줄이는 데 도움이 됩니다. 회의 중에 나올 질문을 미리 위키 근거와 연결했기 때문입니다.

### 회의 전 점검 질문 만들기

회의 준비 자료를 만들었다면 마지막으로 점검 질문을 던집니다. 이 질문은 LLM에게도, 작성자 자신에게도 사용할 수 있습니다.

```text
Copy위 회의 준비 자료를 검토해 주세요.

다음 기준으로 부족한 점만 지적해 주세요.
- 회의에서 결정할 항목이 너무 많지 않은가?
- 사전 읽기 자료가 실제 결정과 연결되는가?
- 근거 없는 주장이 결정 항목에 섞여 있지 않은가?
- 확인 필요 항목이 실행 항목처럼 쓰이지 않았는가?
- 회의 후 위키에 반영할 항목이 구체적인가?
```

예상되는 검토 결과는 다음과 같습니다.

| 점검 항목 | 발견 가능한 문제 | 보완 방법 |
| --- | --- | --- |
| 결정 항목 수 | 결정할 것이 5개 이상이면 회의가 흐려진다 | 이번 회의 결정과 다음 회의 결정으로 나눈다 |
| 사전 자료 | 위키 문서만 있고 원천 자료가 없다 | 중요한 판단에는 `raw/` 경로를 함께 둔다 |
| 근거 | “성공 가능성이 높다” 같은 문장이 근거 없이 쓰인다 | 근거 문서를 연결하거나 확인 필요로 낮춘다 |
| 회의 후 반영 | “위키 업데이트”처럼 넓게 쓰인다 | 어느 문서의 어느 항목을 바꿀지 적는다 |

회의 준비의 목적은 회의를 멋지게 포장하는 것이 아닙니다. 결정할 수 있는 상태로 만드는 것입니다. LLM위키는 그 결정이 어디에서 왔는지 보여 주는 배경 자료 역할을 합니다.

## 산출물과 위키의 연결 유지하기

보고서, 실행 계획, 회의 준비 자료는 `output/`에 둘 수 있습니다. 그러나 `output/`만 관리하면 지식이 다시 흩어집니다. 산출물은 특정 시점의 결과물이고, 위키는 계속 갱신되는 지식층입니다. 둘의 연결을 유지해야 다음 작업에서 같은 맥락을 다시 설명하지 않습니다.

이때 지켜야 할 원칙은 단순합니다.

- 원천 자료는 `raw/`에 보관합니다.
- 정리된 지식은 `wiki/`에 둡니다.
- 공유하거나 실행할 산출물은 `output/`에 둡니다.
- 산출물에는 근거 문서와 생성 날짜를 남깁니다.
- 산출물에서 나온 결정은 다시 위키에 반영합니다.

### 산출물은 근거로 돌아갈 수 있어야 합니다

산출물에는 최소한 다음 정보가 있어야 합니다.

| 항목 | 이유 | 예시 |
| --- | --- | --- |
| 생성 날짜 | 산출물의 기준 시점을 알기 위해 | 2026-05-16 |
| 작성 목적 | 왜 만든 문서인지 알기 위해 | 자동화 실험 범위 결정 회의 준비 |
| 근거 위키 | 어떤 정리 문서를 바탕으로 했는지 확인하기 위해 | `wiki/automation-priority.md` |
| 원천 자료 | 위키 요약을 검증하기 위해 | `raw/meeting-notes/2026-05-10-customer-support.md` |
| 후속 반영 | 회의나 실행 결과를 어디에 되돌릴지 정하기 위해 | `wiki/customer-inquiry-patterns.md` 갱신 |

이 표는 문서의 앞부분에 넣어도 되고, 마지막의 “근거와 후속 반영” 섹션에 넣어도 됩니다. 중요한 것은 산출물이 혼자 떠 있지 않게 만드는 것입니다.

**학습자료: 산출물과 위키를 연결하는 순환 구조**

flowchart TD
A\[raw 원천 자료\] --> B\[wiki 정리 문서\]
B --> C\[output 보고서\]
C --> D\[실행 항목\]
D --> E\[회의와 결정\]
E --> F\[실행 결과\]
F --> G\[wiki 갱신\]
G --> B

C --> H\[근거 링크\]
H --> B
H --> A

E --> I\[결정 기록\]
I --> G

이 순환 구조에서 `output/`은 끝점이 아닙니다. 업무를 밖으로 내보내는 지점입니다. 밖으로 나간 결과가 회의, 실행, 결정으로 돌아오면 다시 `wiki/`를 갱신해야 합니다.

### 실습: 산출물에 연결 정보 남기기

**목표**

보고서나 회의 자료에 근거와 후속 반영 위치를 남깁니다.

**실행 전제**

`output/`에 보고서나 회의 준비 자료를 만든 상태라고 가정합니다.

**성공 기준**

산출물만 읽어도 어떤 위키 문서와 원천 자료를 확인해야 하는지 알 수 있습니다.

다음 템플릿을 산출물 앞이나 뒤에 붙입니다.

```markdown
Copy## 문서 정보

- 문서 목적: 고객 문의 자동화 실험 범위 결정
- 생성 날짜: 2026-05-16
- 작성 기준: 2026-05-10 회의록과 고객 문의 패턴 위키
- 상태: 회의 전 검토용

## 근거

### 위키 문서

- `wiki/customer-inquiry-patterns.md`
- `wiki/automation-priority.md`

### 원천 자료

- `raw/meeting-notes/2026-05-10-customer-support.md`

## 확인 필요

- 환불 절차 문의의 최신 운영 기준
- 세금계산서 재발행 요청의 회계팀 검토 조건

## 후속 반영 위치

- 회의에서 첫 실험 대상이 확정되면 `wiki/automation-priority.md`를 갱신한다.
- 새 문의 유형이 발견되면 `wiki/customer-inquiry-patterns.md`에 추가한다.
- 결정 사항과 담당자는 `output/customer-support-automation-action-plan.md`에 반영한다.
```

이 템플릿은 문서를 조금 길게 만들지만, 나중에 큰 시간을 줄입니다. 특히 “후속 반영 위치”가 중요합니다. 회의가 끝난 뒤 무엇을 어디에 업데이트해야 하는지 미리 정해 두기 때문입니다.

### 운영 규칙으로 연결을 습관화하기

LLM 도구를 함께 쓴다면 `AGENTS.md`나 `CLAUDE.md` 같은 작업 기준 파일에 산출물 규칙을 적어 둘 수 있습니다. 다만 이런 파일은 LLM의 행동을 강제하지 않습니다. 따르도록 유도하는 문맥에 가깝습니다. 따라서 결과를 반드시 사람이 확인해야 합니다.

Codex를 쓴다면 프로젝트의 `AGENTS.md`에 다음과 같은 규칙을 둘 수 있습니다.

```markdown
Copy# LLM위키 산출물 규칙

- `raw/`의 원천 자료는 임의로 수정하지 않는다.
- `wiki/` 문서는 원천 자료를 바탕으로 정리한 파생 지식으로 다룬다.
- `output/` 문서에는 생성 날짜, 목적, 근거 위키, 원천 자료를 남긴다.
- 보고서에서 실행 항목을 뽑을 때 담당자, 기한, 완료 기준, 근거를 표로 작성한다.
- 근거가 약한 항목은 실행 항목이 아니라 "확인 필요"로 분리한다.
- 회의 후 결정 사항은 관련 `wiki/` 문서에 다시 반영할 후보로 표시한다.
```

Claude Code를 쓴다면 `CLAUDE.md`에 같은 규칙을 둘 수 있습니다. 이미 `AGENTS.md`를 운영 중이라면 `CLAUDE.md`에서 가져오는 방식도 사용할 수 있습니다. 구체적인 지원 범위와 파일 로딩 방식은 도구의 공식 문서를 확인해야 합니다.

이 규칙의 목적은 자동화를 완성하는 것이 아닙니다. 산출물을 만들 때마다 같은 기준을 떠올리게 만드는 것입니다. 원본 보존, 근거 연결, 후속 반영 위치를 반복해서 확인하면 위키가 오래 쓸 수 있는 업무 시스템이 됩니다.

### 오래된 산출물은 그대로 믿지 않기

산출물은 작성 시점의 결론입니다. 시간이 지나면 정책, 일정, 담당자, 제품 상태가 바뀔 수 있습니다. 그래서 오래된 산출물은 위키 문서보다 더 조심해서 다뤄야 합니다.

다음과 같은 표시를 남기면 안전합니다.

```markdown
Copy## 최신성 상태

- 작성일: 2026-05-16
- 마지막 검토일: 2026-05-20
- 다음 검토 필요일: 2026-06-03
- 최신성 주의: 환불 정책과 회계 처리 기준은 변경 가능성이 있어 재확인 필요
```

도구에 아카이브나 린트 기능이 있다면 오래된 산출물과 연결되지 않은 문서를 점검하는 데 활용할 수 있습니다. 다만 구현체마다 명령과 동작이 다릅니다. 책에서 특정 명령을 그대로 실행하기보다, 사용하는 도구의 README와 릴리스 노트를 확인한 뒤 적용해야 합니다.

## 7.3의 검증 포인트

이 절의 목표는 산출물을 “읽고 끝나는 문서”에서 “다음 행동을 만드는 문서”로 바꾸는 것입니다. 다음 질문으로 결과를 점검합니다.

| 점검 질문 | 통과 기준 |
| --- | --- |
| 보고서에서 실행 항목을 뽑았는가? | 담당자, 기한, 완료 기준, 근거가 표로 정리되어 있다 |
| 근거가 약한 항목을 분리했는가? | 실행 항목과 확인 필요 항목이 섞이지 않는다 |
| 회의 준비 자료가 결정 중심인가? | 회의에서 결정할 항목이 3개 이하로 좁혀져 있다 |
| 사전 읽기 자료가 연결되어 있는가? | 위키 문서와 원천 자료 경로가 함께 적혀 있다 |
| 산출물이 위키로 돌아가는가? | 회의 후 갱신할 위키 문서가 지정되어 있다 |
| 오래된 산출물을 구분할 수 있는가? | 작성일, 검토일, 최신성 주의가 남아 있다 |

마지막으로 한 문장으로 정리해 봅니다.

```text
Copy이 산출물을 읽은 사람이 오늘 무엇을 해야 하는지 알 수 있는가?
```

이 질문에 답할 수 없다면 산출물은 아직 업무로 연결되지 않은 상태입니다. 실행 항목, 회의 결정, 후속 반영 위치를 보완해야 합니다.
