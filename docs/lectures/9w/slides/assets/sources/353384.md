# 2.3 좋은 위키 문서의 조건

![2.3 좋은 위키 문서의 조건 삽화](https://static.wikidocs.net/images/page/353384/2.3-%EC%A2%8B%EC%9D%80-%EC%9C%84%ED%82%A4-%EB%AC%B8%EC%84%9C%EC%9D%98-%EC%A1%B0%EA%B1%B4.jpg)

LLM위키는 문서를 많이 모은다고 좋아지지 않습니다. 나중에 근거를 확인할 수 있고, 질문에 다시 쓸 수 있고, 관련 문서로 이어질 때 비로소 업무 지식이 됩니다.

이 절에서는 좋은 위키 문서의 조건을 세 가지로 정리합니다. 출처가 남아야 합니다. 질문에 다시 쓰기 쉬워야 합니다. 링크로 다른 문서와 이어져야 합니다. 이 세 조건을 갖추면 LLM이 만든 요약을 그대로 믿는 위험을 줄이고, 실제 업무 산출물로 이어가기 쉬워집니다.

먼저 나쁜 문서와 좋은 문서의 차이를 보겠습니다.

| 구분 | 나중에 곤란한 문서 | 다시 쓰기 좋은 문서 |
| --- | --- | --- |
| 출처 | “회의록 자동화가 필요하다.” | `raw/meetings/2026-05-15-weekly.md`를 근거로 남긴다. |
| 주장 | “시간을 많이 줄일 수 있다.” | “시간 절감률은 아직 측정 전이므로 확인 필요”라고 표시한다. |
| 구조 | 메모가 문장 몇 줄로 끝난다. | 요약, 근거, 확인된 내용, 확인 필요, 다음 질문을 나눈다. |
| 연결 | 다른 문서와 이어지지 않는다. | 반복 업무 후보, 개인정보 기준, 실험 계획으로 링크한다. |

이 표의 핵심은 간단합니다. 좋은 위키 문서는 더 길게 쓰는 문서가 아닙니다. 나중에 다시 확인하고, 다시 질문하고, 다시 연결할 수 있게 만든 문서입니다.

## 출처가 남는 문서

출처가 남는 문서는 “그럴듯한 문서”가 아니라 “확인할 수 있는 문서”입니다. LLM위키에서 위키 문서는 원천 자료를 대신하지 않습니다. 원천 자료를 읽고 정리한 파생 문서입니다.

원본 회의록을 요약문으로 덮어쓰면 나중에 결정의 근거를 찾기 어렵습니다. 웹 문서를 정리하면서 URL과 확인 날짜를 빼면 최신성이 필요한 주장을 점검하기 어렵습니다. LLM이 만든 문장과 사람이 남긴 기록이 섞이면 어느 쪽이 근거인지도 흐려집니다.

그래서 좋은 위키 문서는 출처를 문서의 장식이 아니라 검증 장치로 다룹니다.

**학습자료: 출처가 남는 문서의 흐름**

raw/회의록.md

원천 자료

wiki/회의록-자동화.md

정리된 문서

출처 정보

경로, URL, 확인 날짜

질문

자동화 후보는?

산출물

실험 계획

검증

근거 있음 / 확인 필요

이 흐름에서 `raw`는 근거를 보존하는 층입니다. `wiki`는 그 근거를 업무 질문에 쓰기 좋게 정리한 층입니다. 질문과 산출물은 `wiki`를 사용할 수 있지만, 중요한 판단은 다시 `raw`나 출처 정보로 돌아가 확인해야 합니다.

### 최소 출처 블록

모든 문서에 긴 서지가 필요한 것은 아닙니다. 하지만 다음 항목은 되도록 남기는 편이 좋습니다.

| 항목 | 쓰는 이유 | 예시 |
| --- | --- | --- |
| 원천 자료 | 근거 위치를 찾기 위해 | `raw/meetings/2026-05-15-weekly.md` |
| 확인 날짜 | 최신성 판단을 위해 | `2026-05-16` |
| 자료 성격 | 신뢰 범위를 구분하기 위해 | 내부 회의록, 공식 문서, 개인 메모 |
| 확인 필요 | 단정하면 위험한 내용을 분리하기 위해 | 시간 절감률은 측정 전 |
| 관련 문서 | 이어서 읽을 문서를 찾기 위해 | `repetitive-work-candidates.md` |

다음은 짧은 위키 문서에 붙일 수 있는 출처 블록 예시입니다.

```markdown
Copy# 회의록 자동화 후보

## 한 문장 요약

주간 회의록에서는 실행 항목 추출, 담당자 확인, 마감일 정리가 반복 업무로 나타난다.

## 근거

- 원천 자료: `raw/meetings/2026-05-15-weekly.md`
- 확인 날짜: 2026-05-16
- 자료 성격: 내부 회의록 메모
- 관련 문서: [반복 업무 후보](repetitive-work-candidates.md)

## 확인된 내용

- 매주 회의 뒤 실행 항목을 다시 정리한다.
- 담당자와 마감일이 회의 중에 정해지지만 후속 문서에 다시 옮겨야 한다.
- 회의록 표현이 일정하지 않아 사람이 최종 확인해야 한다.

## 확인 필요

- 자동 추출 결과가 실제 담당자 배정과 얼마나 일치하는지 아직 측정하지 않았다.
- 개인정보나 민감한 고객명이 포함된 회의록 처리 기준은 별도로 정해야 한다.
```

이 예시는 짧지만 안전합니다. 문서만 보고도 내용의 출발점과 한계를 알 수 있습니다. 나중에 LLM에게 이 문서를 읽히면 “확인된 내용”과 “확인 필요”를 구분해 답변하도록 요청할 수 있습니다.

## 질문에 다시 쓰기 쉬운 문서

위키 문서는 한 번 읽고 끝나는 글이 아닙니다. 나중에 질문할 때 다시 쓰는 재료입니다. 그래서 좋은 위키 문서는 읽기 좋은 설명뿐 아니라 질문에 넣기 좋은 구조를 갖춥니다.

“자동화 후보를 골라 줘”라고만 물으면 답이 넓어집니다. 반대로 위키 문서에 적용 조건, 판단 기준, 한계가 정리되어 있으면 질문이 좁아집니다. LLM은 그 문서를 기준으로 비교표, 실험 계획, 보고서 초안을 만들 수 있습니다.

**학습자료: 질문 재료로 쓰기 좋은 문서 구조**

| 문서 항목 | 작성 예시 | 나중에 가능한 질문 |
| --- | --- | --- |
| 한 문장 요약 | 회의록 자동화는 실행 항목, 담당자, 마감일을 구조화하는 작업이다. | 핵심 입력과 출력은 무엇인가? |
| 적용 조건 | 회의록에 결정 사항과 담당자가 어느 정도 명시되어 있어야 한다. | 우리 회의록은 자동화에 적합한가? |
| 판단 기준 | 반복 빈도, 검토 시간, 오류 위험, 민감 정보 포함 여부를 본다. | 자동화 우선순위를 정해 줘. |
| 한계 | 사람의 최종 확인 없이 외부 공유 문서를 만들면 위험하다. | 자동화하면 안 되는 경우는 무엇인가? |
| 다음 질문 | 샘플 회의록 5개에서 추출 결과를 비교한다. | 2주 실험 계획을 만들어 줘. |

이 표는 문서를 “읽을거리”에서 “질문 재료”로 바꾸는 기준입니다. 좋은 문서는 답을 다 끝내지 않습니다. 다음 질문을 더 정확하게 만들 수 있게 도와줍니다.

### 메모를 위키 문서로 바꾸기

아래 메모는 흔히 나오는 초안입니다.

```markdown
Copy# 자동화 아이디어

회의록 정리는 매번 귀찮다.
담당자랑 마감일을 뽑아 주면 좋겠다.
보고서에도 쓸 수 있을 것 같다.
```

이 메모는 출발점으로는 괜찮습니다. 하지만 바로 위키 문서로 쓰기에는 약합니다. 무엇을 근거로 하는지, 어떤 조건에서 가능한지, 어떤 질문으로 이어질지 알기 어렵습니다.

다음처럼 바꾸면 질문에 다시 쓰기 쉬워집니다.

```markdown
Copy# 회의록 실행 항목 자동화

## 한 문장 요약

회의록 실행 항목 자동화는 회의 내용에서 할 일, 담당자, 마감일을 뽑아 후속 작업 목록으로 바꾸는 흐름이다.

## 적용 조건

- 회의록에 결정 사항이 문장으로 남아 있다.
- 담당자나 팀 이름이 어느 정도 표시된다.
- 사람이 최종 검토할 시간이 있다.

## 판단 기준

| 기준 | 확인할 질문 |
|---|---|
| 반복 빈도 | 이 작업이 매주 반복되는가? |
| 검토 시간 | 사람이 정리하는 데 시간이 얼마나 걸리는가? |
| 오류 위험 | 잘못 추출했을 때 업무 피해가 큰가? |
| 민감 정보 | 고객명, 계약 조건, 장애 원인이 포함되는가? |

## 한계

- 회의록이 너무 구어체이면 추출 품질이 낮아질 수 있다.
- 담당자가 명확하지 않은 결정은 자동 배정하면 안 된다.
- 외부 공유 전에는 사람이 반드시 검토해야 한다.

## 다시 물어볼 질문

- 이 문서 기준으로 자동화 우선순위를 평가해 줘.
- 회의록 샘플 5개로 작은 실험 계획을 만들어 줘.
- 개인정보가 들어간 회의록을 처리할 때 제외해야 할 항목을 정리해 줘.
```

바뀐 문서는 보고서가 아닙니다. 대신 보고서와 실험 계획을 만들기 좋은 재료입니다. LLM에게 “이 문서를 기준으로 첫 2주 실험 계획을 작성해 줘”라고 요청할 수 있습니다.

### 제목도 질문을 돕는다

파일명과 제목도 재사용성에 영향을 줍니다. `summary.md`, `notes.md` 같은 이름은 나중에 찾기 어렵습니다. 제목만 보고도 어떤 질문에 쓸 수 있는지 드러나야 합니다.

| 약한 제목 | 다시 쓰기 쉬운 제목 | 이유 |
| --- | --- | --- |
| `summary.md` | `meeting-action-item-automation.md` | 회의록 실행 항목 자동화라는 주제가 드러난다. |
| `notes.md` | `customer-inquiry-labeling-risks.md` | 고객 문의 라벨링의 위험을 다루는 문서임을 알 수 있다. |
| `report-draft.md` | `weekly-report-automation-plan.md` | 주간 보고서 자동화 계획으로 다시 찾기 쉽다. |

제목을 잘 붙이면 사람도 빠르게 찾고, LLM에게 문서를 고르게 할 때도 맥락이 분명해집니다.

## 링크로 이어지는 문서

위키 문서는 혼자 완성되는 글이 아닙니다. 다른 문서와 이어질 때 가치가 커집니다. 링크가 없으면 위키는 파일 묶음에 가깝습니다. 링크가 있으면 사람과 LLM이 지식의 길을 따라갈 수 있습니다.

링크는 보통 세 가지 역할을 합니다. 관련 개념으로 이동하게 합니다. 원천 자료나 출처 메모로 돌아가게 합니다. 보고서, 계획서, 체크리스트 같은 산출물로 이어지게 합니다.

**학습자료: 링크로 이어지는 위키 구조**

회의록 실행 항목 자동화

반복 업무 후보

회의록 원천 자료

2주 실험 계획

개인정보 처리 기준

고객 문의 분류 자동화

주간 보고서 초안 자동화

실험 결과 기록

이 도해에서 `회의록 실행 항목 자동화`는 끝점이 아닙니다. 반복 업무 후보, 원천 자료, 실험 계획, 개인정보 기준으로 이어지는 허브입니다. 나중에 “업무 자동화 후보를 비교해 줘”라고 질문하면 관련 문서를 함께 읽히기 쉽습니다.

### 어떤 링크를 붙일 것인가

링크는 많을수록 좋은 것이 아닙니다. 관련 없는 링크가 많으면 탐색이 어려워집니다. 좋은 링크는 다음에 무엇을 확인해야 하는지 알려 줍니다.

| 링크할 대상 | 링크하는 이유 |
| --- | --- |
| 상위 개념 | 이 문서가 어느 큰 주제에 속하는지 알려 준다. |
| 비슷한 후보 | 비교 질문에 쓸 수 있다. |
| 원천 자료 | 근거를 확인할 수 있다. |
| 위험 기준 | 실행 전 검토할 제한 조건을 붙인다. |
| 산출물 | 보고서나 실험 계획으로 이어진다. |

예를 들어 다음 문서는 내용은 있지만 연결이 약합니다.

```markdown
Copy# 고객 문의 분류 자동화

고객 문의를 유형별로 나누면 담당자 배정 시간을 줄일 수 있다.

확인 필요:
- 개인정보가 포함된 문의를 어떻게 처리할지 정해야 한다.
- 라벨 기준이 팀마다 다를 수 있다.
```

이 문서가 반드시 잘못된 것은 아닙니다. 다만 다른 문서로 이어지지 않기 때문에 질문에 쓰일 때 맥락이 좁습니다.

다음처럼 보강하면 위키 문서로 쓰기 좋아집니다.

```markdown
Copy# 고객 문의 분류 자동화

## 한 문장 요약

고객 문의 분류 자동화는 문의 내용을 유형별 라벨로 나누고 담당자 배정을 돕는 흐름이다.

## 근거

- 원천 자료: `raw/support/sample-inquiries-2026-05.md`
```

## 세 조건을 함께 적용하기

출처, 재사용성, 링크는 따로 움직이지 않습니다. 출처만 있고 질문에 쓰기 어려우면 자료 목록에 머뭅니다. 질문에는 좋지만 출처가 없으면 위험합니다. 링크가 없으면 다른 문서와 합쳐지지 않습니다.

**학습자료: 좋은 위키 문서 점검표**

| 조건 | 점검 질문 | 보완 방법 |
| --- | --- | --- |
| 출처 | 이 문장의 근거를 다시 찾을 수 있는가? | 원천 자료, URL, 확인 날짜를 붙인다. |
| 재사용 | 이 문서를 바탕으로 어떤 질문을 할 수 있는가? | 적용 조건, 판단 기준, 다음 질문을 넣는다. |
| 링크 | 이 문서가 어디로 이어지는가? | 상위 개념, 관련 후보, 산출물 링크를 추가한다. |
| 한계 | 아직 모르는 내용을 표시했는가? | `확인 필요` 항목을 둔다. |
| 최신성 | 시간이 지나면 틀릴 수 있는 내용인가? | 확인 날짜와 재확인 기준을 적는다. |

이 점검표는 문서를 완벽하게 만드는 기준이 아닙니다. 최소한의 안전장치입니다. 특히 비용, 보안, 법률, 제품 기능, 최신 버전처럼 틀리면 위험한 내용은 근거 없이 단정하지 않아야 합니다.

### 실습: 나쁜 문서를 좋은 문서로 바꾸기

**목표**

출처, 재사용성, 링크가 없는 메모를 위키 문서로 바꿉니다.

**실행 전제**

Markdown 문서를 편집할 수 있으면 됩니다. 실제 업무 자료를 사용할 때는 고객 정보, 개인정보, 내부 정책을 그대로 넣지 않습니다.

**성공 기준**

바뀐 문서에 근거, 비교 기준, 확인 필요, 다시 물어볼 질문이 있어야 합니다.

먼저 위키에 그대로 두기 어려운 문서를 봅니다.

```markdown
Copy# 자동화 아이디어

회의록이랑 고객 문의는 자동화하면 좋다.
보고서도 자동으로 만들 수 있을 것 같다.
요즘 LLM 도구가 좋아서 가능하다.
```

이 문서는 짧지만 실무에서 재사용하기 어렵습니다. 출처가 없고, 질문에 다시 쓰기 어렵고, 링크도 없습니다. 무엇을 근거로 “좋다”고 했는지도 알 수 없습니다. “요즘 LLM 도구가 좋다”는 표현도 너무 넓습니다.

같은 내용을 좋은 위키 문서로 바꾸면 다음과 같습니다.

```markdown
Copy# 반복 업무 자동화 후보

## 한 문장 요약

현재 업무 메모 기준으로 회의록 실행 항목 정리, 고객 문의 분류, 주간 보고서 초안 작성이 반복 업무 자동화 후보로 보인다.

## 후보 비교

| 후보 | 기대 효과 | 주요 위험 | 다음 확인 |
|---|---|---|---|

## 확인 필요

- 각 후보의 실제 시간 절감률은 아직 측정하지 않았다.
- 고객 정보가 포함된 자료는 조직 보안 기준을 먼저 확인해야 한다.
- 도구별 기능과 명령어는 구현체마다 다르므로 별도 문서에서 확인해야 한다.

## 다시 물어볼 질문

- 후보 세 가지 중 첫 2주 실험에 가장 적합한 것은 무엇인가?
- 개인정보 위험을 제외하면 어떤 후보가 가장 작게 시작하기 좋은가?
- 이 표를 바탕으로 팀 공유용 1쪽 제안서를 만들어 줘.
```

바뀐 문서는 같은 아이디어를 담고 있지만 훨씬 안전합니다. 근거가 있고, 비교 기준이 있고, 후속 질문이 있습니다. 무엇보다 “아직 측정하지 않았다”는 한계를 분명히 남겼습니다.

LLM위키에서 이런 한계 표시는 중요합니다. 위키는 한 번 만들어 끝나는 문서가 아니라 계속 갱신되는 문서입니다. 불확실한 부분을 남겨 두면 나중에 자료를 추가할 때 어디를 보강해야 하는지 알 수 있습니다.

## 정리와 검증 포인트

좋은 위키 문서를 만들었는지 확인할 때는 다음 항목을 봅니다.

- 원천 자료, URL, 확인 날짜 중 하나 이상이 남아 있는가?
- LLM이 만든 요약과 원천 자료가 구분되어 있는가?
- 단정할 수 있는 내용과 `확인 필요` 항목이 나뉘어 있는가?
- 한 문장 요약, 적용 조건, 판단 기준이 있는가?
- 나중에 다시 물어볼 질문이 2개 이상 있는가?
- 관련 문서, 원천 자료, 산출물 중 하나 이상으로 링크되어 있는가?
- 링크가 문서의 목적과 관련이 있는가?
- 시간이 지나면 틀릴 수 있는 주장에 확인 날짜가 있는가?
- 개인정보, 보안, 비용, 제품 기능처럼 위험한 주장을 근거 없이 단정하지 않았는가?
- 이 문서를 바탕으로 보고서, 실험 계획, 비교표 중 하나를 만들 수 있는가?

세 가지 조건을 모두 만족하는 문서는 LLM에게 다시 읽히기 좋습니다. 사람이 검토하기도 쉽습니다. 그래서 LLM위키에서는 문서의 양보다 문서의 재사용성을 먼저 봐야 합니다.
