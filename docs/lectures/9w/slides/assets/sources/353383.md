# 2.2 좋은 폴더 구조 이해하기

![2.2 좋은 폴더 구조 이해하기 삽화](https://static.wikidocs.net/images/page/353383/2.2-%EC%A2%8B%EC%9D%80-%ED%8F%B4%EB%8D%94-%EA%B5%AC%EC%A1%B0-%EC%9D%B4%ED%95%B4%ED%95%98%EA%B8%B0.jpg)

LLM위키는 자료를 많이 모아 두기만 하는 창고가 아닙니다. 나중에 다시 찾고, 근거를 확인하고, 보고서나 실행 계획으로 바꾸기 위한 지식 작업 공간입니다.

폴더 구조가 흐트러지면 곧바로 문제가 생깁니다. 원본인지 요약인지 헷갈리고, 산출물의 근거를 다시 찾기 어렵고, LLM이 관련 없는 자료를 섞어 답할 가능성도 커집니다. 반대로 처음부터 위치를 나누어 두면 사람과 LLM이 같은 기준으로 자료를 찾을 수 있습니다.

이 절에서는 특정 구현체에만 묶이지 않는 최소 구조를 사용합니다. 이 책의 수동 실습에서는 다음 구조를 기준으로 설명합니다. 도구형 LLM위키를 쓸 때는 실제 저장 위치가 다를 수 있으므로 각 도구의 README와 상태 출력을 함께 확인해야 합니다.

```text
Copywork-automation/
├── index.md
├── log.md
├── raw/
├── wiki/
└── output/
```

`raw/`는 원본 자료를 보존합니다. `wiki/`는 원본을 읽고 정리한 지식을 둡니다. `index.md`는 전체 안내판입니다. `log.md`는 작업 이력입니다. `output/`은 보고서, 실행 계획, 공유용 요약처럼 업무에 바로 쓰는 산출물을 둡니다.

## 주제별 폴더를 나누는 이유

좋은 LLM위키는 모든 자료를 한곳에 넣지 않습니다. 주제별로 폴더를 나눕니다. 예를 들어 “반복 업무 자동화”, “고객 문의 분석”, “책 원고 집필”은 서로 다른 질문을 다루므로 별도 위키로 두는 편이 좋습니다.

가장 큰 이유는 질문의 범위를 좁히기 위해서입니다. 관련 없는 자료가 함께 있으면 LLM은 답변을 넓고 흐릿하게 만들 수 있습니다. 반대로 한 주제 안에 필요한 자료만 모여 있으면 질문이 선명해지고, 답변의 근거도 확인하기 쉬워집니다.

또 하나의 이유는 운영 주기입니다. 어떤 주제는 매주 갱신됩니다. 어떤 주제는 보고서 하나를 만들고 끝납니다. 갱신 주기가 다른 자료를 한곳에 섞으면 오래된 판단과 최신 판단이 충돌하기 쉽습니다.

**학습자료: 주제 분리 기준표**

| 주제 후보 | 같은 폴더에 둘 수 있는가 | 판단 이유 |
| --- | --- | --- |
| 회의록에서 실행 항목 뽑기 | 가능 | 반복 업무 자동화라는 같은 목적을 가집니다. |
| 주간 보고서 초안 만들기 | 가능 | 같은 팀의 반복 문서 작성 흐름에 속합니다. |
| 고객 문의 개인정보 처리 기준 | 분리 권장 | 보안·법무 검토가 필요해 접근 범위가 다를 수 있습니다. |
| 새 프런트엔드 프레임워크 조사 | 분리 권장 | 업무 자동화보다 기술 선정 리서치에 가깝습니다. |
| 책 원고 집필 자료 | 분리 권장 | 산출물과 독자가 다릅니다. |

이 표의 기준은 파일 형식이 아닙니다. “같은 질문에 함께 쓰일 자료인가?”가 기준입니다. PDF, 회의록, 웹 문서처럼 형식이 달라도 같은 업무 질문에 답한다면 한 폴더에 둘 수 있습니다.

### 좋은 주제 폴더의 조건

좋은 주제 폴더는 질문 하나로 설명할 수 있습니다.

예를 들어 `work-automation/`은 “반복 업무를 LLM으로 줄이려면 무엇부터 해야 할까?”라는 질문을 다룹니다. 이 질문에 답하는 자료라면 같은 폴더에 둡니다. 답하지 않는 자료라면 다른 주제로 분리합니다.

| 기준 | 좋은 예 | 피해야 할 예 |
| --- | --- | --- |
| 폴더 이름 | `work-automation` | `everything` |
| 중심 질문 | 반복 업무 자동화 후보를 고릅니다. | 회사 업무 자료를 전부 모읍니다. |
| 처음 자료 수 | 3~10개 자료로 시작합니다. | 시작부터 수백 개 파일을 넣습니다. |
| 산출물 | 실행 후보 목록, 보고서 초안 | 목적 없는 메모 묶음 |

첫 위키는 작은 범위에서 시작하는 편이 좋습니다. 작은 위키는 구조를 이해하기 쉽고, 잘못 정리했을 때 되돌리기도 쉽습니다.

**학습자료: 주제를 나누지 않았을 때의 문제**

모든 자료를 하나의 폴더에 저장

업무 자동화 자료와 기술 조사 자료가 섞임

LLM이 관련 없는 근거를 함께 사용

답변은 그럴듯하지만 출처 확인이 어려움

보고서 수정 때 원문을 다시 찾아야 함

가장 위험한 지점은 C입니다. LLM은 관련 없어 보이는 자료도 자연스럽게 이어 붙여 설명할 수 있습니다. 그래서 폴더 구조는 단순한 정리가 아니라 답변 품질을 지키는 장치입니다.

### 실습: 작은 주제 폴더 만들기

**목표**

업무 자동화라는 작은 주제 위키를 만들고, 기본 폴더와 안내 파일을 확인합니다.

**실행 전제**

macOS, Linux, WSL, Git Bash처럼 `mkdir`, `printf`, `find` 명령을 사용할 수 있는 터미널이 필요합니다. 같은 경로에 파일이 이미 있으면 예제 파일 내용이 덮어써질 수 있습니다. 학습용 폴더에서만 실행합니다.

**성공 기준**

`index.md`, `log.md`, `raw/`, `wiki/`, `output/`이 같은 주제 폴더 안에 만들어지면 성공입니다.

```bash
CopyBASE="$HOME/llm-wiki-demo/work-automation"

mkdir -p "$BASE/raw" "$BASE/wiki" "$BASE/output"

printf '%s\n' \
'# 업무 자동화 위키' \
'' \
'## 이 위키의 질문' \
'' \
'반복 업무를 LLM으로 줄이려면 무엇부터 해야 할까?' \
'' \
'## 주요 위치' \
'' \
'- raw/ : 원본 자료' \
'- wiki/ : 정리한 지식' \
'- output/ : 보고서와 실행 계획' \
> "$BASE/index.md"

printf '%s\n' \
'# 처리 이력' \
'' \
'| 날짜 | 작업 | 결과 |' \
'|---|---|---|' \
'| 2026-05-16 | 위키 초기 구조 생성 | raw, wiki, output 폴더 생성 |' \
> "$BASE/log.md"

find "$BASE" -maxdepth 2 -print | sort
```

예상 결과는 다음과 비슷합니다.

```text
Copy/Users/사용자명/llm-wiki-demo/work-automation
/Users/사용자명/llm-wiki-demo/work-automation/index.md
/Users/사용자명/llm-wiki-demo/work-automation/log.md
/Users/사용자명/llm-wiki-demo/work-automation/output
/Users/사용자명/llm-wiki-demo/work-automation/raw
/Users/사용자명/llm-wiki-demo/work-automation/wiki
```

사용자명과 홈 디렉터리 경로는 환경마다 다릅니다. 중요한 것은 같은 주제 폴더 안에 기본 구성 요소가 모여 있는지입니다. 이 실습을 끝내면 “어디에 무엇을 넣을지”를 매번 새로 고민하지 않아도 됩니다.

## `index`, `log`, `output`의 역할

LLM위키에는 자료 폴더만 있으면 부족합니다. 사람이 다시 읽을 수 있는 안내판과 작업 이력이 필요합니다. 이때 `index.md`, `log.md`, `output/`이 핵심 역할을 합니다.

`index.md`는 위키의 첫 화면입니다. 이 위키가 어떤 질문을 다루는지, 어떤 문서를 먼저 읽어야 하는지 알려줍니다. 사람에게는 목차이고, LLM에게는 탐색 출발점입니다.

`log.md`는 처리 이력을 남깁니다. 언제 어떤 자료를 넣었는지, 어떤 문서를 새로 만들었는지, 어떤 주장을 확인하지 못했는지 기록합니다. 로그가 있으면 나중에 답변이 이상할 때 원인을 추적할 수 있습니다.

`output/`은 외부로 나갈 산출물을 둡니다. 보고서, 회의 준비 자료, 실행 계획, 요약문처럼 업무에 바로 쓰는 문서가 여기에 들어갑니다. `wiki/`가 지식을 쌓는 공간이라면, `output/`은 그 지식을 꺼내 쓰는 공간입니다.

**학습자료: 기본 파일과 폴더의 역할**

| 이름 | 위치 | 역할 | 넣으면 좋은 내용 | 넣지 말아야 할 내용 |
| --- | --- | --- | --- | --- |
| `index.md` | 주제 폴더 바로 아래 | 전체 안내판 | 위키의 질문, 주요 문서 링크, 읽는 순서 | 긴 원문 전체 |
| `log.md` | 주제 폴더 바로 아래 | 처리 이력 | 자료 추가, 요약 생성, 검증 결과 | 최종 보고서 본문 |
| `raw/` | 하위 폴더 | 원본 보관 | 웹 문서 저장본, 회의록 원문, 메모 원문 | LLM이 다시 쓴 요약 |
| `wiki/` | 하위 폴더 | 정리된 지식 | 개념 설명, 비교표, 결정 사항 정리 | 출처 없는 단정 |
| `output/` | 하위 폴더 | 업무 산출물 | 보고서, 실행 계획, 공유용 요약 | 원본 자료의 유일한 사본 |

핵심은 찾는 위치가 예측 가능해야 한다는 점입니다. 원문은 `raw/`, 정리한 지식은 `wiki/`, 내보낼 결과는 `output/`에 둡니다. 이 구분이 지켜지면 사람과 LLM 모두 같은 기준으로 자료를 찾을 수 있습니다.

### `index.md`는 길을 알려주는 문서입니다

`index.md`에는 모든 내용을 자세히 쓰지 않습니다. 대신 어디로 가야 하는지를 알려줍니다.

```markdown
Copy# 업무 자동화 위키

## 핵심 질문

반복 업무를 LLM으로 줄이려면 무엇부터 해야 할까?

## 먼저 읽을 문서

1. wiki/repeated-tasks.md
2. wiki/automation-candidates.md
3. wiki/risks-and-review.md

## 최근 산출물

- output/automation-plan-2026-05.md
```

이 예시는 실행 코드가 아니라 Markdown 문서 예시입니다. `index.md`에 넣으면 위키의 시작 화면으로 쓸 수 있습니다. 좋은 `index.md`는 짧습니다. 모든 내용을 담는 파일이 아니라 길을 잃지 않게 해 주는 파일입니다.

### `log.md`는 판단의 흔적을 남깁니다

LLM위키를 며칠만 써도 “이 내용을 언제 넣었더라?”라는 질문이 생깁니다. 그래서 `log.md`가 필요합니다.

```markdown
Copy# 처리 이력

| 날짜 | 작업 | 결과 | 확인 필요 |
|---|---|---|---|
| 2026-05-16 | 회의록 3개를 raw/에 추가 | 반복 업무 후보 5개 발견 | 고객 정보 익명화 기준 |
| 2026-05-16 | wiki/automation-candidates.md 작성 | 후보를 난이도별로 정리 | 실제 소요 시간 근거 |
```

로그는 완벽한 감사 문서일 필요가 없습니다. 나중에 다시 확인할 수 있을 만큼만 남기면 됩니다. 중요한 것은 자료 처리와 판단의 흔적을 지우지 않는 것입니다.

### `output/`은 산출물 작업 공간입니다

`output/`이라는 이름 때문에 최종본만 넣는 곳으로 오해하기 쉽습니다. 하지만 실무에서는 초안, 검토본, 공유본이 모두 생깁니다. 그래서 `output/`은 외부에 보여 줄 형태로 문서를 다듬는 작업 공간으로 이해하는 편이 좋습니다.

```text
Copyoutput/
├── automation-plan-draft.md
├── automation-plan-review.md
└── automation-plan-final.md
```

다만 `output/`에 있는 보고서가 원본을 대신하면 안 됩니다. 보고서는 `raw/`와 `wiki/`를 바탕으로 만든 결과입니다. 보고서에서 근거가 필요하면 다시 `wiki/`나 `raw/`로 돌아갈 수 있어야 합니다.

**학습자료: 기본 구조에서 문서가 흐르는 방향**

raw/ 원본 자료

wiki/ 정리 문서

index.md 안내와 연결

output/ 업무 산출물

log.md 처리 이력

이 흐름에서 원본은 출발점입니다. 정리 문서와 산출물은 원본을 바탕으로 만들어집니다. 중요한 작업은 `log.md`에 남깁니다.

## 원본과 요약을 섞지 않는 원칙

LLM위키에서 가장 중요한 원칙은 원본과 요약을 섞지 않는 것입니다. 원본은 자료가 처음 들어온 상태입니다. 요약은 사람이든 LLM이든 누군가 해석하고 줄인 결과입니다.

이 둘을 섞으면 검증이 어려워집니다. 요약 문장이 틀렸을 때 원문 자체의 오류인지, 요약 과정에서 빠진 내용인지, LLM이 추정한 내용인지 구분하기 어렵습니다.

Karpathy의 LLM Wiki 개념 문서는 원천 자료와 생성된 위키를 구분합니다. 구현체마다 폴더 이름은 다를 수 있습니다. 하지만 원본 자료와 파생 지식을 나누는 원칙은 공통으로 유지하는 편이 안전합니다.

**학습자료: 원본과 요약을 나누는 기준**

| 구분 | `raw/` 원본 | `wiki/` 요약·정리 |
| --- | --- | --- |
| 문서의 성격 | 처음 확보한 자료 | 자료를 읽고 해석한 문서 |
| 수정 방식 | 가능한 한 그대로 보존 | 최신 판단에 맞게 갱신 가능 |
| 문장 형태 | 회의록, 웹 문서 저장본, 원문 메모 | 요약, 비교, 결정 사항, 확인 필요 |
| 검증 역할 | 최종 근거 | 업무에 다시 쓰기 쉬운 설명 |
| 위험 | 원본을 덮어쓰면 근거가 사라짐 | 출처 없이 단정하면 추정이 사실처럼 보임 |

이 표에서 핵심은 위치가 문서의 역할을 결정한다는 점입니다. `raw/`에 있으면 원본으로 다룹니다. `wiki/`에 있으면 정리된 지식으로 다룹니다. `output/`에 있으면 공유하거나 실행할 산출물로 다룹니다.

### 원본은 보존하고 해석은 분리합니다

회의록 원문이 다음과 같다고 가정해 보겠습니다.

```markdown
Copy# 2026-05-16 팀 회의록

- 매주 월요일마다 고객 문의를 유형별로 다시 분류한다.
- 분류 기준은 담당자마다 조금씩 다르다.
- 다음 회의 전까지 최근 문의 20건을 샘플로 보기로 했다.
```

이 파일은 `raw/meeting-2026-05-16.md`에 둡니다. 그다음 LLM이나 사람이 정리한 문서는 `wiki/customer-inquiry-labeling.md`에 둡니다.

```markdown
Copy# 고객 문의 분류 자동화 후보

## 요약

팀은 매주 고객 문의를 유형별로 다시 분류하고 있다. 현재 분류 기준은 담당자마다 다르므로, 자동화 전에 라벨 기준을 먼저 맞춰야 한다.

## 근거

- raw/meeting-2026-05-16.md

## 확인 필요

- 최근 문의 20건에 개인정보가 포함되는지 확인해야 한다.
- 라벨 기준을 누가 승인할지 정해야 한다.
```

두 문서는 역할이 다릅니다. `raw/` 문서는 관찰된 사실을 담습니다. `wiki/` 문서는 그 사실을 업무 판단에 쓰기 좋게 정리합니다. `wiki/` 문서에는 요약, 근거, 확인 필요 항목이 함께 들어갈 수 있습니다.

### 실습: 원본과 요약을 분리해 저장하기

**목표**

회의록 원문과 정리 문서를 다른 위치에 저장해 근거를 잃지 않는 구조를 만듭니다.

**실행 전제**

앞 실습에서 `$HOME/llm-wiki-demo/work-automation` 폴더를 만들었다고 가정합니다. 같은 명령을 다시 실행하면 같은 파일 내용이 덮어써질 수 있습니다.

**성공 기준**

회의록 원문은 `raw/`에 있고, 요약 문서는 `wiki/`에 있으면 성공입니다.

```bash
CopyBASE="$HOME/llm-wiki-demo/work-automation"

printf '%s\n' \
'# 2026-05-16 팀 회의록' \
'' \
'- 매주 월요일마다 고객 문의를 유형별로 다시 분류한다.' \
'- 분류 기준은 담당자마다 조금씩 다르다.' \
'- 다음 회의 전까지 최근 문의 20건을 샘플로 보기로 했다.' \
> "$BASE/raw/meeting-2026-05-16.md"

printf '%s\n' \
'# 고객 문의 분류 자동화 후보' \
'' \
'## 요약' \
'' \
'팀은 매주 고객 문의를 유형별로 다시 분류하고 있다. 현재 분류 기준은 담당자마다 다르므로, 자동화 전에 라벨 기준을 먼저 맞춰야 한다.' \
'' \
'## 근거' \
'' \
'- raw/meeting-2026-05-16.md' \
'' \
'## 확인 필요' \
'' \
'- 최근 문의 20건에 개인정보가 포함되는지 확인해야 한다.' \
'- 라벨 기준을 누가 승인할지 정해야 한다.' \
> "$BASE/wiki/customer-inquiry-labeling.md"

find "$BASE" -maxdepth 2 -type f | sort
```

예상 결과는 다음과 비슷합니다.

```text
Copy/Users/사용자명/llm-wiki-demo/work-automation/index.md
/Users/사용자명/llm-wiki-demo/work-automation/log.md
/Users/사용자명/llm-wiki-demo/work-automation/raw/meeting-2026-05-16.md
/Users/사용자명/llm-wiki-demo/work-automation/wiki/customer-inquiry-labeling.md
```

이제 원본과 요약이 분리되었습니다. 원문을 확인하려면 `raw/meeting-2026-05-16.md`를 봅니다. 업무 판단을 보려면 `wiki/customer-inquiry-labeling.md`를 봅니다.

### 실습: 산출물도 근거로 돌아가게 만들기

**목표**

정리 문서를 바탕으로 업무 산출물을 만들고, 산출물 안에 근거 문서 링크를 남깁니다.

**실행 전제**

앞 실습에서 `raw/meeting-2026-05-16.md`와 `wiki/customer-inquiry-labeling.md`를 만들었다고 가정합니다.

**성공 기준**

`output/customer-inquiry-automation-plan.md`가 만들어지고, 문서 안에 `wiki/`와 `raw/` 근거가 함께 적혀 있으면 성공입니다.

```bash
CopyBASE="$HOME/llm-wiki-demo/work-automation"

test -f "$BASE/wiki/customer-inquiry-labeling.md" || {
  echo "먼저 wiki/customer-inquiry-labeling.md를 만드는 실습을 실행하세요." >&2
  exit 1
}

test -f "$BASE/raw/meeting-2026-05-16.md" || {
  echo "먼저 raw/meeting-2026-05-16.md를 만드는 실습을 실행하세요." >&2
  exit 1
}

mkdir -p "$BASE/output"

printf '%s\n' \
'# 고객 문의 분류 자동화 1차 실행 계획' \
'' \
'## 목표' \
'' \
'최근 문의 20건을 기준으로 라벨 자동 추천이 가능한지 확인한다.' \
'' \
'## 실행 순서' \
'' \
'1. 라벨 기준 초안을 만든다.' \
'2. 최근 문의 20건에서 개인정보 포함 여부를 확인한다.' \
'3. 사람이 붙인 라벨과 LLM 추천 라벨을 비교한다.' \
'4. 사람이 받아들일 수 있는 추천 비율을 기록한다.' \
'' \
'## 근거 문서' \
'' \
'- wiki/customer-inquiry-labeling.md' \
'- raw/meeting-2026-05-16.md' \
> "$BASE/output/customer-inquiry-automation-plan.md"

ls -1 "$BASE/output"
```

예상 결과입니다.

```text
Copycustomer-inquiry-automation-plan.md
```

이 산출물은 단독으로 읽을 수 있습니다. 동시에 근거 문서로 돌아갈 수 있습니다. 이것이 좋은 LLM위키 폴더 구조의 목표입니다.

## 정리와 검증 포인트

좋은 폴더 구조는 멋진 이름을 붙이는 일이 아닙니다. 문서의 역할을 분명히 나누는 일입니다. 원본은 보존하고, 정리는 따로 만들고, 산출물은 근거로 돌아갈 수 있게 둡니다.

다음 항목을 확인하면 폴더 구조가 제대로 잡혔는지 판단할 수 있습니다.

| 검증 항목 | 확인 질문 |
| --- | --- |
| 주제 분리 | 이 폴더는 하나의 업무 질문으로 설명되는가? |
| 원본 보존 | 원본 자료가 `raw/`에 따로 남아 있는가? |
| 요약 분리 | LLM이나 사람이 정리한 문서가 `wiki/`에 있는가? |
| 안내판 | `index.md`만 읽어도 이 위키의 목적과 주요 문서를 알 수 있는가? |
| 이력 | `log.md`에 자료 추가와 주요 변경 이력이 남는가? |
| 산출물 | 보고서와 실행 계획이 `output/`에 따로 저장되는가? |
| 근거 연결 | `output/` 문서에서 `wiki/`와 `raw/`로 돌아갈 수 있는가? |

모든 항목을 처음부터 완벽히 채울 필요는 없습니다. 다만 원본, 정리 문서, 산출물의 위치는 처음부터 분리해야 합니다. 이 구분이 무너지면 나중에 검증 비용이 크게 늘어납니다.
