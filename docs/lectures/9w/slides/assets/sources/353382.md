# 2.1 지식이 쌓이는 세 층

![2.1 지식이 쌓이는 세 층 삽화](https://static.wikidocs.net/images/page/353382/2.1-%EC%A7%80%EC%8B%9D%EC%9D%B4-%EC%8C%93%EC%9D%B4%EB%8A%94-%EC%84%B8-%EC%B8%B5.jpg)

LLM위키를 제대로 쓰려면 먼저 폴더 이름보다 **역할** 을 이해해야 합니다. 원본, 정리 문서, 작업 규칙이 섞이면 위키는 금방 믿기 어려운 메모 더미가 됩니다. 회의에서 실제로 나온 말인지, LLM이 추정한 결론인지, 내가 나중에 덧붙인 판단인지 구분하기 어려워지기 때문입니다.

이 절에서는 LLM위키를 세 층으로 나누어 봅니다. 첫째는 원본을 보관하는 `raw`입니다. 둘째는 읽고 활용하는 `wiki`입니다. 셋째는 작업 규칙을 담는 `AGENTS.md` 또는 `CLAUDE.md`입니다. 이 세 층을 이해하면 LLM에게 매번 같은 설명을 반복하지 않아도 되고, 나중에 결과를 검증할 근거도 남길 수 있습니다.

> 이 절에서 말하는 LLM위키는 특정 제품 하나가 아닙니다. 2026년 5월 16일 확인한 자료 기준으로, LLM위키는 원천 자료를 모으고 LLM으로 구조화한 뒤 계속 갱신하는 지식 관리 패턴으로 보는 편이 안전합니다. 구현체에 따라 폴더명과 명령은 달라질 수 있습니다.

## 세 층이 필요한 이유

처음에는 자료를 한 폴더에 모아도 충분해 보입니다. 회의록, 웹 문서, LLM 요약, 보고서 초안을 모두 `docs/`에 넣어도 검색은 됩니다. 하지만 시간이 지나면 문제가 생깁니다.

가장 흔한 문제는 **요약이 원본처럼 보이는 것** 입니다. LLM이 만든 문장이 매끄러울수록 더 위험합니다. 원문에는 “검토 후 결정”이라고 되어 있었는데, 위키에는 “도입하기로 결정”이라고 적힐 수 있습니다. 원본과 요약이 섞여 있으면 이 차이를 찾기 어렵습니다.

**학습자료: 섞인 구조와 세 층 구조의 차이**

| 구조 | 처음에는 편한 점 | 나중에 생기는 문제 |
| --- | --- | --- |
| 모든 자료를 한 폴더에 넣음 | 만들기 쉽고 바로 검색할 수 있음 | 원본, 요약, 판단, 산출물이 섞입니다. |
| 원본과 위키만 나눔 | 근거와 정리 문서를 구분할 수 있음 | LLM이 어떤 기준으로 정리해야 하는지 매번 설명해야 합니다. |
| `raw`, `wiki`, 규칙 파일로 나눔 | 원본 보존, 지식 재사용, 작업 기준을 함께 관리할 수 있음 | 처음에 작은 구조를 정해야 합니다. |

이 표에서 보듯이 세 층 구조는 복잡하게 보이지만, 실제로는 사고를 줄이는 장치입니다. `raw`는 증거를 지킵니다. `wiki`는 그 증거를 읽기 쉬운 지식으로 바꿉니다. 규칙 파일은 LLM이 이 둘을 섞지 않게 합니다.

**학습자료: LLM위키의 기본 흐름**

raw/

원본 자료 보관

wiki/

읽고 활용하는 지식

AGENTS.md 또는 CLAUDE.md

작업 규칙

질문

요약

보고서와 실행 계획

이 도해에서 `raw`는 직접 보고서가 되는 공간이 아닙니다. `raw`는 나중에 돌아가 확인할 수 있는 근거입니다. 독자가 자주 읽고 활용하는 곳은 `wiki`입니다. `AGENTS.md`나 `CLAUDE.md`는 LLM이 두 공간을 어떤 기준으로 다룰지 알려 줍니다.

## 원본을 보관하는 `raw`

`raw`는 원천 자료를 보관하는 층입니다. 회의록 원문, 웹 문서 저장본, PDF에서 추출한 텍스트, 업무 메모, 조사 자료가 이곳에 들어갑니다. 핵심 원칙은 단순합니다. `raw`에 들어온 자료는 가능하면 원본 상태를 보존합니다.

원본을 보관해야 하는 이유는 검증 때문입니다. LLM이 만든 요약은 편리하지만 중요한 조건을 빠뜨릴 수 있습니다. 나중에 “이 결론의 근거가 어디였지?”라고 물었을 때 돌아갈 곳이 있어야 합니다. 그 돌아갈 곳이 `raw`입니다.

`raw` 안에서는 원본과 해석을 섞지 않습니다. 예를 들어 회의록 원문 파일에 “이 결정은 위험해 보인다”라는 개인 판단을 덧붙이면, LLM이 그것을 회의 내용처럼 읽을 수 있습니다. 판단은 `wiki` 문서의 해석 영역이나 별도 메모에 둡니다.

**학습자료: `raw`에 넣을 것과 조심할 것**

| 자료 | `raw`에 둘 수 있는가 | 이유 |
| --- | --- | --- |
| 회의록 원문 | 예 | 결정과 발언의 근거를 확인할 수 있습니다. |
| 공식 문서 저장본 | 예 | URL과 확인 날짜를 남기면 나중에 다시 검증할 수 있습니다. |
| 업무 메모 원문 | 예 | 반복 업무의 실제 맥락을 보존할 수 있습니다. |
| LLM 요약문 | 보통 아니요 | 원본이 아니라 파생 문서이므로 `wiki`에 두는 편이 안전합니다. |
| 개인 해석 | 보통 아니요 | 원문과 판단이 섞이면 근거 추적이 어려워집니다. |
| 고객 개인정보, 계약 조건, 비공개 코드 | 확인 필요 | 도구의 데이터 처리 정책과 조직 보안 기준을 먼저 확인해야 합니다. |

이 표는 `raw`를 아무 자료나 모으는 창고로 쓰지 않기 위한 기준입니다. `raw`의 목적은 많이 저장하는 것이 아닙니다. 나중에 다시 확인할 수 있는 근거를 보존하는 것입니다.

### `raw` 파일의 최소 형식

`raw` 파일에는 적어도 자료 제목, 출처, 확인 날짜가 있어야 합니다. 웹 문서라면 URL과 확인 날짜를 남깁니다. 회의록이라면 회의 날짜와 참석 범위를 남깁니다. 내부 문서라면 파일명과 버전 정보를 남깁니다.

다음은 실행 코드가 아니라 Markdown 원본 메모 예시입니다.

```markdown
Copy# 팀 반복 업무 메모

출처: 2026-05-16 팀 운영 회의
작성자: 회의 기록 담당자
확인 날짜: 2026-05-16

## 관찰한 반복 업무

- 매주 월요일 회의록에서 실행 항목을 다시 정리한다.
- 고객 문의를 유형별로 분류한 뒤 담당자에게 전달한다.
- 릴리스 노트를 작성할 때 변경 사항, 영향 범위, 확인 방법을 매번 다시 묻는다.

## 회의에서 나온 제약

- 고객명과 계약 조건은 외부 도구에 입력하지 않는다.
- 최종 발송 문구는 담당자가 확인한다.
```

이 원본은 짧지만 다시 확인할 수 있는 정보를 담고 있습니다. 누가 언제 남긴 자료인지 알 수 있습니다. 관찰한 업무와 제약도 분리되어 있습니다. 나중에 LLM이 자동화 후보를 정리하더라도 이 파일로 돌아와 근거를 확인할 수 있습니다.

## 읽고 활용하는 `wiki`

`wiki`는 LLM이 원본을 읽고 정리한 지식이 쌓이는 층입니다. 독자는 보통 `raw`보다 `wiki`를 더 자주 읽습니다. 질문할 때도, 보고서를 만들 때도, 다음 작업 계획을 세울 때도 `wiki`가 중심이 됩니다.

`wiki` 문서는 원본을 그대로 반복하지 않습니다. 여러 원본에서 반복되는 개념을 묶습니다. 관련 문서끼리 연결합니다. 현재까지 확인된 내용을 읽기 쉬운 형태로 정리합니다. 그래서 `wiki`는 원본보다 짧고, 구조적이며, 다시 쓰기 쉬워야 합니다.

다만 `wiki`는 원본보다 편리한 만큼 위험도 있습니다. LLM이 만든 문장은 그럴듯해 보일 수 있습니다. 하지만 원본의 조건을 빠뜨리거나 서로 다른 자료의 맥락을 섞을 수 있습니다. 좋은 `wiki` 문서는 핵심 주장 옆에 출처나 근거 위치를 남깁니다.

**학습자료: `raw`에서 `wiki`로 바뀌는 과정**

raw/meeting-notes

회의록 원문

wiki/concepts

반복 업무 후보

raw/web-sources

공식 문서와 참고 자료

raw/memos

업무 메모

wiki/index.md

전체 안내

wiki/decisions

결정 사항

output/

보고서 초안

이 흐름에서 `wiki`는 단순 요약 폴더가 아닙니다. 여러 원본을 주제별 문서로 묶는 곳입니다. 회의록에는 “고객 문의 분류”가 한 줄만 나올 수 있습니다. 하지만 관련 메모와 함께 정리하면 `wiki/concepts/customer-ticket-labeling.md` 같은 독립 문서가 됩니다.

### 좋은 `wiki` 문서의 기본 모양

좋은 `wiki` 문서는 질문에 다시 쓰기 쉽습니다. 제목만 보고 무엇을 다루는지 알 수 있어야 합니다. 핵심 내용이 앞에 나오고, 근거가 뒤따라야 합니다. 확실한 내용과 확인이 필요한 내용도 구분해야 합니다.

```markdown
Copy# 반복 업무 자동화 후보

## 요약

현재 자료 기준으로 반복 업무 자동화 후보는 회의록 실행 항목 정리,
고객 문의 1차 분류, 릴리스 노트 초안 작성이다.

## 확인된 내용

- 회의록 실행 항목 정리는 매주 월요일 반복된다.
  - 근거: raw/meeting-notes/2026-05-16-repeat-work.md
- 고객 문의 분류에는 고객명과 계약 조건이 포함될 수 있다.
  - 근거: raw/meeting-notes/2026-05-16-repeat-work.md
- 릴리스 노트 작성에는 변경 사항, 영향 범위, 확인 방법이 필요하다.
  - 근거: raw/meeting-notes/2026-05-16-repeat-work.md

## 확인 필요

- 각 업무에 걸리는 평균 시간
- 자동화 결과를 검수할 담당자
- 고객 문의 데이터의 비식별화 기준

## 다음 질문

- 세 후보 중 가장 작게 실험할 수 있는 업무는 무엇인가?
- 개인정보 위험이 가장 낮은 후보는 무엇인가?
```

이 문서는 원본보다 읽기 쉽습니다. 하지만 원본과 연결되어 있기 때문에 검증도 가능합니다. 특히 `확인 필요`를 따로 두면 LLM이 모르는 내용을 아는 것처럼 쓰는 일을 줄일 수 있습니다.

**학습자료: `raw`와 `wiki`의 역할 비교**

| 항목 | `raw` | `wiki` |
| --- | --- | --- |
| 목적 | 원본 보존 | 이해와 재사용 |
| 문서 성격 | 자료에 가까움 | 지식 문서에 가까움 |
| 수정 방식 | 되도록 원형 유지 | 새 근거에 따라 갱신 |
| 주요 독자 | 검증하는 사람, LLM | 질문하는 사람, 작업자, LLM |
| 주요 위험 | 자료를 잃거나 출처를 놓침 | 요약 오류와 추정이 사실처럼 굳어짐 |
| 좋은 상태 | 출처와 날짜가 남아 있음 | 주장과 근거가 연결되어 있음 |

`raw`와 `wiki`는 우열 관계가 아닙니다. `raw`만 있으면 찾기 어렵고, `wiki`만 있으면 믿기 어렵습니다. 둘이 함께 있어야 읽기 쉬우면서도 검증 가능한 지식이 됩니다.

## 작업 규칙을 담는 `AGENTS.md` 또는 `CLAUDE.md`

세 번째 층은 작업 규칙입니다. 이 파일은 LLM에게 “이 위키를 어떻게 다뤄야 하는지” 알려 줍니다. 사람에게는 운영 규칙이고, LLM에게는 작업 지시서입니다.

도구마다 기본으로 읽는 파일명은 다릅니다. OpenAI Codex는 공식 문서에서 `AGENTS.md`를 프로젝트 지침 파일로 설명합니다. Claude Code는 공식 문서에서 `CLAUDE.md`를 메모리 또는 프로젝트 지침 파일로 설명합니다. 따라서 Codex를 중심으로 쓴다면 `AGENTS.md`, Claude Code를 중심으로 쓴다면 `CLAUDE.md`를 우선 고려합니다.

규칙 파일에는 폴더의 의미, 원본 보존 원칙, 출처 표기 방식, 확인 필요 표시 방법, 금지할 작업을 적습니다. 규칙 파일이 없으면 LLM은 매번 대화에서 즉석으로 판단합니다. 어느 날은 원본을 요약하고, 어느 날은 원본을 덮어쓸 수 있습니다.

**학습자료: 규칙 파일이 하는 일**

사용자 요청

'회의록을 위키에 반영해줘'

AGENTS.md 또는 CLAUDE.md

작업 규칙 확인

raw는 원본 보존

wiki에는 요약과 근거 연결

확인 안 된 내용은 확인 필요 표시

LLM 작업 결과

이 도해는 규칙 파일이 단순한 설명서가 아니라 작업 기준이라는 점을 보여 줍니다. 같은 요청을 하더라도 규칙이 있으면 LLM은 원본 보존, 출처 연결, 불확실성 표시를 함께 고려합니다.

### 최소 규칙 파일 예시

아래 예시는 작은 개인 LLM위키에서 시작할 수 있는 `AGENTS.md` 예시입니다. Claude Code를 쓴다면 같은 취지를 `CLAUDE.md`에 담을 수 있습니다. 실제 사용 전에는 사용하는 도구가 어떤 파일을 자동으로 읽는지 확인해야 합니다.

```markdown
Copy# LLM위키 작업 규칙

## 기본 구조

- `raw/`는 원본 자료를 보관하는 곳이다.
- `wiki/`는 원본을 바탕으로 정리한 지식 문서를 보관하는 곳이다.
- `output/`은 보고서, 요약문, 실행 계획 같은 산출물을 보관하는 곳이다.

## 원본 보존

- `raw/` 안의 원본 자료는 임의로 덮어쓰지 않는다.
- 원본에서 오류를 발견하면 원본을 고치기보다 별도 메모에 수정 사항을 기록한다.
- 원본 자료의 출처, 확인 날짜, 버전 정보가 보이면 유지한다.

## 위키 작성

- `wiki/` 문서에는 핵심 주장과 근거 위치를 함께 남긴다.
- 근거가 부족한 내용은 `확인 필요`로 표시한다.
- 서로 충돌하는 자료가 있으면 하나로 합치지 말고 충돌 사실을 적는다.
- 오래된 정보일 수 있는 내용에는 확인 날짜를 남긴다.

## 답변 원칙

- 위키에 근거가 있는 내용과 추정을 구분한다.
- 사용자가 보고서나 실행 계획을 요청하면 관련 `wiki/` 문서를 먼저 확인한다.
- 민감 정보가 포함된 자료는 외부 전송이나 웹 검색에 사용하지 않는다.
```

이 예시는 완벽한 규칙이 아닙니다. 하지만 시작점으로는 충분합니다. 중요한 것은 LLM이 지켜야 할 기준을 문서로 남기는 일입니다. 규칙을 문서로 남겨야 다음 세션에서도 같은 방식으로 일할 수 있습니다.

**학습자료: 규칙 파일 점검표**

| 점검 항목 | 좋은 예 | 부족한 예 |
| --- | --- | --- |
| 폴더 역할 | `raw/`는 원본, `wiki/`는 정리된 지식이라고 명시 | “자료를 잘 정리한다”처럼 추상적으로만 씀 |
| 원본 보호 | `raw/` 파일을 임의로 덮어쓰지 않는다고 명시 | 원본 수정 기준이 없음 |
| 출처 표시 | 핵심 주장마다 근거 위치를 남긴다고 명시 | 출처가 있으면 좋다고만 씀 |
| 불확실성 | 근거 부족 시 `확인 필요`로 표시 | 모르는 내용도 자연스럽게 이어 씀 |
| 보안 | 민감 정보 처리 제한을 명시 | 외부 호출과 비공개 자료 기준이 없음 |

처음에는 이 정도면 충분합니다. 복잡한 자동화보다 중요한 것은 원본을 보호하고, 출처를 남기고, 불확실한 내용을 단정하지 않는 습관입니다.

## 세 층을 함께 쓰는 작은 실습

이번 실습에서는 특정 LLM위키 구현체를 설치하지 않습니다. 폴더와 파일만 만들어 세 층의 역할을 눈으로 확인합니다. macOS, Linux, WSL, Git Bash, zsh/bash 환경에서 실행할 수 있습니다. Windows PowerShell에서는 명령 문법이 다를 수 있습니다.

### 실습: 최소 LLM위키 구조 만들기

**목표**

`raw`, `wiki`, `AGENTS.md`가 서로 어떤 역할을 하는지 작은 폴더 구조로 확인합니다.

**실행 전제**

현재 폴더 아래에 `work-automation-wiki`라는 실습 폴더를 만들 수 있어야 합니다. 같은 이름의 폴더가 이미 있다면 다른 이름을 사용하세요. 아래 명령은 `AGENTS.md`가 이미 있을 경우 내용을 덮어씁니다.

**성공 기준**

실행 후 `raw/meeting-notes`, `wiki/concepts`, `output` 폴더와 `AGENTS.md` 파일이 생기면 성공입니다.

```bash
Copymkdir -p work-automation-wiki/raw/meeting-notes
mkdir -p work-automation-wiki/wiki/concepts
mkdir -p work-automation-wiki/output

cat > work-automation-wiki/AGENTS.md <<'EOF'
# LLM위키 작업 규칙

- raw/는 원본 자료를 보관한다.
- wiki/는 원본을 바탕으로 정리한 지식 문서를 보관한다.
- 근거가 부족한 내용은 확인 필요로 표시한다.
EOF

find work-automation-wiki -maxdepth 3 -type d -print | sort
```

예상 결과는 다음과 비슷합니다.

```text
Copywork-automation-wiki
work-automation-wiki/output
work-automation-wiki/raw
work-automation-wiki/raw/meeting-notes
work-automation-wiki/wiki
work-automation-wiki/wiki/concepts
```

이 명령은 LLM위키 도구를 설치하지 않아도 구조를 확인할 수 있는 최소 예제입니다. 실제 구현체를 쓰면 `_index.md`, `log.md`, `config.md`, `inbox/` 같은 파일이나 폴더가 더 생길 수 있습니다. 구현체마다 구조는 달라도, 이 절에서는 세 층의 역할만 기억하면 됩니다.

### 실습: 원본과 위키 문서 구분하기

**목표**

같은 내용을 `raw`와 `wiki`에 어떻게 다르게 적는지 확인합니다.

**실행 전제**

앞 실습에서 `work-automation-wiki` 폴더를 만들었다고 가정합니다.

**성공 기준**

`raw`에는 회의 메모 원문이 남고, `wiki`에는 근거가 연결된 정리 문서가 생기면 성공입니다.

```bash
Copycat > work-automation-wiki/raw/meeting-notes/2026-05-16-repeat-work.md <<'EOF'
# 팀 반복 업무 메모

출처: 2026-05-16 팀 운영 회의
확인 날짜: 2026-05-16

## 관찰한 반복 업무

- 매주 월요일 회의록에서 실행 항목을 다시 정리한다.
- 고객 문의를 유형별로 분류한 뒤 담당자에게 전달한다.

## 제약

- 고객명과 계약 조건은 외부 도구에 입력하지 않는다.
EOF

cat > work-automation-wiki/wiki/concepts/repeat-work-automation.md <<'EOF'
# 반복 업무 자동화 후보

## 요약

현재 자료 기준으로 반복 업무 자동화 후보는 회의록 실행 항목 정리와 고객 문의 1차 분류다.

## 확인된 내용

- 회의록 실행 항목 정리는 매주 월요일 반복된다.
  - 근거: raw/meeting-notes/2026-05-16-repeat-work.md
- 고객 문의 분류에는 민감 정보가 포함될 수 있다.
  - 근거: raw/meeting-notes/2026-05-16-repeat-work.md

## 확인 필요

- 각 업무에 걸리는 평균 시간
- 고객 문의 데이터의 비식별화 기준
EOF

find work-automation-wiki -type f -print | sort
```

예상 결과는 다음과 비슷합니다.

```text
Copywork-automation-wiki/AGENTS.md
work-automation-wiki/raw/meeting-notes/2026-05-16-repeat-work.md
work-automation-wiki/wiki/concepts/repeat-work-automation.md
```

이 실습의 핵심은 파일을 많이 만든 것이 아닙니다. 같은 주제라도 원본은 `raw`에, 정리된 지식은 `wiki`에 둔다는 감각을 익히는 것입니다. `wiki` 문서는 더 읽기 쉽지만, 그 문서가 믿을 만하려면 `raw`로 돌아갈 길이 있어야 합니다.

## 이 절의 검증 포인트

이 절을 읽고 나면 다음 질문에 답할 수 있어야 합니다.

| 질문 | 확인 기준 |
| --- | --- |
| `raw`는 무엇을 위한 곳인가? | 원본 자료를 보존하고 나중에 근거를 확인하는 곳이라고 설명할 수 있습니다. |
| `wiki`는 `raw`와 어떻게 다른가? | 원본을 바탕으로 정리한 파생 지식이며, 질문과 산출물 작성에 활용하는 곳이라고 설명할 수 있습니다. |
| 규칙 파일은 왜 필요한가? | LLM이 원본 보존, 출처 표시, 불확실성 표시 같은 기준을 지키게 하기 위해 필요하다고 설명할 수 있습니다. |
| 원본과 요약을 섞으면 어떤 문제가 생기는가? | 어떤 내용이 실제 근거이고 어떤 내용이 해석인지 구분하기 어려워집니다. |
| 근거가 부족한 내용은 어떻게 표시해야 하는가? | 단정하지 않고 `확인 필요`, `추정`, `현재 자료 기준` 같은 표현으로 제한해야 합니다. |
| Codex와 Claude Code의 규칙 파일은 무엇이 다른가? | Codex는 `AGENTS.md`, Claude Code는 `CLAUDE.md`를 공식 문서 기준으로 확인해야 한다고 설명할 수 있습니다. |

LLM위키의 구조는 복잡한 기술에서 시작하지 않습니다. 원본을 지키고, 정리된 지식을 따로 두고, 작업 규칙을 문서로 남기는 것에서 시작합니다. 이 세 층이 분리되어 있으면 다음 절에서 다룰 폴더 구조도 훨씬 쉽게 이해할 수 있습니다.
