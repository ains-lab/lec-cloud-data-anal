# 5.2 자료 수집하기

![5.2 자료 수집하기 삽화](https://static.wikidocs.net/images/page/353395/5.2-%EC%9E%90%EB%A3%8C-%EC%88%98%EC%A7%91%ED%95%98%EA%B8%B0.jpg)

자료 수집은 LLM위키의 첫 단추입니다. 자료를 아무렇게나 넣으면 위키 문서도 아무렇게나 만들어집니다. 반대로 원천 자료, 확인 날짜, 처리 이력을 남기면 나중에 LLM이 만든 요약을 다시 검증할 수 있습니다.

이 절에서는 웹 문서, 업무 메모, 회의록을 LLM위키에 넣는 기본 방법을 익힙니다. 특정 도구 명령보다 오래 가는 원칙을 먼저 다룹니다. 예제는 Markdown 파일과 폴더만으로 실행할 수 있게 구성했습니다.

> 이 절의 예제는 특정 LLM위키 구현체의 필수 명령이 아닙니다. LLM위키 패턴을 수동 Markdown 방식으로 따라 해 보는 실습입니다. Codex, Claude Code, `nvk/llm-wiki` 같은 도구를 쓸 때도 같은 기준을 적용하면 됩니다.

## 웹 문서 넣기

웹 문서를 넣는다는 말은 URL을 하나 붙여 넣는다는 뜻이 아닙니다. 나중에 다시 확인할 수 있도록 문서의 제목, URL, 발행자, 확인 날짜, 수집 이유를 함께 남긴다는 뜻입니다.

LLM은 웹 문서를 읽고 요약할 수 있습니다. 하지만 요약만 남기면 위험합니다. 원문이 바뀌었는지, 어떤 날짜에 확인한 내용인지, 어느 문장을 근거로 삼았는지 추적하기 어렵기 때문입니다. 따라서 웹 문서는 `raw/`에 원천 자료로 보관하고, `wiki/`에는 다시 쓰기 쉬운 정리 문서를 둡니다.

웹 문서를 넣을 때 최소한 다음 네 가지를 남깁니다.

| 항목 | 남기는 이유 | 예 |
| --- | --- | --- |
| 제목 | 나중에 같은 자료를 찾기 위해 | Codex AGENTS.md 공식 문서 |
| URL | 원문으로 돌아가기 위해 | `https://developers.openai.com/...` |
| 확인 날짜 | 최신성 판단을 위해 | 2026-05-16 |
| 수집 이유 | 위키에 넣을 가치가 있는지 판단하기 위해 | Codex에서 작업 규칙 파일을 설명하는 근거 |

이 표의 핵심은 “웹 문서의 내용”보다 “웹 문서를 다시 검증할 수 있는 정보”를 먼저 잡는 것입니다. LLM위키에서 웹 문서는 답변 재료이면서 감사 대상입니다.

**학습자료: 웹 문서 수집 흐름**

아니오

예

웹 문서 발견

위키에 넣을 가치가 있는가

후보에서 제외

raw/web에 원천 카드 저장

wiki/sources에 정리 문서 작성

index.md에 링크 추가

log.md에 처리 이력 기록

나중에 질문과 산출물에 재사용

이 흐름에서 가장 중요한 지점은 `raw/web`과 `wiki/sources`를 나누는 것입니다. `raw/web`은 원문을 추적하기 위한 공간입니다. `wiki/sources`는 사람이 읽고 다시 질문하기 쉽게 정리한 공간입니다.

웹 페이지 전체를 저장할 수 있는 도구를 쓸 수도 있습니다. 예를 들어 Obsidian Web Clipper 같은 도구는 웹 콘텐츠를 노트 저장소에 저장하는 기능을 제공합니다. 다만 모든 웹 문서를 통째로 복사해도 된다는 뜻은 아닙니다. 공개 문서, 사내 문서, 유료 문서, 고객 자료는 각각 권한과 보안 기준이 다릅니다. 저장해도 되는 범위가 불확실하면 제목, URL, 확인 날짜, 짧은 메모만 남기고 원문 전체 저장은 보류합니다.

### 실습: 웹 문서 수집 카드 만들기

**목표**

웹 문서를 바로 요약하지 않고, 먼저 원천 자료 카드와 정리 문서를 분리해 저장합니다.

**실행 전제**

macOS, Linux, WSL처럼 `bash` 또는 `zsh`를 사용할 수 있는 환경이면 됩니다. 이 예제는 인터넷에서 문서를 가져오지 않습니다. 수집 형식을 익히기 위한 로컬 파일 생성 예제입니다.

**성공 기준**

`raw/web`에는 원천 자료 카드가 생기고, `wiki/sources`에는 정리 문서가 생깁니다. `log.md`에는 어떤 자료를 넣었는지 기록됩니다.

```bash
CopyBASE="$HOME/llm-wiki-ch5-2"

if [ -e "$BASE" ]; then
  echo "이미 실습 폴더가 있습니다. BASE 값을 바꾸고 다시 실행하세요." >&2
  exit 1
fi

mkdir -p "$BASE/raw/web" "$BASE/raw/meetings" "$BASE/wiki/sources" "$BASE/wiki/meetings" "$BASE/output"

cat > "$BASE/index.md" <<'EOF'
# 자료 수집 실습 위키

## 수집한 원천 자료

- 웹 문서: `raw/web/2026-05-16-codex-agents-md.md`

## 정리 문서

- `wiki/sources/codex-agents-md-source-note.md`
EOF

cat > "$BASE/log.md" <<'EOF'
# 처리 이력

EOF

cat > "$BASE/raw/web/2026-05-16-codex-agents-md.md" <<'EOF'
# 웹 원천 자료 카드: Codex AGENTS.md 공식 문서

## 메타데이터

- 제목: Codex AGENTS.md 공식 문서
- URL: https://developers.openai.com/codex/guides/agents-md
- 발행자: OpenAI Developers
- 확인 날짜: 2026-05-16
- 자료 성격: 공식 문서
- 수집 이유: Codex에서 프로젝트 작업 규칙 파일을 어떻게 다루는지 확인하기 위해

## 원문에서 확인할 내용

- AGENTS.md가 어떤 범위에서 읽히는지
- 지침 파일의 우선순위와 한계
- 긴 지침 파일을 사용할 때 확인해야 할 제한

## 확인 필요

- 문서 갱신일이 별도로 표시되는지 확인 필요
- 설치된 Codex 버전에서 실제 동작이 같은지 확인 필요
EOF

cat > "$BASE/wiki/sources/codex-agents-md-source-note.md" <<'EOF'
# Codex AGENTS.md 문서 정리

## 한 문장 요약

Codex에서 프로젝트 작업 규칙을 관리할 때 `AGENTS.md`를 근거 문서로 참고할 수 있다.

## 근거

- 원천 자료: `raw/web/2026-05-16-codex-agents-md.md`
- 확인 날짜: 2026-05-16
- 자료 성격: 공식 문서

## 확인된 내용

- Codex 작업 규칙을 설명할 때 공식 문서를 우선 근거로 삼는다.
- 원고에는 `AGENTS.md`가 작업을 강제한다고 쓰지 않는다.
- 지침 파일은 LLM이 따르도록 유도하는 컨텍스트이며, 결과는 검증해야 한다.

## 확인 필요

- 독자가 사용하는 Codex 버전에서 같은 방식으로 로드되는지 확인해야 한다.
EOF

printf '%s\n' \
"- 2026-05-16 | ingest | raw/web/2026-05-16-codex-agents-md.md | 결과: wiki/sources/codex-agents-md-source-note.md | 상태: 초안" \
>> "$BASE/log.md"

find "$BASE" -maxdepth 3 -type f | sed "s|$BASE|.|" | sort
```

예상 결과는 다음과 비슷합니다.

```text
Copy./index.md
./log.md
./raw/web/2026-05-16-codex-agents-md.md
./wiki/sources/codex-agents-md-source-note.md
```

이 예제에서 웹 문서의 내용은 두 번 저장됩니다. `raw/web`에는 수집 당시의 메타데이터와 확인할 항목을 둡니다. `wiki/sources`에는 나중에 질문과 원고에 다시 쓰기 쉬운 형태로 정리합니다.

중요한 점은 정리 문서에 원천 자료 경로가 남아 있다는 것입니다. 나중에 “Codex의 지침 파일은 행동을 보장한다” 같은 문장이 생기면 이 원천 자료로 돌아가 표현을 고칠 수 있습니다. 근거가 부족하면 단정하지 않고 “확인 필요”로 남깁니다.

## 업무 메모와 회의록 넣기

업무 메모와 회의록은 웹 문서보다 더 지저분합니다. 문장이 완성되어 있지 않고, 참석자의 추정과 결정 사항이 섞입니다. 그래서 더 가치가 있습니다. 업무의 실제 맥락은 공식 문서보다 회의록과 메모에 남는 경우가 많기 때문입니다.

LLM위키에 업무 메모를 넣을 때는 예쁘게 고쳐 쓰기 전에 원래 상태를 보존합니다. 회의에서 나온 말, 아직 확정되지 않은 의견, 다음 행동을 구분해 두어야 합니다. 원문을 정리하면서 판단이 섞이면 나중에 “무엇이 실제 결정이었는지” 알기 어려워집니다.

업무 메모와 회의록은 다음처럼 나누어 넣으면 다루기 쉽습니다.

| 자료 종류 | `raw/`에 남길 것 | `wiki/`에 정리할 것 |
| --- | --- | --- |
| 개인 업무 메모 | 작성일, 작성자, 원문 메모, 떠오른 질문 | 반복 업무 규칙, 문제 패턴, 다음 질문 |
| 회의록 | 회의일, 참석자, 안건, 원문 기록 | 결정 사항, 실행 항목, 확인 필요 |
| 인터뷰 메모 | 인터뷰 대상, 맥락, 발언 요지 | 요구사항, 불만, 인용 가능 여부 |
| 결정 기록 | 결정일, 참여자, 대안, 결론 | 채택 이유, 포기한 대안, 재검토 조건 |

이 표는 메모를 “깔끔한 보고서”로 바꾸기 위한 표가 아닙니다. 원문과 해석을 분리하기 위한 표입니다. LLM위키에서 `raw/`는 당시의 기록이고, `wiki/`는 그 기록을 바탕으로 만든 지식입니다.

**학습자료: 회의록을 위키 지식으로 바꾸는 흐름**

회의 중 메모

raw/meetings에 원문 저장

결정 사항 추출

실행 항목 추출

확인 필요 추출

wiki/meetings 회의 요약

다음 회의 질문

업무 산출물 초안

이 도해에서 `결정 사항`, `실행 항목`, `확인 필요`를 따로 뽑는 이유는 각각 쓰임이 다르기 때문입니다. 결정 사항은 보고서의 근거가 됩니다. 실행 항목은 할 일 목록이 됩니다. 확인 필요는 다음 자료 수집의 출발점이 됩니다.

회의록에는 개인정보, 고객명, 계약 정보, 내부 전략이 들어갈 수 있습니다. 이런 자료는 조직의 보안 기준을 먼저 확인해야 합니다. 위키에 넣을 필요가 없는 개인 정보는 익명화하거나 제외합니다. 회의 녹취나 자동 전사본을 사용할 때도 참석자 동의와 사내 규정을 확인해야 합니다.

### 실습: 회의록 원본과 정리 문서 분리하기

**목표**

회의록 원문을 `raw/meetings`에 보존하고, 결정 사항과 실행 항목을 `wiki/meetings`에 정리합니다.

**실행 전제**

앞의 웹 문서 실습을 실행하지 않았더라도 실행할 수 있습니다. 같은 실습 폴더가 있으면 그 안에 회의록 자료를 추가합니다.

**성공 기준**

회의록 원본 파일과 회의 요약 파일이 분리됩니다. 요약 파일에는 결정 사항, 실행 항목, 확인 필요가 따로 표시됩니다.

```bash
CopyBASE="$HOME/llm-wiki-ch5-2"

mkdir -p "$BASE/raw/meetings" "$BASE/wiki/meetings"

RAW="$BASE/raw/meetings/2026-05-16-weekly-ops.md"
SUMMARY="$BASE/wiki/meetings/2026-05-16-weekly-ops-summary.md"

for target in "$RAW" "$SUMMARY"; do
  if [ -e "$target" ]; then
    echo "이미 파일이 있습니다: $target" >&2
    exit 1
  fi
done

cat > "$RAW" <<'EOF'
# 회의록 원본: 주간 운영 회의

## 메타데이터

- 회의일: 2026-05-16
- 회의명: 주간 운영 회의
- 참석: 제품, 운영, 고객지원
- 기록자: 나
- 자료 성격: 내부 회의 메모

## 원문 메모

- 고객 문의 분류가 늦어져 답변 시간이 길어짐
- 운영팀은 문의 유형을 5개로 나누고 싶어 함
- 고객지원팀은 "긴급", "환불", "기술 문제"를 먼저 구분하면 좋겠다고 함
- 이번 주에는 전체 자동화보다 라벨링 기준부터 맞추기로 함
- 다음 회의 전까지 최근 문의 30개를 보고 라벨 후보를 정리하기
- 개인정보가 섞인 문의 원문은 위키에 그대로 넣지 않기
EOF

cat > "$SUMMARY" <<'EOF'
# 주간 운영 회의 요약

## 한 문장 요약

고객 문의 자동화는 전체 자동화보다 라벨링 기준 정리부터 시작하기로 했다.

## 근거

- 원천 자료: `raw/meetings/2026-05-16-weekly-ops.md`
- 확인 날짜: 2026-05-16
- 자료 성격: 내부 회의 메모

## 결정

- 이번 주에는 전체 자동화가 아니라 문의 라벨링 기준 정리를 우선한다.
- 개인정보가 섞인 문의 원문은 위키에 그대로 넣지 않는다.

## 실행 항목

- 최근 문의 30개를 검토해 라벨 후보를 정리한다.
- 후보 라벨에는 최소한 "긴급", "환불", "기술 문제"를 포함해 검토한다.

## 확인 필요

- 문의 유형을 최종적으로 5개로 고정할지 확인해야 한다.
- 라벨링 기준을 누가 승인할지 확인해야 한다.
EOF

LOG="$BASE/log.md"

if [ ! -f "$LOG" ]; then
  printf '# 처리 이력\n\n' > "$LOG"
fi

printf '%s\n' \
"- 2026-05-16 | ingest | raw/meetings/2026-05-16-weekly-ops.md | 결과: wiki/meetings/2026-05-16-weekly-ops-summary.md | 상태: 결정/실행 항목 분리" \
>> "$LOG"

grep -E "## 결정|## 실행 항목|## 확인 필요" "$SUMMARY"
```

예상 결과는 다음과 같습니다.

```text
Copy## 결정
## 실행 항목
## 확인 필요
```

이 실습을 끝내면 회의록을 다음 질문의 재료로 쓸 수 있습니다. 예를 들어 LLM에게 “최근 회의에서 결정된 라벨링 기준만 근거로 고객 문의 분류표 초안을 만들어 주세요”라고 요청할 수 있습니다. 이때 LLM은 원천 자료와 정리 문서를 함께 참고해야 합니다.

주의할 점도 있습니다. 회의록 요약은 사실처럼 보이지만, 실제로는 원문 메모를 해석한 결과입니다. 그래서 `wiki/meetings` 문서에는 반드시 원천 자료 경로를 남깁니다. 결정이 아니라 의견인 내용은 “확인 필요”에 둡니다.

### LLM에게 맡길 때의 요청 예시

회의록을 LLM 도구에 넣을 때는 “요약해 줘”보다 작업 범위를 좁혀 요청하는 편이 안전합니다. 다음 예시는 Codex나 Claude Code 같은 도구에서 프로젝트 폴더를 열어 두고 사용할 수 있는 요청문입니다.

```text
Copyraw/meetings/2026-05-16-weekly-ops.md만 근거로 사용하세요.

다음 작업을 해 주세요.

1. 회의에서 실제로 결정된 내용만 "결정"으로 정리하세요.
2. 담당자나 기한이 불명확한 항목은 "확인 필요"로 분리하세요.
3. 개인정보나 고객 원문은 새 문서에 복사하지 마세요.
4. 결과는 wiki/meetings/2026-05-16-weekly-ops-summary.md 형식으로 작성하세요.
5. log.md에 처리 이력을 한 줄 추가하세요.

근거가 약한 내용은 단정하지 말고 "확인 필요"로 표시하세요.
```

이 요청문의 목적은 LLM에게 “좋은 글”을 쓰게 하는 것이 아닙니다. 원문과 해석을 나누고, 결정과 추정을 구분하게 하는 것입니다. `AGENTS.md`나 `CLAUDE.md` 같은 지침 파일을 쓰더라도 결과를 보장하지는 않습니다. 지침 파일은 작업 기준을 전달하는 장치이고, 최종 문서는 사람이 확인해야 합니다.

## 처리 이력 남기기

자료를 넣을 때마다 처리 이력을 남겨야 합니다. 처리 이력은 “열심히 정리했다”는 기록이 아닙니다. 나중에 위키 문서가 왜 그렇게 만들어졌는지 추적하기 위한 기록입니다.

LLM위키 패턴에서는 원천 자료와 위키 문서가 분리됩니다. 이 구조는 안전하지만 한 가지 문제가 생깁니다. 시간이 지나면 어떤 원천 자료가 어떤 위키 문서를 만들었는지 헷갈릴 수 있습니다. `log.md`는 이 문제를 줄이는 장치입니다.

처리 이력에는 다음 항목을 남깁니다.

| 항목 | 예 | 쓰임 |
| --- | --- | --- |
| 날짜 | 2026-05-16 | 언제 확인한 자료인지 판단 |
| 작업 | ingest, update, review, lint | 무엇을 했는지 구분 |
| 원천 자료 | `raw/meetings/...` | 원문으로 돌아가기 |
| 결과 문서 | `wiki/meetings/...` | 파생 문서 찾기 |
| 상태 | 초안, 확인 필요, 검토 완료 | 신뢰 수준 판단 |
| 다음 행동 | 승인자 확인, 최신 문서 재확인 | 후속 작업 연결 |

이 표에서 `ingest`는 자료를 넣는 작업을 뜻합니다. 도구마다 실제 명령 이름은 다를 수 있습니다. 중요한 것은 이름이 아니라 기록 습관입니다. 새 자료를 넣었으면 어떤 파일을 근거로 어떤 문서를 만들었는지 남깁니다.

**학습자료: 처리 이력과 검증 흐름**

나중의 질문log.mdwiki 정리 문서raw 원천 자료사용자나중의 질문log.mdwiki 정리 문서raw 원천 자료사용자자료 저장요약과 결정 정리날짜, 원천, 결과, 상태 기록위키 문서 참고처리 이력 확인필요하면 원문 재검증

이 흐름은 번거로워 보이지만, 실제 업무에서는 시간을 줄여 줍니다. 나중에 보고서 문장 하나가 의심스러울 때 `log.md`를 열면 어느 회의록과 웹 문서에서 나온 내용인지 바로 확인할 수 있습니다.

### 실습: 원천 자료가 처리 이력에 남았는지 점검하기

**목표**

`raw/`에 있는 원천 자료가 `log.md`에 언급되어 있는지 확인합니다.

**실행 전제**

앞의 웹 문서 실습이나 회의록 실습 중 하나 이상을 실행한 상태를 권장합니다. Python 3만 있으면 추가 패키지는 필요 없습니다.

**성공 기준**

모든 원천 자료가 `log.md`에 한 번 이상 언급되어 있다는 메시지가 나옵니다.

```bash
CopyBASE="$HOME/llm-wiki-ch5-2" python3 - <<'PY'
import os
import pathlib
import sys

base = pathlib.Path(os.environ["BASE"]).expanduser()
raw_dir = base / "raw"
log_path = base / "log.md"

if not raw_dir.exists():
    print(f"raw 폴더를 찾을 수 없습니다: {raw_dir}")
    sys.exit(1)

if not log_path.exists():
    print(f"log.md를 찾을 수 없습니다: {log_path}")
    sys.exit(1)

raw_files = sorted(p for p in raw_dir.rglob("*") if p.is_file())
log_text = log_path.read_text(encoding="utf-8")

missing = []

for path in raw_files:
    relative = str(path.relative_to(base))
    if relative not in log_text:
        missing.append(relative)

if missing:
    print("로그에 없는 원천 자료:")
    for item in missing:
        print(f"- {item}")
    sys.exit(1)

print(f"확인 완료: 원천 자료 {len(raw_files)}개가 log.md에 언급되어 있습니다.")
PY
```

앞의 두 실습을 모두 실행했다면 예상 결과는 다음과 비슷합니다.

```text
Copy확인 완료: 원천 자료 2개가 log.md에 언급되어 있습니다.
```

이 점검은 단순합니다. 하지만 효과가 큽니다. `raw/`에 자료만 쌓이고 `log.md`에 기록이 없다면 나중에 위키 문서를 믿기 어렵습니다. 반대로 `log.md`가 잘 남아 있으면 원천 자료, 정리 문서, 후속 질문을 연결할 수 있습니다.

### 좋은 처리 이력의 예

처리 이력은 길게 쓰지 않아도 됩니다. 한 줄로 충분한 경우가 많습니다.

```markdown
Copy- 2026-05-16 | ingest | raw/web/2026-05-16-codex-agents-md.md | 결과: wiki/sources/codex-agents-md-source-note.md | 상태: 초안
- 2026-05-16 | ingest | raw/meetings/2026-05-16-weekly-ops.md | 결과: wiki/meetings/2026-05-16-weekly-ops-summary.md | 상태: 결정/실행 항목 분리
- 2026-05-17 | review | wiki/meetings/2026-05-16-weekly-ops-summary.md | 결과: 확인 필요 2건 추가 | 상태: 검토 중
```

이 예시는 세 가지를 알려 줍니다. 어떤 자료가 들어왔는지, 어떤 문서가 만들어졌는지, 아직 무엇이 불확실한지입니다. LLM위키의 신뢰도는 완벽한 요약에서 나오지 않습니다. 근거와 불확실성을 계속 추적하는 습관에서 나옵니다.

## 5.2의 검증 포인트

자료 수집을 마친 뒤에는 다음 항목을 확인합니다.

| 점검 질문 | 통과 기준 |
| --- | --- |
| 원천 자료가 `raw/`에 남아 있는가 | 웹 문서, 회의록, 메모의 원본 또는 원천 카드가 있다 |
| 정리 문서가 `wiki/`에 따로 있는가 | 원문과 요약이 같은 파일에 뒤섞이지 않는다 |
| 확인 날짜가 있는가 | 웹 문서와 업무 메모에 확인 날짜가 있다 |
| 출처 경로가 남아 있는가 | 정리 문서에서 `raw/...` 경로로 돌아갈 수 있다 |
| 결정과 추정이 구분되어 있는가 | 결정, 실행 항목, 확인 필요가 따로 표시된다 |
| 처리 이력이 있는가 | `log.md`에 원천 자료와 결과 문서가 연결되어 있다 |

이 절의 목표는 많은 자료를 넣는 것이 아닙니다. 나중에 다시 믿고 쓸 수 있는 자료를 넣는 것입니다. 웹 문서 한 개와 회의록 한 개라도 원천 자료, 정리 문서, 처리 이력이 연결되어 있으면 좋은 시작입니다.
