# 4.2 위키 초기화하기

![4.2 위키 초기화하기 삽화](https://static.wikidocs.net/images/page/353391/4.2-%EC%9C%84%ED%82%A4-%EC%B4%88%EA%B8%B0%ED%99%94%ED%95%98%EA%B8%B0.jpg)

첫 위키의 목적은 거창한 지식베이스를 만드는 것이 아닙니다. 다음에 같은 주제로 LLM에게 질문할 때, 원본 자료와 정리된 지식과 작업 규칙이 한곳에 남아 있게 만드는 것입니다.

이번 절에서는 “업무 자동화”라는 작은 주제로 빈 LLM위키를 초기화합니다. 실습이 끝나면 `raw/`, `wiki/`, `output/`, `AGENTS.md`, `index.md`, `log.md`가 있는 최소 구조가 생깁니다.

## 기본 폴더 만들기

LLM위키는 원본과 정리 문서를 섞지 않는 데서 시작합니다. Karpathy의 LLM Wiki 아이디어 문서는 원천 자료, 위키, 스키마 또는 지침을 나누어 설명합니다. 이 책에서는 초보자가 따라 하기 쉬운 형태로 `raw/`, `wiki/`, `output/`, 규칙 파일을 사용합니다.

| 위치 | 역할 | 처음 넣을 내용 |
| --- | --- | --- |
| `raw/` | 원본 자료 보관 | 회의록, 메모, 웹 문서 저장본 |
| `wiki/` | LLM이 정리한 문서 | 개념 정리, 질문별 답변, 요약 |
| `output/` | 업무 산출물 | 보고서, 실행 계획, 공유용 초안 |
| `index.md` | 위키 안내판 | 문서 목록, 주요 질문 |
| `log.md` | 처리 이력 | 언제 무엇을 넣고 바꿨는지 |
| `AGENTS.md` | 작업 규칙 | Codex 등 LLM 도구가 참고할 규칙 |

이 표에서 가장 중요한 구분은 `raw/`와 `wiki/`입니다. `raw/`는 기준점입니다. 원본을 고치면 나중에 어떤 내용이 사실이었는지 확인하기 어렵습니다. 반대로 `wiki/`는 계속 다듬어도 됩니다. LLM이 읽기 좋게 바꾸고, 링크를 추가하고, 확인 필요 항목을 정리하는 공간입니다.

### 실습: 최소 위키 폴더 만들기

**목표**

첫 주제 위키의 빈 구조를 만듭니다.

**실행 전제**

macOS, Linux, WSL, Git Bash처럼 `mkdir`, `printf`, `find` 명령을 사용할 수 있는 환경을 가정합니다.

**성공 기준**

`work-automation-wiki` 폴더 아래에 `raw/`, `wiki/`, `output/`, `index.md`, `log.md`가 만들어집니다.

```bash
CopyBASE="$HOME/work-automation-wiki"

if [ -e "$BASE" ]; then
  echo "이미 실습 폴더가 있습니다. BASE 값을 바꾸고 다시 실행하세요." >&2
  exit 1
fi

mkdir -p "$BASE/raw/meeting-notes"
mkdir -p "$BASE/wiki/concepts"
mkdir -p "$BASE/output"

printf '%s\n' \
'# 업무 자동화 위키' \
'' \
'## 이 위키의 질문' \
'' \
'- 반복 업무를 LLM으로 줄이려면 무엇부터 정리해야 할까?' \
'- 회의록에서 실행 항목을 안정적으로 뽑으려면 어떤 기준이 필요할까?' \
'' \
'## 문서 목록' \
'' \
'- 아직 없음' \
> "$BASE/index.md"

printf '%s\n' \
'# 처리 이력' \
'' \
'| 날짜 | 작업 | 근거 |' \
'|---|---|---|' \
'| YYYY-MM-DD | 위키 초기화 | 4.2 실습 |' \
> "$BASE/log.md"

find "$BASE" -maxdepth 3 -print | sed "s|$BASE|.|" | sort
```

예상 결과는 다음과 비슷합니다.

```text
Copy.
./index.md
./log.md
./output
./raw
./raw/meeting-notes
./wiki
./wiki/concepts
```

이 실습은 아직 LLM을 쓰지 않습니다. 먼저 사람이 봐도 이해되는 구조를 만드는 단계입니다. 다음 절에서 자료를 넣거나 질문을 던질 때, 이 폴더 구조가 기준선이 됩니다.

원본 자료

raw/

wiki/

output/

AGENTS.md 또는 CLAUDE.md

이 흐름에서 `raw/`는 출발점이고 `output/`은 결과물입니다. `wiki/`는 그 사이에서 지식을 다시 쓰기 좋게 정리하는 층입니다. 규칙 파일은 LLM에게 “어떤 기준으로 읽고 써야 하는가”를 알려 줍니다.

## 작업 규칙 파일 작성하기

폴더만 만들면 LLM은 이 위키를 어떻게 다뤄야 하는지 모릅니다. 그래서 작업 규칙 파일을 둡니다. Codex에서는 공식 문서 기준으로 `AGENTS.md`가 프로젝트 지침 파일로 쓰입니다. Claude Code에서는 `CLAUDE.md`가 프로젝트 메모리 파일로 쓰입니다.

다만 이런 파일은 LLM의 행동을 강제로 보장하지 않습니다. 규칙을 따르도록 유도하는 장치입니다. 결과가 규칙대로 나왔는지는 사용자가 확인해야 합니다.

| 사용하는 도구 | 기본 규칙 파일 | 이 절에서의 권장 방식 |
| --- | --- | --- |
| OpenAI Codex | `AGENTS.md` | 프로젝트 루트에 `AGENTS.md` 작성 |
| Claude Code | `CLAUDE.md` | 필요하면 `CLAUDE.md`에서 `AGENTS.md`를 가져오기 |
| 일반 Markdown 방식 | 정해진 파일 없음 | `AGENTS.md`를 운영 규칙 문서로 사용 |

도구를 하나만 쓰더라도, 처음에는 `AGENTS.md`부터 만드는 편이 좋습니다. 사람이 읽는 운영 규칙으로도 쓸 수 있고, Codex 같은 도구에서 그대로 참고할 수 있기 때문입니다.

### 실습: AGENTS.md 작성하기

**목표**

LLM이 이 위키를 다룰 때 지켜야 할 최소 규칙을 적습니다.

**실행 전제**

앞의 실습에서 만든 `$HOME/work-automation-wiki` 폴더가 있어야 합니다.

**성공 기준**

프로젝트 루트에 `AGENTS.md`가 생기고, 원본 보존, 출처 표기, 확인 필요 표시 규칙이 들어갑니다.

```bash
CopyBASE="$HOME/work-automation-wiki"

test -d "$BASE" || {
  echo "먼저 기본 폴더 만들기 실습을 실행하세요." >&2
  exit 1
}

cat > "$BASE/AGENTS.md" <<'EOF'
# LLM위키 작업 규칙

## 기본 원칙

- `raw/` 안의 원본 자료는 임의로 수정하지 않는다.
- 정리된 문서는 `wiki/` 아래에 Markdown으로 작성한다.
- 공유하거나 제출할 산출물은 `output/` 아래에 둔다.
- 새 문서에는 근거 파일, 확인 날짜, 확인 필요 항목을 남긴다.
- 근거가 부족한 내용은 단정하지 않고 "확인 필요"로 표시한다.

## 문서 작성 형식

위키 문서는 가능하면 다음 흐름으로 작성한다.

1. 한 문장 요약
2. 근거
3. 확인된 내용
4. 확인 필요
5. 다시 물어볼 질문

## 이 위키의 주제

이 위키는 개인 또는 소규모 팀의 반복 업무 자동화를 다룬다.
첫 실습 범위는 회의록 정리와 실행 항목 추출이다.
EOF
```

작성된 규칙 파일의 핵심은 “무엇을 만들 것인가”보다 “무엇을 섞지 않을 것인가”입니다. 첫 위키에서 자주 생기는 문제는 원본, 요약, 보고서 초안이 한 문서에 뒤섞이는 것입니다. `AGENTS.md`는 이 혼란을 줄이는 기준표 역할을 합니다.

Claude Code를 쓴다면 다음처럼 `CLAUDE.md`를 추가할 수 있습니다.

```bash
CopyBASE="$HOME/work-automation-wiki"

cat > "$BASE/CLAUDE.md" <<'EOF'
@AGENTS.md

## Claude Code 추가 규칙

- 이 프로젝트에서는 `AGENTS.md`의 LLM위키 작업 규칙을 따른다.
- `raw/` 원본을 바꾸기 전에 반드시 사용자에게 확인한다.
- 위키 문서에는 근거 파일명과 확인 날짜를 남긴다.
EOF
```

`CLAUDE.md` 예시는 Claude Code 사용자를 위한 선택 사항입니다. Codex만 쓰거나 일반 Markdown 편집기만 쓴다면 없어도 됩니다. 중요한 것은 하나의 프로젝트 안에서 LLM과 사람이 같은 작업 기준을 보게 만드는 것입니다.

## 생성된 구조 확인하기

초기화의 마지막 단계는 확인입니다. 위키는 처음부터 복잡하지 않아도 됩니다. 대신 “다음 작업을 시작해도 길을 잃지 않는가”를 확인해야 합니다.

예

아니오

예

아니오

예

아니오

위키 초기화 확인

원본과 정리 문서가 분리됐는가

작업 규칙이 있는가

raw/와 wiki/를 다시 분리

찾아갈 입구가 있는가

AGENTS.md 또는 CLAUDE.md 작성

첫 자료 입력 준비 완료

index.md와 log.md 보완

이 도해는 폴더가 “존재하는가”만 보지 않습니다. 원본을 보존할 수 있는지, LLM에게 작업 기준을 줄 수 있는지, 사람이 다시 찾을 수 있는지를 함께 확인합니다.

### 실습: 구조 점검 명령 실행하기

**목표**

초기화한 위키가 다음 실습을 시작할 수 있는 상태인지 확인합니다.

**실행 전제**

앞의 두 실습을 모두 실행했다고 가정합니다.

**성공 기준**

필수 폴더와 파일이 모두 확인되고, `AGENTS.md`에서 핵심 규칙을 찾을 수 있습니다.

```bash
CopyBASE="$HOME/work-automation-wiki"

for path in \
  "$BASE/raw" \
  "$BASE/wiki" \
  "$BASE/output" \
  "$BASE/index.md" \
  "$BASE/log.md" \
  "$BASE/AGENTS.md"
do
  if [ -e "$path" ]; then
    echo "OK: ${path#$BASE/}"
  else
    echo "MISSING: ${path#$BASE/}"
  fi
done

printf '\n규칙 확인:\n'
grep -n "raw/.*수정하지 않는다\|확인 필요\|근거" "$BASE/AGENTS.md"
```

예상 결과는 다음과 비슷합니다.

```text
CopyOK: raw
OK: wiki
OK: output
OK: index.md
OK: log.md
OK: AGENTS.md

규칙 확인:
5:- `raw/` 안의 원본 자료는 임의로 수정하지 않는다.
9:- 새 문서에는 근거 파일, 확인 날짜, 확인 필요 항목을 남긴다.
10:- 근거가 부족한 내용은 단정하지 않고 "확인 필요"로 표시한다.
```

`MISSING`이 나온다면 해당 폴더나 파일을 다시 만듭니다. `grep` 결과가 비어 있다면 규칙 파일에 원본 보존, 근거, 확인 필요 문구가 들어 있는지 확인합니다.

마지막으로 현재 구조를 사람이 읽기 좋은 형태로 확인합니다.

```bash
CopyBASE="$HOME/work-automation-wiki"

find "$BASE" -maxdepth 3 -print | sed "s|$BASE|work-automation-wiki|" | sort
```

예상 결과는 다음과 비슷합니다.

```text
Copywork-automation-wiki
work-automation-wiki/AGENTS.md
work-automation-wiki/CLAUDE.md
work-automation-wiki/index.md
work-automation-wiki/log.md
work-automation-wiki/output
work-automation-wiki/raw
work-automation-wiki/raw/meeting-notes
work-automation-wiki/wiki
work-automation-wiki/wiki/concepts
```

`CLAUDE.md`는 선택 파일입니다. Claude Code를 쓰지 않는다면 없어도 됩니다. 반대로 Claude Code를 쓴다면 `CLAUDE.md`가 `AGENTS.md`를 가져오도록 만들어 두면 두 도구의 규칙을 맞추기 쉽습니다.

## 정리와 검증 포인트

이번 절에서 만든 것은 빈 폴더가 아니라 첫 위키의 운영 기준입니다. 이제 원본은 `raw/`에 남기고, 정리 문서는 `wiki/`에 만들고, 업무 산출물은 `output/`에 둘 수 있습니다.

검증할 항목은 다음과 같습니다.

| 점검 항목 | 확인 방법 |
| --- | --- |
| 원본 보관 위치가 있는가 | `raw/` 폴더가 있다 |
| 정리 문서 위치가 있는가 | `wiki/` 폴더가 있다 |
| 결과물 위치가 있는가 | `output/` 폴더가 있다 |
| 위키 입구가 있는가 | `index.md`가 있다 |
| 작업 이력이 남는가 | `log.md`가 있다 |
| LLM 작업 기준이 있는가 | `AGENTS.md` 또는 `CLAUDE.md`가 있다 |
| 근거 부족 표현이 정해졌는가 | 규칙 파일에 “확인 필요”가 있다 |

이 실습을 끝내면 다음 작업에서 LLM에게 프로젝트 구조를 길게 설명하지 않아도 됩니다. 대신 위키 폴더를 열고, 규칙 파일을 기준으로 첫 자료를 넣으면 됩니다.
