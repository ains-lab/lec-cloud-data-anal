# 4.3 첫 질문으로 방향 잡기

![4.3 첫 질문으로 방향 잡기 삽화](https://static.wikidocs.net/images/page/353392/4.3-%EC%B2%AB-%EC%A7%88%EB%AC%B8%EC%9C%BC%EB%A1%9C-%EB%B0%A9%ED%96%A5-%EC%9E%A1%EA%B8%B0.jpg)

첫 위키를 만들었는데 무엇부터 물어봐야 할지 막히는 순간이 옵니다. 이때 좋은 질문은 단순히 “요약해 줘”가 아닙니다. 첫 질문은 위키의 방향을 잡는 나침반입니다.

이번 절에서는 업무에서 떠오르는 막연한 질문을 위키가 답할 수 있는 질문으로 바꿉니다. 그다음 초기 답변을 만들고, 답변이 비어 있는 지점을 이용해 다음에 모을 자료를 찾습니다.

## 업무 질문을 위키 질문으로 바꾸기

업무 질문은 보통 넓고 애매합니다. 예를 들어 “반복 업무를 줄이려면 어떻게 해야 할까?”는 좋은 출발점이지만, 첫 위키 질문으로는 범위가 큽니다. LLM은 그럴듯한 일반론을 답할 수 있습니다. 하지만 그 답이 내 업무에 맞는지는 확인하기 어렵습니다.

위키 질문은 조금 다릅니다. 위키 안에 있는 자료를 기준으로 답하게 만듭니다. “내가 가진 회의록과 업무 메모 기준으로, 반복되는 업무는 무엇이고 어떤 기준으로 우선순위를 정할 수 있는가?”처럼 묻습니다.

이렇게 바꾸면 질문의 초점이 세 가지로 좁아집니다.

- 어떤 자료를 기준으로 답할 것인가
- 어떤 결정을 돕는 답이어야 하는가
- 답변 뒤에 무엇을 더 확인해야 하는가

Karpathy의 LLM Wiki 아이디어는 원천 자료, 정리된 위키, 스키마 또는 작업 규칙을 구분합니다. 이 절에서는 그중 `raw`와 `wiki`를 함께 사용합니다. 원천 자료는 기준점이고, 위키 문서는 질문에 다시 쓰기 좋게 정리한 지식입니다.

### 학습자료: 업무 질문을 위키 질문으로 바꾸는 흐름

막연한 업무 질문

자료 기준 붙이기

결정 목적 붙이기

답변 형식 붙이기

검증 요청 붙이기

반복 업무를 줄이려면?

회의록과 업무 메모 기준으로

우선순위를 정하기 위해

표로 정리하고

근거와 확인 필요를 나눠 달라

이 흐름의 핵심은 질문을 더 길게 만드는 것이 아닙니다. 답변이 어디에서 왔는지 확인할 수 있게 만드는 것입니다.

좋은 위키 질문은 LLM에게 “생각해 봐”라고만 말하지 않습니다. “이 자료를 기준으로, 이 결정을 돕도록, 이 형식으로, 불확실한 부분을 표시해서 답하라”고 요청합니다.

### 실습: 첫 질문 후보 만들기

**목표**

업무 질문 하나를 LLM위키에 던질 수 있는 질문으로 바꿉니다.

**실행 전제**

4.1과 4.2에서 작은 주제 위키를 만들었다고 가정합니다. 예시는 “업무 자동화 위키”입니다. 아직 자료가 많지 않아도 괜찮습니다. 회의록 1개, 업무 메모 1개 정도면 시작할 수 있습니다.

**성공 기준**

질문에 자료 기준, 결정 목적, 답변 형식, 검증 요청이 들어갑니다.

```markdown
Copy| 항목 | 작성 예 |
|---|---|
| 막연한 업무 질문 | 반복 업무를 줄이려면 무엇부터 해야 할까? |
| 자료 기준 | `raw/meeting-notes/`와 `wiki/`에 있는 현재 자료 기준 |
| 결정 목적 | 다음 주에 자동화 후보 1개를 고르기 위해 |
| 답변 형식 | 업무명, 반복 빈도, 예상 효과, 근거, 확인 필요를 표로 정리 |
| 검증 요청 | 근거가 없는 추정은 `확인 필요`로 표시 |
```

위 표를 채우면 질문은 다음처럼 바뀝니다.

```text
Copy현재 위키의 `raw/meeting-notes/`와 `wiki/` 문서를 기준으로,
다음 주에 자동화 후보 1개를 고르려고 합니다.

반복되는 업무를 찾아서 다음 항목으로 표로 정리해 주세요.

- 업무명
- 반복되는 이유
- 자동화했을 때 기대 효과
- 근거가 되는 원천 자료 또는 위키 문서
- 아직 확인이 필요한 내용

근거가 부족한 내용은 단정하지 말고 `확인 필요`로 표시해 주세요.
```

이 질문은 “무엇을 자동화할까?”보다 길지만, 더 실용적입니다. 답변이 바로 다음 행동으로 이어지고, 부족한 자료도 함께 드러납니다.

## 초기 답변 만들기

첫 질문의 목적은 완벽한 답을 얻는 것이 아닙니다. 첫 답변으로 위키의 현재 상태를 확인하는 것입니다. 답변이 얕다면 자료가 부족한 것입니다. 답변이 넓고 산만하다면 질문이 아직 넓은 것입니다. 답변에 근거가 없다면 위키 문서의 출처 연결이 약한 것입니다.

초기 답변은 세 부분으로 받는 편이 좋습니다.

1. 현재 자료로 확인된 내용
2. 제한된 근거로 추정한 내용
3. 답하기 위해 더 필요한 자료

이 세 부분을 나누면 답변을 그대로 믿지 않아도 됩니다. 위키가 이미 아는 것과 아직 모르는 것을 구분할 수 있습니다.

### 학습자료: 초기 답변의 권장 구조

| 구역 | 들어갈 내용 | 좋은 답변의 조건 |
| --- | --- | --- |
| 확인된 내용 | 원천 자료나 위키 문서로 뒷받침되는 내용 | 파일명, 문서명, 확인 날짜가 함께 남는다 |
| 제한된 추정 | 자료가 적지만 가능성이 있는 해석 | “추정”, “가능성”, “확인 필요”가 표시된다 |
| 추가 자료 | 더 나은 답변을 위해 필요한 자료 | 다음 수집 행동으로 바꿀 수 있다 |

이 표는 답변을 평가하는 기준입니다. 처음부터 모든 칸이 풍성할 필요는 없습니다. 오히려 빈칸이 보여야 다음 작업이 쉬워집니다.

LLM위키의 중요한 장점은 답변을 일회성으로 버리지 않는 데 있습니다. 초기 답변에서 확인된 내용은 `wiki/` 문서에 반영할 수 있습니다. 확인이 필요한 내용은 `log.md`나 별도 작업 목록에 남깁니다.

### 실습: 초기 답변 요청하기

**목표**

위키를 기준으로 첫 답변을 만들고, 확인된 내용과 확인 필요를 분리합니다.

**실행 전제**

LLM 도구가 현재 위키 폴더를 읽을 수 있어야 합니다. Codex에서는 `AGENTS.md`, Claude Code에서는 `CLAUDE.md` 같은 작업 규칙 파일이 있으면 더 좋습니다. 단, 이런 지침 파일은 행동을 보장하지 않습니다. 결과는 사용자가 확인해야 합니다.

**성공 기준**

답변에 `확인된 내용`, `제한된 추정`, `추가로 필요한 자료`가 분리되어 있습니다.

```text
Copy현재 위키를 기준으로 다음 질문에 답해 주세요.

질문:
다음 주에 가장 먼저 자동화해 볼 만한 반복 업무는 무엇인가?

답변 형식:
1. 확인된 내용
2. 제한된 추정
3. 추가로 필요한 자료
4. 다음 질문 3개

규칙:
- `raw/` 원천 자료나 `wiki/` 문서에서 확인되는 내용만 `확인된 내용`에 넣어 주세요.
- 근거가 약한 내용은 `제한된 추정`에 넣어 주세요.
- 출처가 없는 단정은 하지 마세요.
```

예상되는 답변은 다음과 비슷한 형태입니다.

```markdown
Copy## 확인된 내용

- 회의록 정리 업무가 반복해서 등장합니다.
- 실행 항목을 담당자, 기한, 확인 방법으로 나누는 형식이 여러 메모에서 반복됩니다.
- 근거: `raw/meeting-notes/2026-05-10.md`, `wiki/meeting-summary-rule.md`

## 제한된 추정

- 회의록 정리는 자동화 후보일 가능성이 있습니다.
- 다만 실제 소요 시간 기록이 없어 기대 효과는 아직 추정입니다.

## 추가로 필요한 자료

- 최근 4주 동안 회의록 정리에 걸린 시간
- 회의록을 검토하는 사람의 수정 요청 사례
- 자동화해도 사람이 반드시 확인해야 하는 항목

## 다음 질문

1. 회의록 정리에서 반복되는 출력 형식은 무엇인가?
2. 자동화하면 안 되는 판단 항목은 무엇인가?
3. 다음 주에 30분 안에 검증할 수 있는 자동화 실험은 무엇인가?
```

이 답변에서 가장 중요한 부분은 “회의록 정리가 자동화 후보”라는 결론이 아닙니다. 더 중요한 것은 “소요 시간 기록이 없다”는 빈틈입니다. 이 빈틈이 다음 자료 수집 방향을 알려 줍니다.

## 부족한 자료를 역으로 찾기

첫 답변을 받으면 바로 다음 질문으로 넘어가고 싶어집니다. 하지만 LLM위키를 키우는 데 더 좋은 습관은 답변을 거꾸로 읽는 것입니다. 답변에서 근거가 약한 문장, 추정으로 표시된 문장, 확인 필요로 남은 항목을 찾습니다. 그리고 그 항목을 다음에 넣을 자료 목록으로 바꿉니다.

이 작업을 “역방향 자료 찾기”라고 부를 수 있습니다. 질문에서 답을 얻고 끝나는 것이 아니라, 답변의 빈틈에서 다음 자료를 찾는 방식입니다.

예를 들어 초기 답변에 “회의록 정리는 자동화 효과가 클 가능성이 있다”라고 나왔다면 바로 믿으면 안 됩니다. 다음처럼 되물어야 합니다.

- 효과가 크다는 근거가 있는가?
- 반복 빈도를 보여 주는 자료가 있는가?
- 사람이 수정한 사례가 남아 있는가?
- 자동화하면 안 되는 예외 조건이 있는가?

이 질문에 답할 자료가 없다면 위키는 아직 그 결론을 강하게 말할 수 없습니다.

### 학습자료: 답변의 빈틈을 자료 목록으로 바꾸기

| 초기 답변의 문장 | 위험 신호 | 필요한 자료 | 다음 행동 |
| --- | --- | --- | --- |
| 회의록 정리는 자동화 효과가 클 가능성이 있다 | 효과 근거가 없음 | 최근 회의록 정리 소요 시간 | 3회분 작업 시간을 기록한다 |
| 실행 항목 형식이 반복된다 | 반복 빈도 근거가 약함 | 회의록 3~5개 | 최근 회의록을 `raw/meeting-notes/`에 추가한다 |
| 검토자가 자주 수정한다 | 수정 사례가 없음 | 검토 코멘트, 수정 이력 | 수정 요청 5개를 메모로 남긴다 |
| 자동화 후보 1순위다 | 다른 후보와 비교 없음 | 후보별 빈도, 영향, 난이도 | 비교표를 만든다 |

이 표는 LLM의 답변을 반박하기 위한 도구가 아닙니다. 위키를 더 쓸모 있게 키우기 위한 도구입니다. 좋은 답변은 결론만 주지 않습니다. 다음에 무엇을 모아야 하는지도 알려 줍니다.

### 실습: 자료 보강 목록 만들기

**목표**

초기 답변에서 확인 필요 항목을 뽑아 다음 자료 수집 목록으로 바꿉니다.

**실행 전제**

앞 실습에서 받은 초기 답변이 있어야 합니다. 실제 답변이 없다면 위의 예상 답변을 예시로 사용해도 됩니다.

**성공 기준**

확인 필요 항목마다 필요한 자료와 저장 위치가 정해집니다.

```markdown
Copy| 확인 필요 항목 | 필요한 자료 | 저장 위치 | 우선순위 |
|---|---|---|---|
| 회의록 정리에 걸리는 시간 | 최근 3회 작업 시간 기록 | `raw/work-logs/` | 높음 |
| 검토자가 자주 고치는 부분 | 수정 요청 사례 5개 | `raw/review-comments/` | 높음 |
| 자동화하면 안 되는 항목 | 사람이 판단해야 하는 예외 목록 | `wiki/automation-boundaries.md` | 중간 |
| 다른 자동화 후보와 비교 | 후보별 빈도, 영향, 난이도 표 | `wiki/automation-candidates.md` | 중간 |
```

이 표를 만들면 다음 작업이 분명해집니다. 이제 LLM에게 “더 생각해 봐”라고 요청할 필요가 줄어듭니다. 대신 “이 자료를 추가했으니 다시 판단해 달라”고 요청할 수 있습니다.

### 실습: 다음 질문으로 연결하기

**목표**

부족한 자료 목록을 바탕으로 두 번째 질문을 만듭니다.

**실행 전제**

아직 자료를 실제로 추가하지 않아도 됩니다. 지금은 질문 형태를 만드는 연습입니다.

**성공 기준**

두 번째 질문이 첫 답변의 부족한 근거를 직접 겨냥합니다.

```text
Copy초기 답변에서 회의록 정리 업무의 자동화 효과는 `확인 필요`로 표시되었습니다.

다음 자료를 추가로 모으려고 합니다.

- 최근 3회 회의록 정리에 걸린 시간
- 검토자가 수정한 사례 5개
- 사람이 반드시 판단해야 하는 예외 조건

이 자료를 모으면 자동화 우선순위를 판단할 수 있는지 평가해 주세요.
부족하다면 어떤 자료가 더 필요한지도 알려 주세요.
```

이 질문은 첫 질문보다 좁습니다. 이제 위키는 일반적인 자동화 조언이 아니라, “회의록 정리 자동화가 첫 실험으로 적합한가”라는 구체적인 판단을 돕게 됩니다.

## 4.3의 검증 포인트

첫 질문을 잘 만들었는지는 답변의 멋진 문장으로 판단하지 않습니다. 다음 기준으로 확인합니다.

| 점검 항목 | 확인 질문 |
| --- | --- |
| 자료 기준 | 질문에 `raw/` 또는 `wiki/` 기준이 들어 있는가? |
| 결정 목적 | 답변이 어떤 결정을 돕는지 분명한가? |
| 답변 형식 | 표, 목록, 비교 기준처럼 재사용 가능한 형식이 있는가? |
| 근거 표시 | 확인된 내용과 추정이 나뉘어 있는가? |
| 다음 자료 | 부족한 자료가 다음 행동으로 바뀌었는가? |

이 절을 마치면 첫 위키는 단순한 메모 묶음이 아닙니다. 질문을 받고, 현재 아는 것을 답하고, 모르는 것을 드러내는 작은 지식 시스템이 됩니다.
