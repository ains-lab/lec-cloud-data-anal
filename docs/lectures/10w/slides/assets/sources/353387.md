# 3.2 도구를 고를 때 확인할 것

![3.2 도구를 고를 때 확인할 것 삽화](https://static.wikidocs.net/images/page/353387/3.2-%EB%8F%84%EA%B5%AC%EB%A5%BC-%EA%B3%A0%EB%A5%BC-%EB%95%8C-%ED%99%95%EC%9D%B8%ED%95%A0-%EA%B2%83.jpg)

LLM위키 도구를 고를 때 가장 먼저 볼 것은 기능 목록이 아닙니다. 이번 주에 자료 하나를 넣고, 위키 문서 하나를 만들고, 다음 작업에서 다시 믿고 쓸 수 있는지가 더 중요합니다.

LLM위키는 2026년 5월 조사 기준으로 단일 표준 제품이라기보다 지식 관리 패턴에 가깝습니다. 구현체마다 설치 방법, 저장 위치, 지원 자료 형식, 명령 이름이 다릅니다. 그래서 도구를 고를 때는 “무엇을 많이 할 수 있는가”보다 “내가 계속 관리할 수 있는가”를 먼저 확인해야 합니다.

> 이 절의 도구와 버전 설명은 2026-05-16 KST에 확인한 자료를 기준으로 합니다. LLM위키 구현체는 빠르게 바뀌므로, 실제 설치 전에는 각 도구의 README, Releases, Changelog, 설치된 도구의 도움말을 다시 확인해야 합니다.

## 설치 난이도와 유지보수 부담

도구 설치는 한 번만 해결하면 되는 문제처럼 보입니다. 하지만 LLM위키에서는 설치 뒤의 부담이 더 중요합니다. 플러그인을 켜야 하는지, API 키가 필요한지, Python이나 Node.js 버전을 맞춰야 하는지, 업그레이드할 때 명령이 바뀌는지 확인해야 합니다.

첫 도구는 작게 시작할 수 있어야 합니다. LLM 도구를 가볍게 써 본 독자라면, 하루 종일 설치하다가 지치는 도구보다 30분 안에 샘플 자료 하나를 넣어 볼 수 있는 방식이 좋습니다. 첫 위키가 작으면 나중에 도구를 바꾸기도 쉽습니다.

**학습자료: 시작 방식별 부담 비교**

| 방식 | 시작 부담 | 유지보수 부담 | 잘 맞는 경우 | 먼저 확인할 것 |
| --- | --- | --- | --- | --- |
| 수동 Markdown | 낮음 | 낮음 | 폴더와 문서를 직접 관리하고 싶은 경우 | 원본과 위키 문서를 분리할 수 있는가 |
| Claude Code/Codex 기반 방식 | 중간 | 중간 | 이미 에이전트 도구를 쓰는 경우 | 지침 파일, 플러그인 권한, 저장 위치 |
| CLI 도구 | 중간~높음 | 중간~높음 | 명령줄과 API 키 관리에 익숙한 경우 | Python/Node.js 버전, API 키, 릴리스 노트 |
| 데스크톱 앱 | 낮음~중간 | 낮음~중간 | GUI에서 시작하고 싶은 경우 | 내보내기, 백업, 원본 보존 |
| 연구·실험 구현체 | 높음 | 높음 | 새 방식을 실험하려는 경우 | 문서 최신성, 한계, 변경 이력 |

이 표는 도구의 순위를 정하는 표가 아닙니다. 내 조건에서 실패할 가능성이 낮은 방식을 찾기 위한 표입니다. 터미널이 낯설다면 CLI 도구는 뒤로 미뤄도 됩니다. 반대로 반복 수집과 점검을 자주 해야 한다면 수동 Markdown만으로는 곧 한계를 느낄 수 있습니다.

### 첫 도구의 최소 조건

첫 LLM위키 도구는 다음 세 가지를 만족하면 충분합니다.

1. 원천 자료와 정리된 위키 문서를 구분해 저장할 수 있습니다.
2. 생성된 위키 문서를 사람이 직접 열어 고칠 수 있습니다.
3. 공식 문서와 변경 이력을 확인할 수 있습니다.

이 조건이 약하면 나중에 문제가 생깁니다. 원천 자료와 요약이 섞이면 근거를 잃습니다. 사람이 문서를 고칠 수 없으면 LLM이 만든 오류를 바로잡기 어렵습니다. 변경 이력을 찾을 수 없으면 오래된 명령을 따라 하게 됩니다.

**학습자료: 첫 도구 선택 체크리스트**

| 확인 항목 | 예 | 아니오 |
| --- | --- | --- |
| 오늘 30분 안에 샘플 자료 하나를 넣어 볼 수 있다 |  |  |
| 원본 자료가 따로 남는다 |  |  |
| 위키 문서가 Markdown처럼 사람이 읽을 수 있는 형식이다 |  |  |
| 저장 위치를 확인할 수 있다 |  |  |
| 공식 README가 있다 |  |  |
| Releases 또는 Changelog가 있다 |  |  |
| 권한과 네트워크 호출 범위를 설명할 수 있다 |  |  |

`예`가 5개보다 적으면 바로 도구를 도입하지 않아도 됩니다. 수동 Markdown 방식으로 먼저 시작해도 LLM위키의 핵심은 배울 수 있습니다. 핵심은 도구가 아니라 원본을 보존하고, 정리된 지식을 갱신하고, 답변의 근거를 확인하는 흐름입니다.

### 실습: 30분 검증용 위키 만들기

**목표**

도구를 설치하기 전에, 내가 기대하는 최소 구조가 무엇인지 직접 확인합니다.

**실행 전제**

macOS, Linux, WSL, Git Bash처럼 Bash 계열 셸을 사용할 수 있어야 합니다. 같은 이름의 폴더가 있으면 예제 파일이 덮어써질 수 있습니다.

**성공 기준**

`raw`, `wiki`, `output`이 분리되고, 사람이 읽을 수 있는 Markdown 파일이 만들어집니다.

```bash
CopyBASE="$HOME/llm-wiki-tool-check"

mkdir -p "$BASE/raw" "$BASE/wiki/concepts" "$BASE/output"

printf '%s\n' \
'# 회의록 샘플' \
'' \
'팀은 매주 회의록에서 실행 항목을 다시 정리한다.' \
'다음 실험 후보는 회의록 액션 아이템 초안 만들기다.' \
> "$BASE/raw/meeting-sample.md"

printf '%s\n' \
'# 회의록 자동화 후보' \
'' \
'## 한 문장 요약' \
'' \
'회의록에서 실행 항목을 뽑아 담당자, 기한, 확인 방법으로 정리하는 흐름을 실험한다.' \
'' \
'## 근거' \
'' \
'- 원천 자료: raw/meeting-sample.md' \
'- 확인 날짜: 2026-05-16' \
'' \
'## 확인 필요' \
'' \
'- 실제 회의록 예시 3개에서 같은 형식이 반복되는지 확인해야 한다.' \
> "$BASE/wiki/concepts/meeting-action-items.md"

find "$BASE" -maxdepth 3 -type f | sort
```

예상 결과는 다음과 비슷합니다.

```text
Copy/Users/사용자명/llm-wiki-tool-check/raw/meeting-sample.md
/Users/사용자명/llm-wiki-tool-check/wiki/concepts/meeting-action-items.md
```

이 실습은 특정 도구의 기능을 검증하는 예제가 아닙니다. 좋은 도구가 최소한 어떤 구조를 만들어야 하는지 미리 보는 예제입니다. 나중에 플러그인이나 CLI 도구를 써도 이 기준은 그대로 사용할 수 있습니다.

## 자료 형식과 지원 범위

LLM위키는 자료를 넣고, 정리하고, 다시 질문하는 흐름으로 움직입니다. 따라서 도구가 어떤 자료를 안정적으로 다루는지 확인해야 합니다. 개인 업무 자료는 보통 Markdown, 텍스트 메모, 웹 문서, PDF, 회의록, 코드 작업 기록, 이미지가 섞여 있습니다.

여기서 중요한 것은 “파일을 가져올 수 있는가”만이 아닙니다. 가져온 자료의 출처를 남기는지, 나중에 답변에서 그 출처로 돌아갈 수 있는지가 더 중요합니다. LLM위키에서 자료 지원은 단순 업로드 기능이 아니라 검증 가능한 지식으로 바꾸는 능력입니다.

**학습자료: 자료가 위키가 되는 흐름**

이 도해에서 원천 자료와 위키 문서는 분리되어 있습니다. 원천 자료는 근거입니다. 위키 문서는 활용하기 쉽게 정리한 결과입니다. PDF를 읽는 기능이 있어도 원본 위치와 수집 날짜가 남지 않으면 업무 근거로 쓰기 어렵습니다.

### 지원 범위를 확인하는 질문

도구 문서를 볼 때는 다음 질문을 순서대로 확인합니다.

| 질문 | 왜 중요한가 | 확인 방법 |
| --- | --- | --- |
| Markdown 파일을 읽고 쓸 수 있는가 | 사람이 직접 수정하고 백업하기 쉽다 | README의 저장 구조 확인 |
| 웹 URL을 수집할 수 있는가 | 공식 문서와 릴리스 노트를 넣기 쉽다 | `ingest`, `research`, `add URL` 기능 확인 |
| PDF나 긴 문서를 처리할 수 있는가 | 보고서, 논문, 매뉴얼을 다룰 때 필요하다 | 지원 형식, 크기 제한, 잘림 표시 확인 |
| 코드 작업 기록을 읽을 수 있는가 | Codex나 Claude Code 사용 이력을 지식으로 바꿀 수 있다 | session ingest 기능 확인 |
| 이미지나 멀티모달 자료를 다루는가 | 캡처, 슬라이드, 도해 자료가 많은 업무에 필요하다 | 멀티모달 지원과 전제 모델 확인 |
| 출처와 변경 이력을 남기는가 | 답변 검증과 감사에 필요하다 | provenance, audit, lint 기능 확인 |

처음부터 모든 형식을 지원할 필요는 없습니다. 첫 위키는 Markdown과 웹 문서만으로도 충분할 수 있습니다. 다만 내 업무 자료의 대부분이 PDF라면 PDF 지원을 미리 확인해야 합니다. 회의록과 코드 작업 기록이 많다면 텍스트 파일과 세션 기록 수집 기능이 더 중요합니다.

### 도구별 지원 범위를 읽는 법

2026-05-16 조사 기준으로 확인한 구현체들은 목표가 서로 다릅니다. `nvk/llm-wiki`는 Claude Code와 Codex 같은 에이전트 도구에서 쓰는 플러그인 흐름을 제공합니다. `atomicstrata/llm-wiki-compiler`는 CLI 컴파일러에 가깝고, Node.js 24 이상과 제공자 인증 정보를 요구합니다. OpenKB는 PDF, Word, Markdown, PowerPoint, HTML, Excel, 텍스트 등 넓은 형식 지원을 설명하지만, LLM API 키와 설정이 필요합니다. `nashsu/llm_wiki`는 데스크톱 앱 형태로 문서 가져오기와 그래프 탐색을 강조합니다.

이 차이는 우열이 아닙니다. 사용 장면의 차이입니다. 개인 업무 메모를 꾸준히 정리하려면 단순한 Markdown 구조가 편할 수 있습니다. 여러 문서를 반복적으로 수집하고 검사해야 한다면 플러그인이나 CLI 방식이 맞을 수 있습니다. 긴 문서와 PDF가 많다면 그 형식을 실제로 처리할 수 있는지 작은 샘플로 확인해야 합니다.

**학습자료: 내 자료와 도구 기능 맞추기**

| 내 자료 | 필요한 기능 | 낮은 위험의 시작 방식 |
| --- | --- | --- |
| 짧은 업무 메모 | Markdown 저장, 수동 편집 | 수동 Markdown |
| 회의록 텍스트 | 텍스트 수집, 요약, 출처 표시 | 수동 Markdown 또는 에이전트 기반 방식 |
| 공개 웹 문서 | URL 수집, 수집 날짜 기록 | 에이전트 기반 방식 또는 CLI |
| PDF 보고서 | 긴 문서 처리, 페이지 근거 | PDF 지원 도구 확인 필요 |
| 코드 작업 기록 | 세션 기록 수집 | 세션 ingest 지원 도구 확인 필요 |
| 이미지 캡처 | 이미지 해석, 설명 생성 | 멀티모달 지원 도구 확인 필요 |

이 표에서 “확인 필요”라고 표시한 항목은 바로 업무 자료를 넣지 않습니다. 공개 샘플이나 더미 자료로 먼저 테스트합니다. 특히 고객 정보, 계약 정보, 개인정보, 비공개 코드는 조직의 보안 기준을 확인한 뒤에만 사용해야 합니다.

## 버전 변화와 문서 확인 방법

LLM위키 구현체는 빠르게 바뀝니다. 예를 들어 `nvk/llm-wiki`는 GitHub Releases 기준 2026년 5월 14일 `v0.9.0 — Topic Archive Lifecycle` 릴리스가 확인되었습니다. 이 릴리스는 아카이브된 주제 위키를 기본 맥락에서 제외하는 흐름을 도입했습니다.

이런 변경은 사용법에 직접 영향을 줍니다. 어제까지 통하던 명령이나 저장 위치가 오늘도 같다고 단정하면 안 됩니다. 책이나 블로그의 예제 명령도 그대로 믿지 말고, 공식 README와 Releases를 다시 확인해야 합니다.

**학습자료: 문서 확인 순서**

flowchart TD
A\[도구 후보 발견\] --> B\[공식 저장소 README 확인\]
B --> C\[최신 Releases 또는 Changelog 확인\]
C --> D\[설치 전제 확인<br/>OS, Python/Node.js, API 키\]
D --> E\[저장 위치와 권한 확인\]
E --> F\[설치된 도구의 도움말 확인\]
F --> G\[작은 샘플로 실행\]
G --> H{원본과 위키 문서가 분리되는가?}
H -- 예 --> I\[업무 자료로 확장\]
H -- 아니오 --> J\[문서와 버전 차이 확인\]
J --> B

이 흐름은 번거로워 보여도 시간을 아껴 줍니다. LLM위키 도구는 파일 시스템, LLM 호출, 웹 접근, 플러그인 권한을 함께 다룹니다. 어느 한 부분이 바뀌면 예제가 실패할 수 있습니다. 작은 샘플로 먼저 확인하면 실제 업무 자료를 넣기 전에 위험을 줄일 수 있습니다.

### 공식 문서에서 볼 항목

공식 문서를 열었다면 다음 항목을 확인합니다.

| 확인 항목 | 볼 내용 | 원고와 실습에 반영하는 방법 |
| --- | --- | --- |
| 최신 버전 | Releases의 최신 태그와 날짜 | “확인일 기준”으로만 설명 |
| 설치 방법 | 플러그인 설치, 패키지 설치, 앱 다운로드 | 내 환경 하나를 기준으로 확인 |
| 실행 전제 | OS, Python, Node.js, API 키, 호스트 앱 | 실습 전제에 적기 |
| 저장 위치 | 기본 위키 폴더, 설정 파일 위치 | 고정 경로처럼 단정하지 않기 |
| 권한 | 웹 접근, 로컬 파일 접근, LLM 호출 | 민감 자료 입력 전 확인 |
| 명령 목록 | `ingest`, `query`, `compile`, `audit` 등 | 문서에 있는 이름만 사용 |
| 변경 이력 | 제거된 명령, 바뀐 옵션, 새 기능 | 오래된 예제 피하기 |

저장 위치와 권한은 특히 중요합니다. LLM위키는 개인 지식 자료를 다룹니다. 어디에 저장되는지 모르면 백업과 삭제가 어렵습니다. 또 웹 수집이나 리서치 기능은 호스트 도구의 네트워크 접근 정책을 따를 수 있습니다.

### Codex와 Claude Code 문서를 나눠 보기

Codex와 Claude Code는 지침 파일을 다루는 방식이 다릅니다. Codex 공식 문서는 `AGENTS.md`를 프로젝트 지침 파일로 설명합니다. 기본 설정에서는 프로젝트 지침의 합산 크기 제한도 있으므로, 큰 지침 파일을 만들 때는 로드 여부를 확인해야 합니다.

Claude Code는 `CLAUDE.md`를 기본 지침 파일로 사용합니다. Claude Code 문서는 `./CLAUDE.md` 또는 `./.claude/CLAUDE.md` 같은 프로젝트 범위 위치를 설명합니다. 이미 `AGENTS.md`를 쓰는 저장소라면 `CLAUDE.md`에서 가져오는 방식도 문서에 제시되어 있습니다.

즉, “어떤 지침 파일이든 모든 도구가 읽는다”고 생각하면 안 됩니다. Codex를 쓰면 `AGENTS.md` 기준으로 확인하고, Claude Code를 쓰면 `CLAUDE.md` 기준으로 확인합니다.

**학습자료: 지침 파일 확인 예시**

| 도구 | 기준 파일 | 확인 방법 | 주의할 점 |
| --- | --- | --- | --- |
| Codex | `AGENTS.md` | 프로젝트 루트에서 현재 지침 요약 요청 | 작업 디렉터리와 크기 제한 확인 |
| Claude Code | `CLAUDE.md` | `/memory`로 로드된 파일 확인 | `AGENTS.md`는 직접 읽지 않으므로 import 필요 |
| 일반 에이전트 | 도구마다 다름 | 문서의 instruction, memory, rules 항목 확인 | 파일명과 우선순위를 단정하지 않기 |

Codex에서 `AGENTS.md` 로드 여부를 확인하는 예시는 다음과 같습니다.

**실행 전제**

Codex CLI가 설치되어 있고, 확인하려는 프로젝트 루트에 `AGENTS.md`가 있어야 합니다.

```bash
Copycodex --ask-for-approval never "Summarize the current instructions."
```

**예상 결과**

Codex가 전역 또는 프로젝트의 `AGENTS.md`에 적은 주요 작업 규칙을 요약하면 로드가 확인된 것입니다. 아무 지침도 읽지 못했다면 현재 작업 디렉터리, 파일 내용, 지침 파일 크기 제한, override 파일 여부를 확인합니다.

## 도구 선택표로 결정하기

설치 난이도, 자료 형식, 버전 확인을 따로 보면 결정이 어렵습니다. 마지막에는 하나의 표로 모아야 합니다.

**학습자료: LLM위키 도구 선택표**

| 기준 | 질문 | 낮은 위험의 답 |
| --- | --- | --- |
| 설치 | 오늘 30분 안에 샘플을 실행할 수 있는가 | 예 |
| 유지보수 | 업그레이드 방법과 릴리스 노트를 찾을 수 있는가 | 예 |
| 저장 구조 | 원천 자료와 위키 문서가 분리되는가 | 예 |
| 수정 가능성 | 생성된 위키를 사람이 직접 고칠 수 있는가 | 예 |
| 자료 형식 | 내 업무 자료의 대부분을 처리할 수 있는가 | 예 |
| 출처 | 답변에서 원천 자료로 돌아갈 수 있는가 | 예 |
| 권한 | 웹 접근, 파일 접근, API 키 사용 범위를 이해했는가 | 예 |
| 이동성 | 나중에 다른 도구로 옮길 수 있는가 | Markdown 같은 개방 형식 |

이 표에서 `예`가 적다면 도구 도입을 미루는 것이 실패가 아닙니다. 수동 Markdown으로 작게 시작해도 LLM위키의 핵심은 배울 수 있습니다. 반대로 대부분 `예`라면 플러그인이나 CLI 도구를 검토해도 좋습니다.
