# 1. 지식이 쌓이는 세 층 — 보관함, 정리 노트, 작업 규칙

[목차](README.md) · 다음: [좋은 폴더 구조](02-folder-structure.md)

> 원전 대응: 2.1 지식이 쌓이는 세 층.[4]

## 1.1 먼저 비유로 이해하기

친구와 함께 발표를 준비한다고 생각해 보자.

- 선생님이 준 자료와 친구들의 회의 기록은 **원본 보관함**에 넣는다.
- 자료를 읽고 알아낸 내용은 **정리 노트**에 쓴다.
- “원본에는 낙서하지 않기”, “모르는 것은 모른다고 쓰기”는 **작업 규칙**으로 정한다.

LLM 위키도 같은 구분을 사용한다. 원본은 `raw`, 정리된 지식은 `wiki`, 정리 방법은 규칙 파일에 둔다.[4]

| 층 | 쉬운 이름 | 하는 일 | 핵심 질문 |
| --- | --- | --- | --- |
| `raw` | 원본 보관함 | 확보한 자료와 출처를 보존한다. | 실제 자료에는 뭐라고 적혀 있었지? |
| `wiki` | 정리 노트 | 자료를 주제별로 묶고 근거를 연결한다. | 지금까지 무엇을 알게 되었지? |
| 작업 규칙 | 정리 약속 | 원본 보호, 출처 표기, 불확실성 표시 기준을 정한다. | 어떤 기준으로 정리해야 하지? |

이 표는 원전의 역할 구분을 쉬운 말로 바꾼 것이다.[4]

## 1.2 `raw`: 나중에 다시 확인할 원본

`raw`는 “AI가 다듬기 전 자료”를 보관하는 곳이다. 회의록 원문, 업무 메모, 공식 문서 저장본 등이 해당한다.[4]

예를 들어 회의록에 “다음 주에 도입 여부를 검토하자”라고 적혀 있었다면, 그 표현을 보존해야 한다. AI가 만든 “도입하기로 결정했다”라는 문장으로 바꾸면 검토와 결정의 차이가 사라진다.[4]

**수업용 가상 원본**은 다음과 같다. 실제 회의 기록이 아니다.

```markdown
# 팀 발표 준비 회의 메모

자료 성격: 수업용 가상 회의 메모
회의 날짜: 수업용 예시 날짜

- 회의 후 할 일 목록을 다시 쓰는 일이 반복된다.
- 다음 회의에서 AI로 할 일 목록 초안을 만들지 검토하자고 제안했다.
- AI 정리 결과는 사람이 확인해야 한다.
- 팀원 연락처는 외부 도구에 보내지 않는다.
```

이 자료에서 직접 확인할 수 있는 것은 **제안이 있었다는 것**이다. 실제 도입, 시간 절약, 정확도 향상은 확인할 수 없다.

### 원본에 붙일 정보

원본은 자료 제목·출처·확인 날짜를 남기고, 자료 종류에 따라 회의 날짜나 문서 버전도 기록하도록 설명한다.[4]

| 정보 | 쉬운 이유 |
| --- | --- |
| 제목 | 무슨 자료인지 알기 위해 |
| 출처 또는 URL | 어디에서 왔는지 다시 찾기 위해 |
| 자료 날짜·확인 날짜 | 작성 시점과 읽은 시점을 구분하기 위해 |
| 버전 또는 근거 위치 | 어떤 내용에 근거했는지 확인하기 위해 |

**파일을 보존했다고 그 내용까지 참으로 증명되는 것은 아니다.** 원본은 “그 자료에 무엇이 적혀 있었는지” 확인하는 출발점이다.

## 1.3 `wiki`: 원본을 다시 쓰기 좋은 지식으로 정리하기

`wiki`는 원본을 바탕으로 만든 정리 문서다. 여러 자료의 공통 주제를 묶고, 관련 문서를 연결하고, 확인된 내용과 모르는 내용을 구분한다.[4]

원전에서 말하는 **컴파일**은 자료를 짧게 줄이는 것만이 아니다. 자료를 나중에 질문과 보고서에 다시 쓸 수 있도록 구조화하는 정리 작업이다.[1]

앞의 가상 메모를 정리하면 다음처럼 쓸 수 있다. 이 역시 사람이 작성한 수업용 예시이지 실제 모델 출력이 아니다.

```markdown
# 회의 후 할 일 목록 정리

## 한 문장 요약

팀은 반복되는 할 일 목록 정리 작업에 AI 초안을 활용할지 검토하려 한다.

## 확인된 내용

- 회의 후 할 일 목록을 다시 쓰는 일이 반복된다.
- AI 초안 활용은 제안 단계다.
- AI 결과를 사람이 확인해야 한다.

## 근거

- 원천 자료: raw/team-meeting.md
- 근거 위치: 회의 메모의 네 항목
- 자료 성격: 수업용 가상 회의 메모

## 확인 필요

- 실제로 AI를 사용할지 결정했는가?
- 기존 정리 작업에 얼마나 시간이 걸리는가?
- 초안에서 담당자나 기한을 틀리게 적지는 않는가?
```

좋은 정리본은 원본보다 읽기 쉬우면서도, 틀렸을 때 원본으로 돌아갈 수 있어야 한다.[4]

| 원본의 말 | 안전한 정리 | 잘못된 정리 |
| --- | --- | --- |
| 활용을 검토하자는 제안 | 제안 단계이며 결정 여부 확인 필요 | AI를 도입했다. |
| 할 일 정리가 반복됨 | 반복 작업이 있다. 소요 시간은 확인 필요 | 매주 많은 시간을 절약했다. |
| 사람이 확인해야 함 | 결과 검토가 필요하다. | AI가 최종 결정한다. |

표의 사례는 가상 메모를 바탕으로 만든 연습이다. **제안·결정·실행·성과는 같은 말이 아니다.**

## 1.4 작업 규칙: 매번 설명하지 않도록 약속을 남기기

규칙 파일에는 폴더 역할, 원본 보존, 출처 표시, 확인 필요 표시, 금지 작업 등을 적는다.[4]

규칙이 없으면 “자료를 잘 정리해 줘”라는 요청만 남는다. 무엇을 고쳐도 되는지, 모르는 정보를 어떻게 처리할지 분명하지 않다.[4]

다음은 설명용 규칙 예시다. 저장소의 실제 `AGENTS.md`를 바꾸라는 지시가 아니다.

```markdown
# 정리 작업 규칙 예시

- raw/의 원본은 임의로 덮어쓰지 않는다.
- wiki/의 핵심 주장에는 원천 자료와 근거 위치를 남긴다.
- 제안, 결정, 실행 결과를 구분한다.
- 근거가 없으면 확인 필요로 표시한다.
- 자료가 충돌하면 두 내용과 출처를 함께 남긴다.
- 개인정보를 승인 없이 외부로 보내지 않는다.
```

원전은 Codex의 `AGENTS.md`, Claude Code의 `CLAUDE.md`를 예로 든다. 실제 적용 전에는 사용하는 도구가 무엇을 읽는지 확인해야 한다.[4]

규칙 문서를 쓰는 것과 시스템이 그 규칙을 확실히 강제하는 것은 다르다. 이 수업에서는 규칙을 **작업 기준**으로 이해하고, 결과는 별도로 점검한다.

## 1.5 세 층은 같이 있어야 한다

- `raw`만 있으면: 자료는 남지만 다시 읽고 정리하는 일이 반복된다.[4]
- `wiki`만 있으면: 설명은 편하지만 잘못된 정리를 검증할 원본이 없다.[4]
- 규칙이 없으면: 원본 보호와 출처 표기 기준을 매번 다시 설명해야 한다.[4]

`output/`의 보고서나 발표 자료는 정리한 지식을 꺼내 쓴 결과물이다. **이 절의 세 번째 층인 작업 규칙과는 역할이 다르다.**[4][5]

### 이해 확인

**Q. 원본 회의록에 AI 요약을 덧붙여도 될까?**

원문과 해석이 섞이지 않게 별도 정리 문서로 둔다. 원본 자체의 오류를 발견해도 수정 의견은 따로 남긴다.[4]

**Q. “시간을 아낄 것 같다”를 “시간 절감이 확인됐다”로 바꿔도 될까?**

안 된다. 기대와 측정 결과는 다르다. 실제 측정 전에는 효과를 `확인 필요`로 남긴다.[6]

> **핵심: 원본은 보관함에, 해석은 정리 노트에, 정리 방법은 규칙에 둔다.**
