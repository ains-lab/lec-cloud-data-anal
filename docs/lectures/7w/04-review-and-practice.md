# 4. 복습과 종이 실습 — 자료의 역할과 근거 구분하기

[목차](README.md) · 이전: [좋은 위키 문서](03-good-wiki-pages.md)

> 이 문서는 2.1~2.3의 내용을 적용해 만든 수업용 활동이다. 원전의 명령 실행 실습을 그대로 옮긴 것이 아니다.[4][5][6]

## 4.1 한눈에 복습

| 구성 | 쉬운 이름 | 기억할 한 문장 |
| --- | --- | --- |
| `raw/` | 원본 보관함 | 실제 자료가 무엇이었는지 확인한다. |
| `wiki/` | 정리 노트 | 원본을 다시 쓰기 좋은 지식으로 정리한다. |
| 작업 규칙 | 정리 약속 | 원본 보호·출처·확인 필요의 기준을 남긴다. |
| `index.md` | 안내판 | 무엇을 어디서 읽을지 알려 준다. |
| `log.md` | 작업 일지 | 언제 무엇을 추가·수정·검토했는지 남긴다. |
| `output/` | 결과물 자료함 | 발표·보고서·계획서로 지식을 꺼내 쓴다. |

역할 구분은 원전의 기본 구조를 따른다.[4][5]

좋은 정리 노트는 **출처가 있고, 다음 질문에 쓸 수 있고, 관련 문서로 연결된다.**[6]

## 4.2 활동 1 — 문서의 집 찾아 주기

**목표:** 원본, 정리본, 산출물, 안내, 이력, 규칙을 구분한다.

**준비:** 종이나 Markdown 편집기만 있으면 된다. 도구 설치·로그인·네트워크·실제 위키 생성은 필요 없다.

**할 일:** 아래 항목이 어디에 들어갈지 적는다.

| 항목 | 어디에 둘까? |
| --- | --- |
| 팀 회의에서 기록한 메모 원문 | 직접 적기 |
| 여러 회의 메모를 읽고 정리한 반복 문제 | 직접 적기 |
| 교수님께 보여 줄 발표 초안 | 직접 적기 |
| 먼저 읽을 문서 목록과 위키의 목적 | 직접 적기 |
| “정리본을 수정하고 원문과 대조했다”는 기록 | 직접 적기 |
| “원본은 덮어쓰지 않고 모르면 표시한다”는 기준 | 직접 적기 |

**성공 기준:** 각 항목의 위치뿐 아니라 그 이유를 한 문장으로 설명한다.

### 예시 답

1. 회의 메모 원문 → `raw/`. 다시 대조할 자료다.
2. 반복 문제 정리 → `wiki/`. 여러 자료에서 얻은 해석이다.
3. 발표 초안 → `output/`. 특정 독자와 목적을 위한 결과물이다.
4. 목적과 읽을 목록 → `index.md`. 탐색 안내다.
5. 수정·대조 기록 → `log.md`. 실제 한 작업의 이력이다.
6. 보호·표시 기준 → 작업 규칙. 정리 방법을 정한다.

## 4.3 활동 2 — 원문보다 강해진 문장 찾기

**목표:** 제안과 결정, 기대와 측정 결과를 구분한다.

다음은 [1번 노트](01-three-layers.md)의 수업용 가상 메모에서 가져온 문장이다.

> 다음 회의에서 AI로 할 일 목록 초안을 만들지 검토하자고 제안했다.

### 문제

아래 정리 중 어떤 문장이 원문으로 뒷받침되는가?

- A. 팀은 AI를 도입하기로 결정했다.
- B. AI 활용을 검토하자는 제안이 있었다.
- C. AI 도입으로 정리 시간이 줄었다.
- D. AI가 담당자와 기한을 자동으로 결정하기로 했다.

### 예시 답

**B만 원문으로 뒷받침된다.**

- A: 검토 제안을 확정 결정으로 바꿨다.
- C: 실제 실행과 시간 측정 근거가 없다.
- D: 담당자·기한 자동 결정에 대한 합의가 없다.

**수정 연습:** A, C, D를 없애기만 하지 말고 필요한 확인 질문으로 바꾼다.

- AI 도입 여부를 누가 언제 결정할까?
- 정리 시간과 검토 시간을 어떻게 측정할까?
- 담당자·기한이 없는 항목은 어떻게 표시할까?

## 4.4 활동 3 — 다시 쓸 수 있는 문서 한 장 설계하기

**목표:** 출처·재사용 구조·링크를 갖춘 정리 노트를 설계한다.

**준비:** 앞선 가상 메모만 사용한다. 실제 팀원 정보나 고객 자료를 넣지 않는다.

**할 일:** 다음 칸을 채운다.

1. 제목: 다루는 질문이 드러나는 이름.
2. 한 문장 요약: 제안 단계임을 유지한다.
3. 근거: 가상 원천 자료의 이름과 근거 항목.
4. 확인된 내용: 원문으로 뒷받침되는 문장만 적는다.
5. 확인 필요: 결정 여부, 시간, 오류 등 모르는 것을 적는다.
6. 관련 문서: 원본·검토 기준·발표 초안으로 연결할 길을 설계한다.
7. 다음 질문: 나중에 다시 물을 질문을 적는다.

**성공 기준:** 다음을 모두 확인한다.

- 원본과 정리본을 구분했다.
- 측정하지 않은 성과를 만들지 않았다.
- 원문에 없는 담당자나 기한을 만들어 넣지 않았다.
- 새로 제안한 검토 기준은 사실과 구분했다.
- 출처·확인 필요·다음 질문이 있다.
- 설계한 링크의 상대 경로를 설명할 수 있다.

**막혔을 때:** [좋은 문서로 바꾼 예시](03-good-wiki-pages.md)를 읽고 형식만 참고한다. 빈칸을 채우려고 사실을 만들어 쓰지 않는다.

**제출물 예시:** 역할 분류표, 잘못된 문장의 수정안, 정리 노트 설계 한 장. 실제 LLM 실행 결과를 제출하는 활동이 아니다.

## 4.5 빠른 확인 질문

**Q1. 2.1절의 세 층은 무엇인가?**

`raw`, `wiki`, 작업 규칙이다. `output`은 정리한 지식을 활용한 산출물 공간이다.[4][5]

**Q2. `wiki`가 있으니 `raw`는 없어도 될까?**

아니다. 요약이 틀리거나 조건을 빠뜨렸을 때 원본으로 돌아갈 수 있어야 한다.[4]

**Q3. `index.md`와 `log.md` 중 오늘 고친 내용을 기록하는 것은?**

`log.md`다. `index.md`는 주요 문서의 위치와 읽는 순서를 안내한다.[5]

**Q4. 좋은 위키 문서의 세 조건은?**

출처, 질문에 다시 쓰기 쉬운 구조, 다른 문서로 이어지는 링크다.[6]

**Q5. 출처를 달고 규칙을 적었으니 AI 답변을 그대로 믿어도 될까?**

아니다. 정리 과정에서 원문의 조건이 빠지거나 추정이 섞일 수 있다. 중요한 주장은 원문과 대조한다.[4][6]

**Q6. 자료끼리 서로 다른 주장을 하면 하나만 남길까?**

충돌을 숨기지 않고 두 내용과 출처·날짜를 남긴다. 무엇이 맞는지는 추가 확인한다.[4]

## 4.6 다음 단계로 넘어가기 전

실제 위키에 적용하려면 먼저 중심 질문, 입력 자료의 허용 범위, 작업 규칙, 검토 방법을 정한다.[4][5]

이번 노트에서 폴더 역할을 이해한 것과 실제 수집·모델 정리·검증을 수행한 것은 다르다. 예시를 읽었다는 이유로 운영 위키나 자동화를 완료했다고 보고하지 않는다.

> **마지막 확인: “이 문장은 어디서 왔고, 어디까지 확인됐고, 다음에 어디로 이어지는가?”를 설명할 수 있으면 기본 구조를 이해한 것이다.**
