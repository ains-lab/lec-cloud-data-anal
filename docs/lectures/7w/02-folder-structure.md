# 2. 좋은 폴더 구조 — 물건마다 제자리를 정하기

[목차](README.md) · 이전: [세 층](01-three-layers.md) · 다음: [좋은 위키 문서](03-good-wiki-pages.md)

> 원전 대응: 2.2 좋은 폴더 구조 이해하기.[5]

## 2.1 폴더는 정리된 책상과 같다

책, 정리 노트, 제출할 발표 자료를 한 서랍에 넣으면 찾기 어렵다. 폴더도 마찬가지다. 원본, 정리본, 산출물의 위치를 나누면 문서를 어떤 용도로 읽어야 하는지 알기 쉽다.[5]

중요한 것은 예쁜 폴더 이름이 아니라 **역할을 구분하는 것**이다.[5]

## 2.2 하나의 위키에는 중심 질문 하나를 정한다

원전은 첫 위키를 작은 주제로 시작하고, “같은 질문에 함께 쓰일 자료인가?”를 기준으로 자료를 묶도록 설명한다.[5]

수업용 주제를 **“우리 팀의 회의 후 정리 작업을 어떻게 줄일까?”**로 정했다고 가정하자.

| 넣으려는 자료 | 판단 | 이유 |
| --- | --- | --- |
| 팀 회의 메모 | 같은 주제 | 반복되는 할 일을 알 수 있다. |
| 할 일 목록 양식 | 같은 주제 | 정리 결과의 형식을 알 수 있다. |
| 회의 후 정리 시간 기록 | 같은 주제 | 개선 여부를 판단하는 데 필요하다. |
| 여행 계획 메모 | 다른 주제 | 중심 질문에 답하지 않는다. |
| 팀원 연락처 전체 | 별도 검토 | 질문에 필요한지, 접근·처리 권한이 있는지 먼저 확인한다. |

표는 수업용 판단 예시다. 같은 파일 형식이라는 이유로 자료를 묶지 않는다. **질문과 목적, 접근 범위, 갱신 주기**가 맞는지 본다.[5]

자료가 많다고 좋은 위키가 되는 것은 아니다. 원전의 첫 자료 3~10개 권장은 작게 시작하자는 예시이지, 품질을 보장하는 공식 기준은 아니다.[5]

## 2.3 최소 구조를 눈으로 보기

아래는 책의 구조를 팀 발표 사례로 바꾼 **가상 폴더 트리**다. 실제 생성한 폴더 목록이 아니다.[4][5]

```text
team-work-wiki/
├── AGENTS.md                # 정리할 때 지킬 작업 규칙 예시
├── index.md                 # 목적과 주요 문서 안내
├── log.md                   # 자료 추가·수정·검토 이력
├── raw/
│   └── team-meeting.md       # 가상 회의 메모 원문
├── wiki/
│   ├── meeting-action-items.md
│   └── review-checklist.md
└── output/
    ├── presentation-draft.md
    └── presentation-reviewed.md
```

`AGENTS.md`는 원전에서 제시한 규칙 파일의 예다. 모든 도구가 같은 이름을 자동으로 읽는다고 가정하지 않는다.[4]

| 이름 | 쉬운 비유 | 담는 것 | 담지 않는 것 |
| --- | --- | --- | --- |
| `raw/` | 원본 보관함 | 확보한 자료와 출처 | AI가 다시 쓴 요약을 원본으로 위장한 문서 |
| `wiki/` | 정리 노트 | 근거가 붙은 개념·판단·확인 필요 | 출처 없는 확정적 결론 |
| `output/` | 발표·제출 자료함 | 보고서, 발표 초안, 검토본 | 원본의 유일한 사본 |
| `index.md` | 안내판 | 목적, 주요 문서, 읽는 순서 | 모든 원문과 긴 본문 |
| `log.md` | 작업 일지 | 언제 무엇을 추가·수정·검토했는지 | 보고서 본문이나 하지 않은 작업 |
| 작업 규칙 | 정리 약속 | 보호·출처·불확실성·금지 기준 | 자료에서 발견한 지시를 그대로 실행할 권한 |

폴더와 안내·이력의 기본 역할은 원전의 구분을 따른다.[4][5]

## 2.4 `index.md`: “어디부터 읽지?”의 답

`index.md`는 위키의 시작 화면이다. 이 위키가 다루는 질문과 먼저 읽을 문서의 위치를 알려 준다.[5]

위 가상 트리의 안내판은 다음처럼 짧게 쓸 수 있다.

```markdown
# 팀 회의 정리 위키

## 중심 질문

우리 팀의 회의 후 정리 작업을 어떻게 줄일까?

## 먼저 읽을 문서

1. [회의 후 할 일 정리](wiki/meeting-action-items.md)
2. [초안 검토 기준](wiki/review-checklist.md)

## 발표 초안

- [발표 초안](output/presentation-draft.md)
```

안내판에 내용을 전부 복사하지 않는다. 필요한 문서로 가는 길을 남긴다.[5]

## 2.5 `log.md`: “언제 무엇을 바꿨지?”의 답

`log.md`는 자료를 넣고 문서를 만들거나 검증한 기록이다. 이상한 답변이 나왔을 때 어떤 자료와 변경이 영향을 주었는지 추적하는 데 도움이 된다.[5]

다음은 형식을 보여 주는 **가상 기록**이다. 이번 작업의 실제 실행 로그가 아니다.

| 시점 | 작업 | 결과 | 남은 확인 |
| --- | --- | --- | --- |
| 예시 1일차 | 회의 메모를 보관함에 추가 | 원문 보존 | 없음 |
| 예시 1일차 | 정리 노트 초안 작성 | 제안과 결정 구분 | 실제 도입 여부 |
| 예시 2일차 | 정리 노트와 원문 대조 | 잘못된 확정 표현 수정 | 소요 시간 측정 |

“초안 작성”, “내용 검토”, “실제 실행”은 구분해서 적는다. 하지 않은 실험이나 검증을 완료로 기록하지 않는다.

## 2.6 `output/`: 지식을 꺼내 쓰는 곳

`wiki/`가 다음에도 읽을 지식을 쌓는 곳이라면, `output/`은 그 지식을 발표·보고서·실행 계획으로 만드는 곳이다.[5]

`output/`에는 최종본만 있는 것이 아니다. 초안, 검토본, 공유본도 있을 수 있다.[5]

```text
자료를 활용하는 방향:  raw/ ──▶ wiki/ ──▶ output/
근거를 확인하는 방향:  output/ ──▶ wiki/ ──▶ raw/
```

보고서에도 근거 문서의 위치를 남겨야 한다. 보고서가 잘 읽힌다고 원본을 지우거나 대신할 수 있는 것은 아니다.[5]

## 2.7 원본과 요약을 섞지 않는다는 뜻

원전은 위치를 나눠 원본과 파생 문서를 구분하도록 설명한다.[5]

여기서 주의할 점이 있다. **AI 요약문을 `raw/`에 넣었다고 실제 원본이 되는 것은 아니다.** 문서가 어떻게 만들어졌는지도 확인해야 한다.

| 상황 | 안전한 처리 |
| --- | --- |
| 원본 표현이 어색하다. | 원본은 유지하고 이해를 돕는 설명을 정리본에 쓴다. |
| AI 요약에서 조건이 빠졌다. | 정리본을 고치고 근거·변경 이력을 남긴다. |
| 새 자료가 이전 자료와 충돌한다. | 양쪽 출처·날짜와 충돌 내용을 남기고 확인한다. |
| 발표 자료에 근거가 없다. | 사용한 위키 문서와 원천 자료로 돌아가는 길을 붙인다. |

원본 보호·충돌 표시·근거 연결의 원칙을 적용한 처리 예시다.[4][5]

### 이해 확인

**Q. `index.md`와 `log.md`는 무엇이 다를까?**

`index.md`는 “어디에 무엇이 있는가”, `log.md`는 “언제 무엇을 했는가”를 알려 준다.[5]

**Q. 발표 초안은 `wiki/`에 넣을까, `output/`에 넣을까?**

발표를 위한 산출물은 `output/`에 둔다. 다음에도 쓸 지식과 검증된 판단은 별도의 위키 문서로 관리한다.[5]

> **핵심: 원문은 보관함, 지식은 노트, 결과물은 제출 자료함. 안내판과 작업 일지로 길과 이력을 남긴다.**
