# 6.3 답변을 다시 위키에 반영하기

![6.3 답변을 다시 위키에 반영하기 삽화](https://static.wikidocs.net/images/page/353400/6.3-%EB%8B%B5%EB%B3%80%EC%9D%84-%EB%8B%A4%EC%8B%9C-%EC%9C%84%ED%82%A4%EC%97%90-%EB%B0%98%EC%98%81%ED%95%98%EA%B8%B0.jpg)

LLM위키에 질문해서 좋은 답을 얻었다면, 그 답을 대화창에만 남겨 두면 안 됩니다. 다음에 같은 질문을 다시 하게 되기 때문입니다. 6.3에서는 검증한 답변을 위키에 반영하는 방법을 다룹니다. 핵심은 세 가지입니다. 결정 사항은 기록하고, 새로 알게 된 내용은 출처와 함께 추가하며, 반복되는 질문은 템플릿으로 남깁니다.

이 절에서 다루는 작업은 LLM위키의 `query` 이후 단계입니다. 질문해서 답을 얻고, 근거를 확인한 다음, 그 결과를 다시 `wiki/`, `index.md`, `log.md`, 템플릿 문서에 반영합니다. 단, LLM의 답변은 원본이 아닙니다. 위키에 넣기 전에 어떤 자료에서 확인했는지, 어떤 부분은 아직 확인이 필요한지 구분해야 합니다.

아니오

예

위키에 질문

답변 받기

근거 확인

반영할 가치가 있는가

대화 기록으로 종료

결정 사항 기록

새 지식 추가

반복 질문 템플릿화

index.md와 log.md 갱신

이 흐름을 익히면 위키는 단순한 참고 문서가 아니라 계속 좋아지는 업무 시스템이 됩니다. 질문할수록 결정이 쌓이고, 새 지식이 정리되며, 자주 쓰는 질문은 짧아집니다.

## 결정 사항 기록하기

LLM에게 질문하면 여러 답변 후보가 나옵니다. 그중 실제 업무에 채택한 것은 따로 기록해야 합니다. “좋은 답변이었다”와 “우리 업무 기준으로 결정했다”는 다릅니다. 결정 사항에는 선택한 결론, 선택한 이유, 근거 자료, 확인 날짜, 다음 행동이 함께 있어야 합니다.

결정 기록이 없으면 나중에 같은 논의를 반복합니다. 예를 들어 “회의록 자동화는 어떤 형식으로 정리할까?”라는 질문을 여러 번 했다고 가정해 봅니다. 한 번은 담당자 중심으로, 다음에는 일정 중심으로, 또 다음에는 리스크 중심으로 답이 나올 수 있습니다. 위키에 결정 사항을 남겨 두면 다음 질문은 “이미 정한 회의록 형식에 맞춰 이번 회의록을 정리해 줘”처럼 짧아집니다.

**학습자료: 결정 기록에 남길 항목**

| 항목 | 쓰는 내용 | 예시 |
| --- | --- | --- |
| 결정 | 실제로 채택한 결론 | 회의록 실행 항목은 담당자, 기한, 검증 방법으로 기록한다 |
| 이유 | 이 결정을 선택한 배경 | 다음 회의에서 진행 여부를 바로 확인하기 위해 |
| 근거 | 확인한 원천 자료나 위키 문서 | `raw/meetings/2026-05-16-sales-sync.md` |
| 확인 날짜 | 결정을 검토한 날짜 | 2026-05-16 |
| 남은 의문 | 아직 확인하지 못한 부분 | 외부 고객 회의에도 같은 형식을 쓸지는 확인 필요 |
| 다음 행동 | 결정 이후 해야 할 일 | 회의록 템플릿 문서 갱신 |

이 표는 결정을 문장 하나로 남기지 않기 위한 장치입니다. 결정은 나중에 실행으로 이어져야 하므로, 이유와 다음 행동이 함께 있어야 합니다. 근거가 없는 결정은 위키에 넣더라도 다시 검증해야 합니다.

### 실습: 결정 로그 만들기

이번 실습에서는 검증이 끝난 답변을 `wiki/decisions.md`에 기록합니다. 예제 주제는 “회의록 자동화 형식 결정”입니다.

**목표**

LLM 답변에서 실제로 채택한 결정을 골라 위키에 남깁니다.

**실행 전제**

macOS, Linux, 또는 WSL에서 Bash나 Zsh를 사용할 수 있으면 됩니다. 별도 LLM 도구는 필요하지 않습니다. 아래 코드는 실습용 파일을 만듭니다.

**성공 기준**

`wiki/decisions.md`에 결정, 이유, 근거, 확인 날짜, 다음 행동이 들어갑니다.

```bash
CopyBASE="$HOME/llm-wiki-6-3"

if [ -e "$BASE" ]; then
  echo "이미 실습 폴더가 있습니다. BASE 값을 바꾸고 다시 실행하세요." >&2
  exit 1
fi

mkdir -p "$BASE/raw/meetings" "$BASE/wiki" "$BASE/templates"

cat > "$BASE/raw/meetings/2026-05-16-sales-sync.md" <<'EOF'
# 영업 주간 회의 메모

- 반복 문의가 많은 고객군은 온보딩 고객이다.
- 회의록에는 다음 주 담당자와 확인 방법이 함께 있어야 한다.
- 지난주에는 담당자가 없는 실행 항목이 남아 후속 확인이 어려웠다.
EOF

cat > "$BASE/wiki/decisions.md" <<'EOF'
# 결정 사항

## 2026-05-16 회의록 실행 항목 형식

- 결정: 회의록의 실행 항목은 `담당자`, `기한`, `검증 방법`을 함께 기록한다.
- 이유: 담당자만 있으면 다음 회의에서 완료 여부를 확인하기 어렵다.
- 근거: `raw/meetings/2026-05-16-sales-sync.md`
- 확인 날짜: 2026-05-16
- 확인 필요: 외부 고객 회의에도 같은 형식을 적용할지는 추가 확인이 필요하다.
- 다음 행동: 회의록 정리 템플릿에 이 형식을 반영한다.
EOF

sed -n '1,20p' "$BASE/wiki/decisions.md"
```

예상 결과는 다음과 비슷합니다.

```text
Copy# 결정 사항

## 2026-05-16 회의록 실행 항목 형식

- 결정: 회의록의 실행 항목은 `담당자`, `기한`, `검증 방법`을 함께 기록한다.
- 이유: 담당자만 있으면 다음 회의에서 완료 여부를 확인하기 어렵다.
- 근거: `raw/meetings/2026-05-16-sales-sync.md`
- 확인 날짜: 2026-05-16
- 확인 필요: 외부 고객 회의에도 같은 형식을 적용할지는 추가 확인이 필요하다.
- 다음 행동: 회의록 정리 템플릿에 이 형식을 반영한다.
```

이 실습에서 중요한 부분은 파일을 만든 것이 아닙니다. 답변을 “채택한 결정”과 “확인 필요”로 나눴다는 점입니다. LLM의 답변 중 일부만 업무 기준이 됩니다. 나머지는 후보, 추정, 추가 확인 사항으로 남겨야 합니다.

### 결정과 답변을 구분하기

LLM의 답변은 보통 길고 친절합니다. 하지만 위키에 그대로 붙여 넣으면 나중에 읽기 어렵습니다. 결정 기록에는 최종 판단만 남깁니다. 자세한 설명이 필요하면 별도 위키 문서로 분리하고, 결정 로그에서는 링크만 걸어 둡니다.

LLM 답변

근거 있는 내용

추정 또는 제안

채택한 결정

관련 위키 문서에 추가

확인 필요로 표시

decisions.md에 기록

이 도해는 답변을 세 갈래로 나누는 기준을 보여 줍니다. 근거 있는 내용은 지식 문서로 보냅니다. 아직 확인하지 못한 내용은 확인 필요로 둡니다. 실제로 채택한 결론만 결정 로그에 남깁니다.

## 새로 알게 된 내용 추가하기

질문 과정에서 새로 알게 된 내용은 위키 문서에 반영해야 합니다. 이때 중요한 원칙은 원본과 파생 지식을 섞지 않는 것입니다. 원본 자료는 `raw/`에 보존하고, 새로 정리한 지식은 `wiki/`에 둡니다. LLM이 만든 문장은 원본이 아니라 파생 지식입니다.

새 지식을 추가할 때는 세 가지를 함께 남깁니다. 첫째, 무엇을 알게 되었는지 씁니다. 둘째, 어떤 자료에서 확인했는지 씁니다. 셋째, 아직 확실하지 않은 부분을 표시합니다. 이렇게 해야 다음 질문에서 LLM이 근거 있는 내용과 추정을 구분할 수 있습니다.

**학습자료: 새 지식 추가 방식 비교**

| 방식 | 문제점 | 더 나은 방식 |
| --- | --- | --- |
| 답변 전체를 `wiki/notes.md`에 붙여 넣기 | 핵심과 추정이 섞인다 | 확인된 내용만 주제 문서에 추가한다 |
| 출처 없이 요약만 저장하기 | 나중에 검증할 수 없다 | 원천 파일 경로와 확인 날짜를 남긴다 |
| 기존 문서 끝에 계속 덧붙이기 | 문서가 길어지고 다시 찾기 어렵다 | 중복되는 내용을 통합하고 필요한 링크를 건다 |
| 확실하지 않은 내용을 단정하기 | 오류가 위키에 퍼진다 | `확인 필요` 항목으로 분리한다 |

새 지식 추가는 “많이 저장하기”가 아니라 “다시 질문하기 쉽게 정리하기”입니다. 위키 문서가 길어질수록 좋은 것이 아닙니다. 짧더라도 근거가 분명하고 다음 질문에 바로 쓸 수 있어야 합니다.

### 실습: 새로 확인한 내용을 위키 문서에 추가하기

이번 실습에서는 회의록에서 확인한 내용을 `wiki/meeting-summary-rules.md`에 추가합니다. 결정 로그와 달리 이 문서는 “회의록 정리 규칙”이라는 주제 지식입니다.

**목표**

검증한 답변을 주제별 위키 문서에 반영합니다.

**실행 전제**

앞의 실습을 실행해 `~/llm-wiki-6-3` 폴더가 있어야 합니다.

**성공 기준**

`wiki/meeting-summary-rules.md`에 확인된 내용, 근거, 확인 필요 항목이 들어갑니다.

```bash
CopyBASE="$HOME/llm-wiki-6-3"

test -d "$BASE/raw/meetings" || {
  echo "먼저 결정 로그 만들기 실습을 실행하세요." >&2
  exit 1
}

cat > "$BASE/wiki/meeting-summary-rules.md" <<'EOF'
# 회의록 정리 규칙

## 한 문장 요약

회의록의 실행 항목은 다음 회의에서 진행 여부를 확인할 수 있는 형태로 정리한다.

## 확인된 내용

- 실행 항목에는 `담당자`, `기한`, `검증 방법`을 함께 적는다.
- 담당자가 없는 실행 항목은 후속 확인이 어렵다.
- 온보딩 고객군은 반복 문의가 많으므로 별도 추적이 필요하다.

## 근거

- 원천 자료: `raw/meetings/2026-05-16-sales-sync.md`
- 확인 날짜: 2026-05-16
- 자료 성격: 내부 회의 메모

## 확인 필요

- 외부 고객 회의에도 같은 실행 항목 형식을 적용할지 확인해야 한다.
- 반복 문의가 많은 고객군이 다른 기간에도 온보딩 고객인지 추가 자료가 필요하다.

## 다시 물어볼 질문

- 이번 주 회의록에서 담당자, 기한, 검증 방법이 빠진 실행 항목을 찾아 줘.
- 온보딩 고객의 반복 문의를 줄이기 위한 다음 실험을 3개 제안해 줘.
EOF

sed -n '1,40p' "$BASE/wiki/meeting-summary-rules.md"
```

예상 결과는 다음 구조를 포함합니다.

```text
Copy# 회의록 정리 규칙

## 한 문장 요약
...
## 확인된 내용
...
## 근거
...
## 확인 필요
...
## 다시 물어볼 질문
...
```

이 문서는 다음 질문의 바탕이 됩니다. 예를 들어 “이번 회의록을 정리해 줘”라고 묻는 대신 “`wiki/meeting-summary-rules.md`의 규칙에 맞춰 이번 회의록의 실행 항목을 정리해 줘”라고 요청할 수 있습니다. 질문이 짧아지고 결과 형식도 안정됩니다.

### index와 log 갱신하기

새 문서를 만들었다면 `index.md`와 `log.md`도 함께 갱신하는 편이 좋습니다. `index.md`는 위키의 입구입니다. `log.md`는 처리 이력입니다. Karpathy의 LLM Wiki 아이디어 문서에서도 `index.md`와 `log.md`는 작은 위키의 탐색성과 이력을 돕는 요소로 설명됩니다.

**학습자료: 반영 후 갱신할 위치**

| 위치 | 역할 | 이번 예제에서 쓸 내용 |
| --- | --- | --- |
| `wiki/meeting-summary-rules.md` | 주제 지식 | 회의록 실행 항목 규칙 |
| `wiki/decisions.md` | 채택한 결정 | 실행 항목 형식 결정 |
| `index.md` | 위키 입구 | 새 문서 링크와 설명 |
| `log.md` | 처리 이력 | 언제 어떤 자료를 반영했는지 |
| `templates/` | 반복 질문 양식 | 회의록 점검 질문 템플릿 |

다음 코드는 `index.md`와 `log.md`를 만듭니다.

```bash
CopyBASE="$HOME/llm-wiki-6-3"

cat > "$BASE/index.md" <<'EOF'
# LLM위키 6.3 실습 인덱스

## 주요 문서

- `wiki/decisions.md`: 검증 후 채택한 결정 사항
- `wiki/meeting-summary-rules.md`: 회의록 정리 규칙
- `raw/meetings/2026-05-16-sales-sync.md`: 원천 회의 메모

## 다음에 물어볼 질문

- 회의록 정리 규칙에 맞춰 새 회의록을 점검해 줘.
- 결정 사항 중 확인 필요 항목만 모아 다음 행동을 제안해 줘.
EOF

cat > "$BASE/log.md" <<'EOF'
# 처리 이력

## 2026-05-16

- `raw/meetings/2026-05-16-sales-sync.md`를 기준으로 회의록 실행 항목 형식을 검토했다.
- `wiki/decisions.md`에 채택한 결정을 기록했다.
- `wiki/meeting-summary-rules.md`에 확인된 규칙과 확인 필요 항목을 추가했다.
EOF

find "$BASE" -maxdepth 2 -type f | sort
```

예상 결과는 다음 파일들을 포함합니다.

```text
Copy/Users/.../llm-wiki-6-3/index.md
/Users/.../llm-wiki-6-3/log.md
/Users/.../llm-wiki-6-3/raw/meetings/2026-05-16-sales-sync.md
/Users/.../llm-wiki-6-3/wiki/decisions.md
/Users/.../llm-wiki-6-3/wiki/meeting-summary-rules.md
```

`index.md`는 “무엇이 어디에 있는지”를 알려 줍니다. `log.md`는 “왜 이런 문서가 생겼는지”를 알려 줍니다. 둘 중 하나만 있어도 도움이 되지만, 함께 있으면 나중에 위키를 다시 열었을 때 훨씬 빨리 맥락을 회복할 수 있습니다.

## 반복 질문 템플릿 만들기

반복 질문은 템플릿으로 바꿔야 합니다. 템플릿은 매번 같은 배경 설명을 다시 쓰지 않기 위한 장치입니다. 특히 회의록 정리, 보고서 초안 작성, 자료 검토, 결정 사항 추적처럼 자주 반복되는 작업에 효과적입니다.

좋은 질문 템플릿에는 입력 자료, 참고할 위키 문서, 원하는 출력 형식, 검증 기준이 들어갑니다. “회의록 정리해 줘”는 템플릿이 아닙니다. “다음 회의록을 `wiki/meeting-summary-rules.md` 기준으로 점검하고, 실행 항목 누락과 확인 필요 사항을 표로 정리해 줘”가 템플릿에 가깝습니다.

**학습자료: 질문 템플릿의 기본 구조**

```text
Copy[작업 목적]
무엇을 얻고 싶은지 쓴다.

[입력 자료]
이번에 처리할 원천 자료를 지정한다.

[참고할 위키 문서]
이미 정리된 기준, 결정 사항, 용어집을 지정한다.

[출력 형식]
표, 목록, 보고서 초안 등 원하는 형태를 지정한다.

[검증 기준]
근거 표시, 확인 필요 분리, 누락 항목 점검 기준을 쓴다.
```

이 구조는 LLM에게 친절한 문장을 쓰기 위한 것이 아닙니다. 매번 같은 품질 기준을 적용하기 위한 것입니다. 템플릿이 있으면 질문을 짧게 바꾸면서도 결과 품질을 유지할 수 있습니다.

### 실습: 회의록 점검 템플릿 만들기

이번 실습에서는 반복 질문 템플릿을 `templates/check-meeting-notes.md`로 만듭니다.

**목표**

앞에서 정리한 결정 사항과 위키 문서를 재사용하는 질문 템플릿을 만듭니다.

**실행 전제**

앞의 실습을 실행해 `wiki/decisions.md`와 `wiki/meeting-summary-rules.md`가 있어야 합니다.

**성공 기준**

템플릿에 작업 목적, 입력 자료, 참고 문서, 출력 형식, 검증 기준이 들어갑니다.

```bash
CopyBASE="$HOME/llm-wiki-6-3"

test -f "$BASE/wiki/decisions.md" || {
  echo "먼저 결정 로그 만들기 실습을 실행하세요." >&2
  exit 1
}

test -f "$BASE/wiki/meeting-summary-rules.md" || {
  echo "먼저 새 지식 추가 실습을 실행하세요." >&2
  exit 1
}

cat > "$BASE/templates/check-meeting-notes.md" <<'EOF'
# 반복 질문 템플릿: 회의록 실행 항목 점검

## 작업 목적

새 회의록에서 실행 항목을 찾고, 위키에 기록된 회의록 정리 규칙에 맞는지 점검한다.

## 입력 자료

- 원천 회의록: `{raw_meeting_file}`

## 참고할 위키 문서

- `wiki/meeting-summary-rules.md`
- `wiki/decisions.md`

## 요청 문장

다음 원천 회의록을 읽고 `wiki/meeting-summary-rules.md`와 `wiki/decisions.md` 기준으로 실행 항목을 점검해 주세요.

원천 회의록: `{raw_meeting_file}`

다음 형식으로 답하세요.

| 실행 항목 | 담당자 | 기한 | 검증 방법 | 근거 문장 | 상태 |
|---|---|---|---|---|---|

## 검증 기준

- 원천 회의록에 없는 내용은 추정이라고 표시한다.
- 담당자, 기한, 검증 방법 중 빠진 항목은 `확인 필요`로 표시한다.
- 결정 사항과 충돌하는 내용이 있으면 별도 목록으로 분리한다.
- 답변 끝에 위키에 반영할 후보를 제안한다.
EOF

sed -n '1,80p' "$BASE/templates/check-meeting-notes.md"
```

예상 결과는 템플릿 문서가 출력되는 것입니다. `{raw_meeting_file}`은 나중에 실제 회의록 파일 경로로 바꿔 넣을 자리입니다.

이 템플릿을 사용하면 매번 긴 설명을 다시 하지 않아도 됩니다. 새 회의록이 생겼을 때 파일 경로만 바꾸면 됩니다. 위키 문서와 결정 로그를 함께 지정했기 때문에, 답변은 현재 위키의 기준을 따르게 됩니다. 단, 지침 파일이나 템플릿은 LLM 행동을 완전히 보장하지 않습니다. 결과는 항상 검토해야 합니다.

### 템플릿을 위키 운영 규칙과 연결하기

반복 질문 템플릿이 늘어나면 템플릿 자체도 찾기 어려워집니다. 그래서 `index.md`에 자주 쓰는 템플릿을 등록해 둡니다. Codex를 쓴다면 `AGENTS.md`, Claude Code를 쓴다면 `CLAUDE.md`에 “반복 작업은 `templates/`를 먼저 확인한다”는 작업 기준을 둘 수 있습니다. 다만 공식 문서 기준으로 이런 지침 파일은 모델이 참고하는 컨텍스트입니다. 결과를 강제하는 장치는 아니므로, 출력 검증은 계속 필요합니다.

```bash
CopyBASE="$HOME/llm-wiki-6-3"

cat >> "$BASE/index.md" <<'EOF'

## 반복 질문 템플릿

- `templates/check-meeting-notes.md`: 새 회의록의 실행 항목을 점검할 때 사용
EOF

cat > "$BASE/AGENTS.md" <<'EOF'
# LLM위키 실습 작업 기준

- `raw/`의 원천 자료는 임의로 수정하지 않는다.
- 질문에 답할 때는 먼저 `index.md`에서 관련 위키 문서와 템플릿을 확인한다.
- 결정 사항은 `wiki/decisions.md`에 기록한다.
- 새로 확인한 지식은 근거와 확인 날짜를 포함해 `wiki/`에 반영한다.
- 확인되지 않은 내용은 단정하지 않고 `확인 필요`로 표시한다.
EOF

sed -n '1,120p' "$BASE/index.md"
```

예상 결과는 `index.md` 아래에 반복 질문 템플릿 항목이 추가되는 것입니다.

```text
Copy## 반복 질문 템플릿

- `templates/check-meeting-notes.md`: 새 회의록의 실행 항목을 점검할 때 사용
```

이제 위키에는 세 가지가 연결되어 있습니다. 결정 로그는 “무엇을 정했는지”를 알려 줍니다. 주제 문서는 “무엇을 알게 되었는지”를 설명합니다. 질문 템플릿은 “다음에 어떻게 다시 물을지”를 남깁니다.

index.md

wiki/decisions.md

wiki/meeting-summary-rules.md

templates/check-meeting-notes.md

raw/meetings/2026-05-16-sales-sync.md

log.md

이 구조가 만들어지면 다음 작업이 쉬워집니다. 새 회의록을 넣고, 템플릿으로 질문하고, 결과를 검증한 뒤, 결정과 새 지식을 다시 반영하면 됩니다. 위키는 질문할 때마다 조금씩 나아집니다.

## 6.3의 검증 포인트

답변을 위키에 반영할 때는 다음 기준을 확인합니다.

| 점검 항목 | 확인 질문 |
| --- | --- |
| 결정 기록 | 실제로 채택한 결론만 `decisions.md`에 남겼는가 |
| 근거 연결 | 새 지식에 원천 자료 경로와 확인 날짜가 있는가 |
| 원본 보존 | `raw/` 파일을 요약문으로 덮어쓰지 않았는가 |
| 확인 필요 표시 | 근거가 약한 내용을 단정하지 않았는가 |
| 템플릿화 | 반복될 질문을 `templates/`에 남겼는가 |
| 탐색성 | `index.md`에서 새 문서와 템플릿을 찾을 수 있는가 |
| 이력 | `log.md`에 반영 이력이 남아 있는가 |

이 절의 핵심은 “좋은 답변을 저장한다”가 아닙니다. 검증된 답변을 위키의 구조 안에 넣는 것입니다. 결정은 결정 로그로, 새 지식은 주제 문서로, 반복 질문은 템플릿으로 보내야 합니다. 이렇게 나누면 위키가 커져도 다시 찾고 다시 쓸 수 있습니다.
